# Agent files are laid once and shared with the backend by ownership list

opencode reads agents, skills and its config only as files in a Project's `/workspace/.opencode/`. Two parties write there: the image script (`agent-workspace-migrate`), which lays what an Agent's package ships, and the backend, which writes which agent a Project runs, a Custom Agent's prompt and the Skills an Organization added. The backend also lays a Custom Agent's Template into the workspace root. Each owns a fixed list of paths and never touches the other's.

**The image files are laid once, on a workspace's first boot, and a restart re-lays nothing. Built-in content reaches existing Projects only through the Agent-Updates Job, with no pod restart. The backend writes its own files directly over its storage mount before the pod exists, and delivers later changes by writing again and telling the pod.**

- **First boot only.** The init container runs the image script on every boot, and the script does nothing when the workspace has a ledger (`/workspace/.opsiforce/agents/<package>.json`). The ledger is written last, so its presence means the first boot finished, and a crashed first boot is retried whole. On first boot the script lays the package's template when there is one and `app/` does not exist, or else creates an empty `app/`, and runs `git init` with a first commit so Publish has a repository to sync. A workspace that already holds files, because the backend laid a Custom Agent's Template there, gets no package template: its first commit is "Initial template", and a root `.gitignore` it brought keeps its lines and gains every missing platform line under a `# platform` marker.
- **A package is the image folder a pod boots from.** A Built-in Agent's Project boots from `/opt/agents/<name>/` (prompt, skills, template, migrations). Every Custom Agent's Project boots from `/opt/agents/custom/`, which holds only the `platform` skill: no prompt, no template, no migrations. A Custom Agent's starting files are its own Template, which the backend lays before the pod exists ([ADR-0073](0073-a-custom-agents-template-is-a-folder-per-environment-copied-into-every-new-project.md)). `AGENT_NAME` names the package and nothing else.
- **What the image script owns.** (1) `opencode.json`, rebuilt from the image's file: every platform key comes from the image, the `deny` rules included, so a key removed from the image disappears; `default_agent` and any `agents.<slug>` block the package does not ship are carried forward; the package's own model is rewritten from the registry. (2) `agents/<package>.md`, when the package ships a prompt. (3) The skills it wrote, recorded as `ownedSkills` in the ledger. Later runs delete only owned names the image dropped and never touch a directory they did not write.
- **The backend owns everything else in `.opencode/`:** `default_agent`, a Custom Agent's `agents/<slug>.md` (the prompt body, with `model: <provider>/<model>#<variant>` and `mode: primary` in the frontmatter), and the Store Skills — an Organization's Skills on a Built-in Agent, or a Custom Agent's pinned Skills. It writes them before creating the pod, so opencode never boots half-configured. It also names the agent when it creates the primary session, and re-points an adopted session that carries none. Both read one resolver, `runtimeAgentSlug`, which prefers `projects.imported_agent`.
- **Built-in Projects get a fan-out; Custom Projects are written once.** Adding, removing or re-pinning a Skill on a Built-in Agent queues a delivery to every ProjectEnvironment of that Agent in the Organization. A Custom Agent's Project gets its Template, prompt and pinned Skills at create, from its Default environment (Agent) or, for a Test Project, from Development, and they are never re-derived: not on restart, not on Agent Updates, not when the Agent is edited or published ([ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md)).
- **The Job has two modes and covers every environment.** `content` rewrites the config, the package prompt and the owned skills, and bumps the ledger version; it runs on every environment and never asks for a pod recreate. `full` adds workspace migrations and runs only on a Project's Development environment, because migrations edit the app tree that other environments receive from Development through git. A Custom Agent's Project runs the `custom` package, versioned by the agent image version.
- **The backend writes directly.** It already mounts the whole workspace storage, and CephFS makes a completed write visible to the pod's next read. Every file is written under a temporary name and renamed into place. The fan-out is one BullMQ job per environment, deduplicated with `keepLastIfActive` so a change that lands while a delivery runs is not lost. A failed delivery retries on the 5, 15, 30 and 60 minute ladder that the Agent-Updates reload uses.
- **Stage, then rename.** opencode scans `skills/` with `dot: true`, so no temporary directory may sit there. A new skill is built in `/workspace/.opsiforce/staging/` and moved in with one `rename`. An existing skill is updated per file in place, with `.<file>.tmp-<uuid>` names that match no skill pattern. A removed skill is deleted. Skill bytes live in `/workspace/.opencode/skills/<name>/` and nowhere else.
- **Collisions.** Name reservation at Skill creation ([ADR-0051](0051-skills-are-stored-as-immutable-per-file-versions-and-a-built-in-agents-skills-live-on-a-development-profile.md)) makes them rare. When the image ships a skill name the backend also writes: on a Built-in Agent's Project the image takes the name and the backend omits its copy (built-in wins); on a Custom Agent's Project the image script skips the name and never records it as owned (the snapshot wins). The fan-out decides "built-in here" from the installed set in that workspace's ledger, not from the newest registry.
- **One critical section per environment.** The Job and the skill reconcile that follows it (Built-in Projects only) run as one unit, and the fan-out defers while that environment has a `running` row in `project_agent_updates`. The row is the durable claim, and stale `running` rows are reaped before any writer starts. The backend records the name and content hash of each skill it delivered in `project_skill_deliveries`, and deletes a skill only if it delivered it, no longer wants it, and the image does not own it.
- **The pool claim delivers last.** Delivery is the final step before `finalizeClaim`. Reverting a reservation resets rows only, so from delivery on any failure destroys the slot and replenishes the pool. A slot never carries one Organization's files to the next.
- **Publish, Duplicate and Import.** `.opencode/` is git-ignored, so Publish (App) copies Development's backend-owned files into a target that has no `.opencode/` yet, before the target pod is created. A republish touches none of them. Duplicate carries `.opencode/` with the workspace and copies only the delivery bookkeeping. An imported Project whose agent does not exist here links to the Organization's default agent and records the original slug in `projects.imported_agent`.
- **Reload is confirmed.** opencode watches with inotify, which sees only writes made through the local kernel. The backend writes as another CephFS client, which raises no event in the pod. After every write into a running pod (a fan-out delivery, a pool claim, an Agent-Updates Job) the backend calls `agent-control`'s `POST /notify-config-change`, which creates and deletes a marker in each named directory (`.opencode/`, `.opencode/agents/`, `.opencode/skills/`), then polls the pod's `GET /api/skill` until the served set matches. A claim whose pod does not serve its Skills falls back to a fresh Project; a Job whose pod cannot be told recreates the pod once it is idle.
- **The `agents` table carries the registry.** The reconciler writes `origin`, `version`, `model`, `variant` and `pool_size` from the registry at boot, so the pool, the sweep, the picker and the public API read one table for both kinds of Agent ([ADR-0054](0054-built-in-and-custom-agents-share-one-agents-table-told-apart-by-origin.md)).

## Considered options

- **Re-lay on every boot with a script that respects ownership** — safe, but a restart should touch nothing, and with the sweep on every environment the per-boot copy has no job left.
- **Built-in files in a separate root** (`OPENCODE_CONFIG_DIR` on the read-only image, or a second workspace folder) — reading from the image turns every built-in text change into a pod recreate that takes the App down, and a second folder is a second place for the same kind of file.
- **Per-skill symlinks into a store under `.opsiforce/`** — the only truly atomic directory replace, but skill bytes belong in `.opencode/skills/<name>/` and nowhere else. Per-file writes in place give the same no-absent-window guarantee.
- **A two-rename directory swap under `skills/`** — the swap directories are discovered as skills, and a crash between the renames loses the skill.
- **Plugin-served definitions** — snapshot-at-create would need a frozen per-Project copy in the database, `references/` and `scripts/` need real directories anyway, and it puts the backend on the pod's boot path.
- **`OPENCODE_CONFIG_CONTENT` for `default_agent`** — immune to the script, but it cannot hot-reload and splits one key across two sources.
- **A database copy of delivered content** — nothing would read it: Publish reads Development's directory, Duplicate and Export copy the files, and a lost volume loses the App too. Bookkeeping of names and hashes is not a copy.
- **A `custom` entry in `agents.json`** to version the custom package — mixes a non-agent into the file everything reads as "the agents"; the image version serves.
- **A short-lived Kubernetes Job as the backend's writer** — seconds of scheduling per delivery and per claim for a few file writes.
- **A write endpoint on `agent-control`** — does over an authenticated HTTP hop what the backend's mount does natively, and adds a pod-health dependency.
- **An init container that fetches from the backend at pod start** — the volume outlives the pod, so the backend has already written what the pod needs.
- **Serving skills from the database at use time (`skills.urls`)** — puts the Store on the request path, and opencode's discovery needs files anyway.
- **Restart-shaped or polling propagation** — a restart kills the Project's session, and polling adds a poller per pod with staleness no user controls.
- **A generic marker for reload** — does not reach the agent or skill catalogs; a marker per directory does.

## Consequences

- A pod that resumes on a newer image before the sweep reaches its workspace runs the previous built-in content until the Job lands. The state is recorded per environment, and a Store Skill that has not reached some Projects shows as "Not applied to N project(s) yet".
- After an image bump every Custom Agent Project receives one `content` Job, even when only a built-in prompt changed.
- Skill writes are atomic per file and per new skill. A crash mid-update leaves a mixed-version skill that the next run rewrites, because the ledger and the bookkeeping are written last. There is no window in which a skill is absent.
- The workspace root is never deleted and recreated while a pod mounts it: `subPath` pins the inode, so the pod would see a frozen tree. Wipes go to subdirectories only.
