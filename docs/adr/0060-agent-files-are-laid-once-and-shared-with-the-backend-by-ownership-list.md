# Agent files are laid once per workspace, updated only by the Agent-Updates Job, and shared with the backend by ownership list

opencode reads agents, skills and its config only as files in a project's `/workspace/.opencode/` directory. Today the image script (`agent-config/scripts/agent-workspace-migrate.mjs`) lays those files on **every pod boot** and does so destructively — it overwrites `opencode.json` and hard-sets `default_agent` to the pod's `AGENT_NAME`, overwrites `agents/<AGENT_NAME>.md`, and deletes `skills/` before re-copying it (`backend/src/pod/pod.template.ts:85`; `agent-workspace-migrate.mjs:109-123`). The Agent & Skill Platform needs the **backend** to write into the same directory: which agent a Project runs, a Custom Agent's prompt, and the Skills an Organization added ([ADR-0057](0057-authored-skills-and-agents-are-private-or-public-within-one-organization.md), [ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md), [ADR-0059](0059-skills-exist-only-as-published-versions-and-a-built-in-agents-skills-live-on-a-development-profile.md)). [ADR-0053](0053-dynamic-artifacts-delivered-by-direct-backend-write-plus-dispose.md) answered this with a second skills directory, a `skills.paths` config line, a `POST /instance/dispose` call that opencode v2 no longer has ([ADR-0030](0030-agent-owned-file-changes-need-no-opencode-reload.md)), and a sync that re-applied the backend's files after every clobber. It treated the per-boot wipe as a law of nature. It is not one: `AGENT_NAME` was made to mean two things — which image folder to copy from and which agent to run — and one directory had three parties with no rule about who owns what.

**The image files are laid once, when a workspace is born, and never re-laid on restart — as the template is handled today. Built-in content reaches existing Projects only through the existing Agent-Updates Job, with no pod restart. The image script and the backend share `.opencode/` under an explicit ownership list, and the backend writes its files before the pod exists.** Concretely:

- **First boot only.** The init container runs the image script only when the workspace has no ledger (`/workspace/.opsiforce/agents/<package>.json`). A restart, resume, resource change or Restart (environment) touches nothing. The ledger is written last, after every file has landed, so its presence means "provisioned successfully" and a crashed first boot is simply retried.
- **A package is the image folder a pod boots from.** A Built-in Agent's Project boots from that agent's folder (`/opt/agents/<name>/`: prompt, skills, template, migrations). Every Custom Agent's Project boots from one shared folder that carries only the runtime config and whatever shared skills the platform grants Custom Agents — **no prompt, no template, no migrations**; a Custom Agent's workspace starts empty and the agent builds what its prompt describes. `AGENT_NAME` keeps a single meaning, "which package", and is `custom` for Custom Agents. It no longer decides which agent runs.
- **The image script owns three things and carries the rest forward.** (1) `opencode.json` is built from the image's file by an allow-list, not merged from the old one: the image supplies every platform key (so a setting removed from the image disappears); `default_agent` is carried forward from the existing file (the backend wrote it once; it names the agent the Project was created with); `agents.<slug>` blocks for agents the package does not ship are carried forward (backend-owned); the package's own `model` and `agents.<package>.model` are rewritten from the registry (that *is* the model rollout). Written once, temp-then-rename. (2) It overwrites only `agents/<package>.md`. (3) It writes only the skill names in its package and records them as `ownedSkills` in the ledger; on later runs it deletes only names it owned that the new image dropped, and never touches a directory it did not write. A workspace whose ledger predates `ownedSkills` treats everything present in `skills/` as owned, once — the backend has never written skills before this decision.
- **The backend owns everything else in `.opencode/`** and writes it over its storage mount **before creating the pod**, so opencode never boots half-configured: `opencode.json` with `default_agent`, a Custom Agent's `agents/<slug>.md` (prompt in the body, `model: <provider>/<model>#<variant>` and `mode` in the frontmatter), and the dynamic skills — the Organization's Skills on a Built-in Agent, or a Custom Agent's pinned Skills. It also passes the same agent when it creates the primary session, and re-points an adopted session that has none, so a session can never be stuck on the wrong agent (`backend/src/agent-session/pod-opencode.client.ts:72-74` sends an empty body today). Both reads come from one resolver, `runtimeAgentSlug(project)`.
- **Two kinds of Project, one routine.** A Built-in Agent's Project gets its Organization's Skills written at create or pool claim and rewritten by a queued fan-out to every ProjectEnvironment whenever a Skill is added, removed or re-pinned on that Agent. A Custom Agent's Project gets prompt and pinned Skills written once and never re-derived — not on restart, not on Agent Updates, not when the Agent is edited or republished ([ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md)).
- **The Job gains two modes and a wider sweep.** `content` — config, package prompt, owned-skills reconcile, ledger version — runs on **every** environment of a Project and never asks for a pod recreate; `full` adds workspace migrations and runs on **Development only**, because migrations edit the app tree that published environments receive from Development through git. The sweep resolves a Project's package from its agent's `origin` (`custom` for Custom Agents) and versions the custom package by the agent image version, since its shared content changes only when the image does. Pool slots need no sweep: drifted slots are already destroyed and re-provisioned.
- **Skill writes never leave a discoverable temporary directory and never leave a skill absent.** opencode scans `skills/` with `dot: true`, so a `.tmp` or `.old` directory there would be indexed as a skill. A new skill is built complete in a transient staging directory outside the scanned root (`/workspace/.opsiforce/staging/`) and moved in with one `rename`; an existing skill is updated **per file, in place** with `.<file>.tmp-<uuid>` + `rename`, names that match neither `*.md` nor `**/SKILL.md`; a removed skill is deleted. Skill bytes live in `/workspace/.opencode/skills/<name>/` and nowhere else.
- **Collisions.** Publish-time name reservation ([ADR-0051](0051-skill-catalog-append-only-store-tables.md)) makes them rare; when a later image ships a skill name the backend already wrote: on a Built-in Agent's Project the Job takes the name (**built-in wins**) and the backend drops it from its set; on a Custom Agent's Project the Job **skips** the name and never records it as owned (**the snapshot wins**). The backend decides "is this name built-in here" against the **installed** set in that workspace's ledger, not against the newest registry.
- **Two writers, one critical section per environment.** The Job and its post-Job reconcile (Built-in Projects only) run as one unit; the fan-out defers while a `project_agent_updates` row is `running` for that environment — the row, not an in-memory lock, is the durable claim, so a backend restart first resolves a still-running Kubernetes Job before anything else writes there. The backend keeps per-environment bookkeeping of the skill names and content hashes it delivered, and deletes a skill only if it delivered it, it is no longer desired, and the Job does not own it.
- **Pool claim delivers last and fails by destroying the slot.** Delivery is the final step before `finalizeClaim`, for both agent kinds. `revertReservation` resets database rows only (`backend/src/pool/project-pool.service.ts:401-427`); after tenant files have been written it would hand one Organization's prompt and Skills to the next Organization that claims the slot. From delivery onward, any failure — write, reload notification, activation check, finalize — destroys and replenishes the slot.
- **Publish copies once; Import keeps identity honest.** A first Publish (App) copies Development's backend-owned files into the empty target directory before the target pod is created (`.opencode/` is git-ignored and does not travel with the git tree); a republish touches none of them. An imported Project whose agent does not exist in the destination links to the default Built-in Agent's row and records the original in `projects.imported_agent`, which `runtimeAgentSlug` prefers, so the workspace's prompt file and the runtime agent always agree.
- **Reload is verified, not assumed.** opencode's watcher is inotify, which reports operations made through the local kernel; the Job and the backend write from other nodes on CephFS, which keeps the data coherent but raises no local events. The first implementation step is to test a content Job against a pod on another node. If the pod does not notice, `agent-control` gains `POST /notify-config-change`, which creates and deletes a marker under each of `.opencode/`, `.opencode/agents/` and `.opencode/skills/` as needed — three separate places because config reload publishes only when the parsed config differs, agent reload filters events to the agents directory, and skills own their watches — and every writer confirms activation through the pod's `:4096` proxy (`GET /api/agent`, `GET /api/skill`) before it reports success.

## Considered options

- **Keep ADR-0053** (second skills directory under `.opsiforce/`, `skills.paths`, write-then-dispose, universal re-apply) — rejected: dispose is gone, the re-apply existed only because the script wiped, and the owner does not want two skills folders.
- **Re-lay on every boot with a preserving script** — safe once the script respects ownership, but restarts should touch nothing, and with the sweep widened to every environment the per-boot copy has no job left.
- **Built-in files in a separate root** — `OPENCODE_CONFIG_DIR` pointed at the read-only image, or at a second workspace folder such as `.xdg/config/opencode/`, with `.opencode/` backend-only. Clean ownership by root, but reading from the image turns every built-in text change into a pod recreate that takes the user's App down (it runs in the same pod), and a second workspace folder is a second folder for the same kind of file. Rejected.
- **Skill content behind per-skill symlinks into a store under `.opsiforce/`** — the only truly atomic directory replace, and opencode's tests cover re-pointed skill symlinks; rejected by the owner: skill bytes belong in `.opencode/skills/<name>/` and nowhere else. In-place per-file writes give the same no-absent-window guarantee.
- **A two-rename directory swap under `skills/`** — the staging directories are discovered as skills, and a crash between the renames loses the skill.
- **Plugin-served definitions** — opencode plugins can define agents and fileless skills over HTTP and hot-reload; rejected because snapshot-at-create would need a frozen per-Project copy in the database, `references/` and `scripts/` need real directories anyway, and it puts the backend on the pod's boot path. Its `session.hook("context")` is the only runtime way to layer a harness prompt onto a persona and is handed to the harness decision.
- **`OPENCODE_CONFIG_CONTENT` for `default_agent`** — highest-priority document, immune to the script, but cannot hot-reload and splits one key across two sources.
- **A database copy of delivered content** — no consumer survived scrutiny: Publish reads Development's directory, Duplicate and Export copy the files, and a lost volume loses the app too. Bookkeeping of names and hashes is not a copy.
- **A `custom` entry in `agents.json`** to version the custom package — mixes a non-agent into the file the reconciler, pool, picker and public API read as "the agents"; the image version serves.
- **A build-time built-in manifest** for the collision delta — Built-in Skills are database rows ([ADR-0059](0059-skills-exist-only-as-published-versions-and-a-built-in-agents-skills-live-on-a-development-profile.md)); the delta is a query against the installed set.
- **A generic marker touch for reload** — does not reach the agent or skill catalogs; three targeted markers do.
- **`revertReservation` after delivery** — leaks tenant files into the pool.

## Consequences

- **Supersedes [ADR-0053](0053-dynamic-artifacts-delivered-by-direct-backend-write-plus-dispose.md)** in full: no dispose, no second discovered skills directory, no `skills.paths`, no per-boot sync, no build-time manifest, no config overlay. **[ADR-0030](0030-agent-owned-file-changes-need-no-opencode-reload.md) and [ADR-0024](0024-agent-opencode-config-lives-in-the-workspace-opencode-dir.md) stand**; the cross-node reload test above is the verification ADR-0030 lacked, and its outcome applies to ADR-0030's own Job writes. ADR-0058 and ADR-0059 stand unchanged.
- The pod's start script changes from "copy everything, every boot" to "copy once, then only what I own"; the init container's call becomes conditional; the Job splits into `content` and `full`; the sweep covers every environment; the image's hard-coded `default_agent` line is removed from both `agent-config/opencode.json` and `opencode.local.json`.
- The backend gains: writing `.opencode/` before pod create; the dynamic-skill reconcile and its fan-out job; per-environment delivery bookkeeping; the environment critical section; `runtimeAgentSlug`; the activation check; import resolution with `projects.imported_agent`; and — completing [ADR-0054](0054-built-in-and-custom-agents-coexist-by-scope.md) — `agents` gains `origin`, `version`, `model`, `variant` and `pool_size` reconciled from the registry at boot, so pool, sweep, picker and public API read one table for both agent kinds and the per-service registry snapshots go.
- A pod that resumes on a newer image before the sweep reaches its workspace runs the previous built-in content until the Job lands; the window is bounded by the sweep and is recorded and shown per environment, never silent. A Skill the Store lists on an Agent that has not reached some Projects is surfaced there as "not applied to N projects".
- After an image bump every Custom Agent Project receives one content-mode Job even when only a built-in prompt changed — a few file copies with a hash-skipped config write, accepted over inventing a non-agent registry entry.
- Skill writes are atomic per file and per new skill; a crash mid-update leaves a mixed-version skill that the next idempotent run rewrites, because the ledger and the backend's bookkeeping are written last. There is no rollback and no window in which a skill is absent.
- **Glossary**: **Dynamic Delivery**, **Custom Agent** and **Built-in Agent** are rewritten in `CONTEXT.md`.
- This ADR has no home page under `docs/` yet; the feature is unbuilt, and the page is owned by the map's PRD ticket.
