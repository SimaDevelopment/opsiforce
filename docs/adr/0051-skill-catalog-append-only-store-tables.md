# Skill catalog: append-only versions with per-file content rows

The Skill Store introduces dynamic skills — tenant-authored alongside platform built-in — served from one catalog (one set of tables for both, with built-in skills seeded as read-only projections by a boot-time reconciler, and delivery layered: baked files from the image as today, only the dynamic delta materialized by the backend). A skill is a *directory* — `SKILL.md` plus optional `scripts/`, `references/`, `assets/` — so the schema must hold multi-file content and feed four consumers with different access patterns: the store UI (render one file), the publish validator (walk the tree), version diffs (compare file-to-file), and the pod-delivery writer (lay files down). It must also support a draft → validate → publish lifecycle and work in the standalone build with nothing but Postgres and the backend — no object store, no git service, no network at validation time.

**The catalog is four store-family tables, append-only at the version layer, with content as per-file rows.**

- `skills` — identity and lifecycle: `name` (the frontmatter identity and delivery directory name, **immutable after first publish**), nullable `tenant_id` (a tenant relation ⇒ tenant-scoped, absence ⇒ global), `origin` (`built-in` | `authored`), `status` (`draft` | `published` | `archived` | `deprecated`), a mutable `display_name` for store presentation. Name uniqueness is enforced per visibility scope at publish (a tenant's effective namespace — own ∪ global ∪ baked — must be collision-free; built-in names are reserved; no auto-prefixing), because opencode's skill namespace is flat and duplicate names resolve nondeterministically.
- `skill_versions` — **every save is a new row, none is ever mutated.** Rows without a published version number are *draft revisions*; publishing validates one and stamps it with the skill's next integer version, freezing it. Each row carries provenance (`created_via` = ui | builder | import | reconciler, `source_ref` for a git SHA or upstream URL, a change `reason`, a content hash) and denormalized listing fields (frontmatter description, computed flags).
- `skill_version_files` — one row per file per version: path, content, size, binary flag. The `.skill` zip is the interchange format at the import/export boundary only, never the storage format.
- `agent_skill_attachments` — the reference "this agent uses this skill", tenant-level (attaching affects all that tenant's projects on that agent): `(tenant_id, agent_id, skill_id, pinned_version_id)`, unique per triple, `NULL` pin = track latest. No exclusion rows: the built-in skill set is the platform baseline and cannot be subtracted from.

Custom agents version their prompt content in a parallel `agent_profile_versions` table under the same append-only discipline — **custom agents only**. Built-in agents keep their `agents` rows (reconciled from the registry, unchanged), but their content never enters the database: git and the agent image remain its single source of truth. This applies ADR-0008's "one source of truth per artifact" rule by content class — git for baked content, the database for dynamic content — instead of seeding a second, drifting copy.

Lifecycle end-states are deliberately two: `archived` is a tenant retiring its own skill (reversible, permission-gated), `deprecated` is the reconciler observing a built-in skill's removal from the image (platform-driven, not tenant-reversible). Both behave identically for consumers — hidden from the store, closed to new attachments, **existing attachments keep being served unchanged** — so retiring a skill never silently changes a live agent; removal from an agent is always an explicit detach. Hard delete exists only for skills never published.

The publish gate runs entirely offline. Errors (block): the union of Anthropic's `quick_validate.py` and agentskills.io's `skills-ref validate` rules ported to TypeScript, plus artifact hygiene — no symlinks (opencode follows them), no zip-slip paths, invisible-Unicode/ASCII-smuggling rejection across the tree, high-confidence secret-token formats. The no-angle-brackets rule on `description` is a **security control, not style**: opencode 1.18.18 interpolates skill name and description unescaped into the system prompt and validates nothing at load time. Lints (warn only): oversized body, broken or too-deep reference paths, weak descriptions, `allowed-tools` present (warned and stripped — permissions live in platform-owned `opencode.json`). Flags (stored badges disclosed at attach time): `has_executables` — a fact about the tree that cannot be got wrong. An `external_urls` host list was specified here and removed before acceptance: it was a regex over text files, so it missed a URL assembled at runtime and skipped binaries, and nothing constrains a pod's egress — an empty list read as a safety property the platform never promised. Heavier scanning (YARA rule packs, risk scores) and human-approval gates arrive only with tenant→global promotion, a separate flow.

## Considered options

- **One zip/tar blob per version** — rejected: writes are the rare operation and every read path (store page, validator, diff, delivery) would unpack an archive in the hot path. The zip earns its keep as the wire format that makes the `npx skills` ecosystem and vendor repos directly ingestable.
- **Files on the shared volume with DB metadata** — rejected: splits the catalog's source of truth across two systems with different transaction and backup semantics, and complicates standalone for no gain.
- **One polymorphic config-object table for skills and agents** (openwork's shape) — rejected: two artifact kinds with different consumers gain nothing from a shared table in v1, and the generic taxonomy collides with the existing `agents` table, reconciler, and pool machinery. Its append-only versioning discipline is adopted; its storage topology is not.
- **A single mutable draft slot per skill** (Bedrock's DRAFT) — rejected: it introduces a second write discipline into an otherwise append-only family, and discards the draft history that makes Builder-chat edits diffable and restorable.
- **Seeding built-in agent prompts into the DB alongside custom ones** — rejected: a write-only mirror of content git already owns is exactly the two-sources-of-truth failure ADR-0008 removed.
- **Renameable published skills** — rejected: a rename silently changes the flat name-space every agent's skill list is built from and re-points what any pinned attachment means; rename is deprecate-and-create.

## Consequences

- Store UI, validator, diff, and delivery are plain queries; no unzip step exists anywhere in the read path.
- Version retention is unbounded and no pruning code ships in v1; per-skill caps and quota enforcement are a later, purely additive concern.
- Provenance columns (`created_via: 'import'`, `source_ref`) make linked, re-syncing external skill sources a feature addition, not a schema migration; v1 ships one-shot import only, and re-importing an updated upstream lands as the next version, which track-latest attachments pick up automatically on the next delivery sweep.
- An archived or deprecated skill continues to be delivered to agents already attached; operators and tenants reason about "who still uses this" through attachments, not through store visibility.
- The API contract (skills CRUD, draft/validate/publish/archive verbs, import/export, and the agent-attachment subresource) is the single surface the store UI, the Builder chat, and any future CLI all consume.
- The gate's error tier is deliberately dependency-free TypeScript; anything requiring rule packs, scanners, or human review is scoped to global promotion so tenant self-service stays instant.
