# An External Service fetches its configurations from the backend by the Caller identity and holds them only in memory

A Custom External Service runs as an App in a pod whose one container also holds an Agent, its shell and code-server, all as root with one shared environment. Any secret that sits in the pod can be read by the Agent there. The Gate forwards a call untouched ([ADR-0046](0046-an-external-service-owns-its-api-and-its-service-policy-the-gate-only-identifies-the-caller-finds-the-service-and-forwards-the-call-untouched.md)), so a configuration cannot travel inside it, and a service does work without any caller: inbound deliveries, background work, a connection kept open to its outside system.

**The backend keeps every `secret` field sealed at rest. The service's SDK fetches the configurations from the backend with its pod's own Gateway Key: the calling ProjectEnvironment's Project configuration, named by the request's Caller identity, and the Service configuration whole. It holds them in process memory, drops a copy when the backend tells it of a save, and keeps no copy longer than five seconds.** Concretely:

- **Fetched, never carried or written.** No configuration travels in a forwarded request or its headers, on the pod's volume, or in the App's Environment Variables. The SDK asks the backend, not the Gate.
- **Unsaved values are the one thing carried.** A Form's option list, info or button is asked while a person edits, before anything is saved, so the platform's call carries the unsaved values in its body, with stored secrets filled in and opened. A Project form's handler still reads the saved Service configuration through the fetch; a Service form's handler sees the unsaved values as its Service configuration. An after-save hook's body carries the previous and current values, because the previous one is not what a fetch returns.
- **The asking pod picks the Service configuration.** Development's pod receives Development's own Service configuration ([ADR-0086](0086-the-external-service-builder-tests-a-service-through-a-consumer-agent-against-developments-own-service-configuration.md)), and the Default environment's pod receives the one callers use.
- **The Caller identity names the Project; it guards nothing against the pod.** The pod holds the key that signs Caller identities, so the service's own code can read every Project configuration of its service. That is accepted: only holders of `can_manage_tenant_external_services` build a service, and they are the people who set its Service configuration. What must never happen, a service acting for whoever reaches its address, is stopped by the SDK refusing every request without a valid Caller identity.
- **Save calls keep it fresh; a short life backs them up.** On every save of a Project configuration, including its removal by Disconnect, the backend calls the pod's `onProjectConfigurationSaved`, and the SDK drops that Project's copy before the service's own hook runs. A copy lives at most five seconds, so a save whose call failed still applies within that time. The Caller identity carries only who is calling, no version. A fetch that finds no Project configuration answers "none": the SDK refuses the caller as not connected and remembers that the same way. A request reads its configuration once, when it starts; a stream already open keeps what it read.
- **Code without a caller reads the same Service configuration by name.** After every Service configuration save the backend calls the pod's `onServiceConfigurationSaved`, whether or not the service has a hook of its own. The SDK drops its copy and tells the service's code before running that hook. The five-second life catches a save whose call failed. Nothing else polls.
- **One Service configuration.** Every handler sees the whole document, as the backend sends it. Using only the items the caller's Project configuration references, such as the WhatsApp number a Project was given, is the service's Service policy, taught to the builder.
- **The answer carries the settings link.** With a caller's Project configuration the backend also returns the address of that Project's settings for this service, which the SDK puts in its refusals so a caller can be sent straight to the setting that refused it.
- **Incomplete means refused.** The backend's answer lists the required fields missing from either configuration, such as a field added by a later Publish. The SDK refuses the call before the service's code runs, with a message an Agent can relay that names the fields and whom to ask. There is no opt-out.
- **Secrets are guarded against accidents, not against the people who build the service.** The SDK keeps them in process memory only, never in logs, and hands each `secret` field over as a `Secret` whose JSON and string forms are masked. An answer of a route the service handles itself, or of a Form or hook handler, that contains the value of any `secret` field fails instead of being sent, and is recorded as `failed` with that reason. Proxied answers pass untouched. The builder Agent shares a container with the Organization's real secrets and can reveal them on purpose, which is why only holders of `can_manage_tenant_external_services` may build a Custom External Service.

A Custom External Service's own pod is therefore the one App that sees provider secrets ([ADR-0044](0044-apps-reach-non-llm-services-through-the-backend-owned-service-gateway.md)); the Apps that call it never do.

## Considered options

- **The Gate carries the configurations in headers of the forwarded request.** Rejected: the Gate would hold plaintext secrets, header size limits cap a configuration, and a service that copies incoming headers to its outside system would ship them there.
- **Writing secrets into the pod, as a file on the volume or the App's Environment Variables.** Rejected: that is plaintext on the volume, and every save restarts the App.
- **Fetching on every request.** Rejected: it puts the backend and a decryption back on the path of every forwarded request, and clients such as kubectl and gh send many small ones.
- **A version stamp per configuration in every Caller identity.** Rejected: the backend already calls a hook on every save, so stamps duplicated that push, needed counters for every configuration, and put more than who is calling into the identity.
- **Caching for a fixed time alone.** Rejected: every change would wait out the whole time. With the save calls, the time limit is only a backstop.
- **Trimming the Service configuration per caller, in the backend or the SDK.** Rejected: code without a caller needs the whole document anyway, so trimming protects nothing from the pod while tying the trimmer to the meaning of the service's Forms and giving handlers two shapes of one document.
- **A Caller identity the pod cannot forge, signed by the backend and checked with a public key, so a pod fetches only for Projects that called it.** Rejected: the same code can record the identities of incoming calls, and it costs an audience claim and key distribution to every pod.
- **Never letting secrets into the pod: the backend sends each outgoing request and fills secrets in only for hosts the Service manifest allows.** Rejected: a database driver speaks its own wire protocol, not HTTP, and many vendor SDKs accept no custom fetch.
- **A Production pod for a service that runs only the App.** Rejected: a service's ProjectEnvironments stay like every other Project's. The building permission already limits who reaches them.

## Consequences

- A service can keep a long-lived connection to its outside system (Slack Socket Mode, a Discord gateway) open and work between calls; it learns of a changed Service configuration from the save call.
- The master encryption key is used on each fetch, not on each call, and the backend is on a call's path only when the pod's copy is empty: after a start, a wake, a save, or five seconds.
- A removed permission stays usable until its save call reaches the pod, at most five seconds if that call fails, and for as long as a stream opened before the change stays open.
- A bug in a Service policy can use any item of the Service configuration; nothing trims it.
