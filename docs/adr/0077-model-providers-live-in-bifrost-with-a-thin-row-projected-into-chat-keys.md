# Model providers live in Bifrost with a thin row, and their weights are projected into chat keys

An Organization chooses its own Model providers, so something has to hold each one's key, URL and Base format, and something has to carry its switch and weight to every `chat` virtual key the Organization owns.

**A Model provider is a Bifrost provider plus one `model_providers` row (`tenant_id`, `bifrost_provider`, `enabled`, `weight`), and the backend projects the rows into the `provider_configs` of every `chat` key of the Organization; reachability, computed from the same rows, gates the model pickers.** Concretely:

- **The row is thin.** It stores no key, URL, Base format or kind: those live only in the Bifrost provider, as its single encrypted copy, and are read from it. A NULL `tenant_id` makes the row a platform provider, whose `enabled` and `weight` are every Organization's values for it; an Organization's row of the same provider replaces them, and exists only while its values differ. The pair is unique with NULLS NOT DISTINCT, and a weight is an integer from 0 to 100.
- **The Base format registry is a code constant.** Each entry (`openai`, `anthropic`) holds Bifrost's `base_provider_type`, the opencode provider id and `models.json` key, the official API URL, the connection test, the allowed kinds and the `allowed_requests` profile per kind, so a new format is one entry plus image changes.
- **`writeChatKeys` writes the whole projection, per Organization, under an advisory lock.** A row is written only when it is reachable: switched on, present in Bifrost and, for a Linked account, connected. Its weight is written as is, so 0 is a backup that Bifrost's own fallback list still reaches, and switching a row off removes it from the key. Weights split traffic only within a Base format because Bifrost first filters a key's providers by the requested model.
- **Bifrost's URL check is the only address rule, and admin-typed URLs are `https://` only.** A typed base URL is written to the Bifrost provider before the connection test, with `allow_private_network: false` and no `proxy_config`, so Bifrost refuses private addresses at save and again at every connection after resolving the name itself, and its refusal reaches the admin as is. The backend adds only the `https://` rule: Bifrost always allows loopback, and its own port is plain http, so a plain-http URL on `127.0.0.1` would loop requests into Bifrost for every Organization. The test never follows a redirect, which would get around Bifrost's check.
- **It runs on every change, never on a timer.** Every save, global create and delete, Linked-account change, every Project create and every pool claim runs it; a failed write fails the calling operation. A pool slot's `chat` key is created with no providers, and the claim writes the claiming Organization's before it finalizes, retrying like the budget and team patches and falling back to the slow path when it keeps failing.
- **The `backend` key is never projected.** It keeps the built-in `openai` and `anthropic` at fixed equal weights, because the App's own AI features and transcription depend on the real vendor catalogue.
- **Reachability gates the pickers and warns before it breaks an Agent.** The reachable Base formats are those with at least one reachable row, computed on every read from the rows and Bifrost's provider list with no cache. They filter the Agent Profile picker and the chat's model picker, and a member-open read serves them with nothing else about the providers. A card save that would leave its format unreachable answers with the Custom Agents whose Profiles name a model of that format and the Built-in Agents whose Agent Model is in it, and goes ahead only when the request acknowledges them; nothing is blocked or rewritten. When Bifrost is not configured or cannot be read, every format counts as reachable, so a gateway outage never empties the pickers.
- **An existing deployment is cut over by a migration alone; a fresh install is seeded from env.** The migration creates rows only on a database that already has Organizations: the platform rows `openai` 0, `anthropic` 1, `custom-openai-1` 1, which every Organization inherits. It rewrites no `chat` key: the keys created before it hold `openai` 0, `anthropic` 1, `custom-openai-1` 0.3, which route exactly like the rows because `anthropic` and `custom-openai-1` never serve the same model, so each Organization's keys take the rows' weights at its first sync. On a database with no Organizations the migration creates nothing, so the first boot finds no platform row and gives `openai` and `anthropic` platform rows at weight 1 each: one Bifrost already has, as Helm declares it, is adopted without touching its key, and one it lacks is created from `OPENAI_API_KEY` / `ANTHROPIC_API_KEY`, only when set, through the platform create code. Weight 1 because a card whose only switched-on row weighs 0 can't be saved. The seed never runs again and never creates a Linked account.
- **A platform provider reaches every Organization by inheritance, and only the Organization turns an added one on.** Every Organization reads every platform row, switched and weighted like it unless it saved its own values: `openai`, `anthropic` and `custom-openai-1` on, an `opsiforce-*` provider off. Creating an `opsiforce-*` provider writes only its platform row and touches no `chat` key, since a switched-off provider changes no projection, and deleting it removes the platform row and every Organization's own row of it and resyncs every Organization; there is no per-Organization choice of who gets it, because a switched-off provider already costs an Organization nothing and leaves the decision with its own admin. A save holds the platform lock shared, so a platform delete can't leave an Organization's row of a provider that no longer exists.
- **`custom-openai-1` is on in every Organization, like the fixed built-ins.** On a fresh install its platform row appears, switched on at weight 1, when a platform admin first signs it in, and the same transaction resyncs every Organization's `chat` keys to take it.
- **Helm declares the platform's `openai` and `anthropic`, and production's `custom-openai-1`, under `split`.** Their keys come from `env.*` references to a Secret, and production's `custom-openai-1` stays a key-less provider at the hosted Codex OAuth Dock, so a deploy changes no traffic and needs no key-storing step before it; a platform admin's sign-in moves `custom-openai-1` to the Linked-account Proxy. Bifrost's `split` source of truth never prunes what its database holds, and keeps a Helm-declared provider's database version while its entry in the values is unchanged, so a key replaced, a connection edited or a sign-in written through the Admin API survives restarts; changing a provider's Helm entry makes the file win for it at the next restart. Every other provider is created and changed only through the Admin API, and only the `backend` key's weights stay fixed in code.

## Considered options

- **A Bifrost routing rule per Organization.** Rejected: a rule picks a target by weight without checking the model, so it needs one rule per Base format with a CEL list of that format's model ids, it cannot grant access a key does not already list, and its single fallback list retries the provider that just failed.
- **Storing the key and URL in our database and reconciling Bifrost from it.** Rejected: it keeps two copies of every secret and adds a reconciler, while Bifrost in `split` mode already keeps API-created providers across restarts.
- **Keeping switched-off rows on the key with a `*` blacklist.** Rejected: absent is the only state every Bifrost check agrees on, and it needs no second meaning for a present entry.
- **A backend address check of its own, or a per-deployment allowlist for private networks.** Rejected: it would duplicate Bifrost's check without its connect-time re-resolution, and LAN-hosted models and Private-Endpoint Azure are out of scope; a Foundry resource behind a Private Endpoint resolves to a private address, which Bifrost refuses for a Compatible endpoint.
- **The migration creating the platform rows on every database, fresh ones included.** Rejected: a migration can't read Bifrost, so on a fresh install whose Bifrost lacks a built-in it would create a row with nothing behind it, and the boot seed, which runs only while no platform row exists, would never create the missing provider from env.
- **Helm declaring no Bifrost provider.** Rejected: a provider dropped from the values keeps its `env.*` key references in Bifrost's database, which stop resolving once the Secret wiring goes with it, so every environment's deploy would depend on storing its keys as values by hand just before its push, and a fresh install's built-ins would depend on the backend's env rather than the deploy's Secret.
- **Copying every platform row into every Organization when it is created, and into every existing Organization when a platform row is added.** Rejected: a platform row's switch and weight are never edited after it is created, so the copies hold nothing an Organization chose; they multiplied the rows by the Organizations, needed a grant on every Organization create and platform create, and hid which values an Organization had actually set.
- **Rewriting every Organization's `chat` keys once after the migration, from a queue the migration fills.** Rejected: the rewrite changes no routing, so it would add a table, a boot step and its retries only to make the Bifrost dashboard show 1 instead of 0.3 sooner.
- **A periodic drift sync.** Rejected: every write that changes the projection already runs the sync, and a timer would hide a failed write instead of failing its operation.
