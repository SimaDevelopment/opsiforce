# Each Custom domain gets its own route, carrying its App's gate or the unprotected marker, and signs in on its own host

A [Custom domain](../../GLOSSARY.md) is the first App host outside the apps domain. Three protections assume every App host is under it: the catch-all apps route that carries the unprotected marker, the pattern rules of App Auth's gate route, and a Sign-in provider's one callback with its session cookie on the apps domain. A domain that skipped any of them could serve a protected App without sign-in, or could not sign anyone in.

**Each Custom domain that passes Check gets its own IngressRoute, matching exactly its host and naming its certificate. One function builds it, and it always carries exactly one of these: the environment's App Auth middleware when the App is protected, the `X-Opsiforce-Unprotected-Route` marker Middleware when it is public, or a redirect that answers before the request reaches the App: a bare domain's `www` to that bare domain, and a domain its owner set to redirect to the [Main domain](../../GLOSSARY.md) while the App has one. A Custom domain signs visitors in on its own host, at `https://<domain>/oidc/callback`, with a session cookie for that host alone.** Concretely:

- **One route per domain, not one more rule in the gate route.** An IngressRoute names one certificate, and a public App has no gate route at all. A route of its own lets a domain be added, re-pointed or removed without touching the App's other routes.
- **A domain's state and its objects change together.** A pass, a connect, Make main, Remove and a takeover each run in one transaction under the environment's App Auth lock and write or delete the cluster objects before committing, so a failed write rolls the change back and the next look or press tries again. A takeover deletes the old App's route before the new App holds the domain, since the app proxy checks the marker but not which environment's sign-in let a request through.
- **The marker covers these routes too.** A public App's domain route carries the marker, so if the App turns protected and rewriting that route fails, the app proxy answers 403 instead of serving the App unsigned-in. A test asserts that every route the function builds carries exactly one of the three. This is the guarantee the per-environment signed route proof considered in [ADR-0012](0012-a-public-url-reads-as-app-slug-environment-slug-and-app-short-id-and-old-hosts-keep-serving.md) would have given, without a Middleware per environment or a mandatory signing key.
- **Every domain serves on its own host unless its owner sends it on to the Main domain.** One App can then answer as several brands or regions, and it sees which host was asked for. A domain set to redirect answers with a temporary 302 to the same path on the Main domain before any sign-in, since Make main and the switch can turn the destination around and a browser keeps a permanent one; the Main domain is still the one Public URL. Each domain that serves a protected App signs visitors in there and needs its own callback registered, which is the price of serving it. Until the first domain connects the App has no Main domain, and every domain serves on its own host, so the first one to connect works at once.
- **A bare domain's `www` always sends visitors to the bare domain,** in one hop and permanently (Traefik answers 301 to a GET), and the bare domain then serves or redirects by its own setting.
- **`manual` and `app_users` App Auth need nothing new.** Their middleware already uses the relative callback with a cookie for one host, so the environment's middleware serves the domain as it is. Like every gate, it runs after the shared headers Middleware that drops caller-supplied `X-Oidc-*` headers ([ADR-0007](0007-per-environment-app-auth.md)).
- **`provider` App Auth gets a second copy of the environment's middleware for its Custom domains,** filled from the same Sign-in provider row, in relative-callback mode with no cookie domain. It exists while the environment has a Custom domain issuing its certificate or connected, and every write of the environment's App Auth (an Auth mode change, inherited App Auth, a save of the provider) rewrites it together with the domain routes, so switching public and protected swaps marker and gate at once. The domain's instructions show its callback for the identity provider's admin to register, and "Make main" shows the new Main domain's callback before it switches.
- **The backend resolves a Custom domain like any other App host.** The App address lookup answers the way the routes do, through the same per-host rule: a domain issuing its certificate or connected with serve on its own host, a bare domain's `www` with a redirect to that bare domain, a domain set to redirect with a redirect to the Main domain while the App has one, and an unknown host with 404. Default addresses keep serving without redirecting to the Main domain.
- **App code never sees the platform's cookies on a Custom domain.** The app proxy already strips every `_opsiforce_` cookie on every request it serves, whatever the host.

## Considered options

- **Adding the domain as one more rule in the environment's gate route.** Rejected: an IngressRoute carries one TLS block, a public App has no gate route to add it to, and every domain change would rewrite the route that guards every other host of the App.
- **One route per environment with a TLSStore gathering its domains' certificates.** Rejected: fewer objects, but a shared list of certificates to keep in step on every add, move and remove, where a route per domain is created and deleted on its own.
- **Redirecting alias hosts in the app proxy instead of a redirect Middleware.** Not now: the proxy already redirects to an App's canonical host, but a protected App's alias must redirect before sign-in, which the proxy only sees after Traefik's sign-in middleware.
- **The per-environment signed route proof from ADR-0012.** Rejected: every custom-domain route is written by the one function the test covers, so the marker gives the same guarantee for them. The proof would add a Middleware per environment to every App Auth write and to the start-up rewrite, and would make the token-forwarding signing key mandatory everywhere.
- **Signing custom-domain visitors in through the sign-in host's one callback, then handing the session to the domain** (Base44's default). Rejected: the session cookie on the apps domain never reaches a Custom domain, so the hand-off needs the ticket broker ADR-0097 already rejected, about a thousand lines of our own.
- **Every other Custom domain redirecting to the Main domain, with no choice.** Rejected after the first build: an owner who connects a second brand's domain expects it to show the App at that address, as Base44 does. Redirecting stays one switch away for owners who want a single address for sign-in and search engines.
- **Redirecting the Default address to the Main domain.** Rejected: links already handed out, registered callbacks and API clients that drop the body on a cross-host redirect keep using the Default address.

## Consequences

- With `provider` App Auth, a visitor signed in on one App's Default address is asked to sign in again on its Custom domain, since the session cookie is per host there.
- An Organization's identity provider admin registers one more callback per domain that serves a protected App: the Main domain, and every other one not set to redirect. Until then, sign-in on that domain fails at the identity provider.
- Search engines may index the App at each domain that serves it; an owner who wants one address turns the redirect on.
- The start-up rewrite that repairs drifted gate routes covers custom-domain routes too, so a route written before a rule change is rewritten like any other.
- A host the platform does not know reaches no route and gets Traefik's 404. Since custom-domain routes match exact hosts, this includes a removed domain whose record still points at the App.
