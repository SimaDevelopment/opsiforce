# Builder chats are hidden Projects whose store writes resolve to the launching user

The Skill & Agent Builder — the Built-in Agent that authors Skills and Custom Agents through conversation ([ADR-0051](0051-skill-catalog-append-only-store-tables.md)/[ADR-0052](0052-custom-agent-anatomy-and-model-presets.md) lifecycle; Anthropic's skill-creator methodology mapped onto it in `.scratch/agent-skill-platform/research/anthropic-skills-ecosystem.md`) — needs a chassis and a credential. The chassis: every piece of chat runtime (pod lifecycle, keep-alive/suspend, the chat proxy, storage attribution, per-environment gateway keys) hangs off Project → ProjectEnvironment and project↔session is 1:1 — yet the product decision is that authoring is *not* a workspace artifact: Builder chats belong to the Store/management surface, never the project list. The credential: the Builder must create Draft Revisions, run validation, and read the store (name-collision checks, edit round-trips) through the backend API from inside the pod, and [ADR-0055](0055-skill-store-authoring-rides-four-flat-scope-partitioned-permissions.md) requires every pod-originated write to be judged as the launching user's permission set — while pods hold no user credential and the chat proxy authorizes by tenant membership only (`backend/src/proxy/proxy.controller.ts`), so the pod never learns which member is prompting.

**A Builder chat is carried by a hidden Project, and its store writes authenticate with the existing gateway key, resolved server-side to the chat's creating user.** Concretely:

- **Hidden carrier.** Each Builder chat is a real `projects` row (`agent` = the Builder's slug, `workspace_id` NULL), excluded from every workspace/sidebar/project listing — unclaimed pool projects are the standing precedent for rows that exist without surfacing. It is reachable only from the Store's Builder surface, which presents a chat *list*: "New chat" per authoring task, past chats revisitable, archive/delete manual. Normal keep-alive/suspend applies; the template ships no `app/` and nothing ever pushes go-live, so no app pane, no publish flow, no terminal state — publishing each artifact is the milestone, the chat itself is a tool.
- **Creator-only access.** The proxy's ensure hop adds a creator check for Builder-kind projects — tenant membership is not enough — because chat access *is* the write credential's perimeter: whoever prompts the chat acts with the creator's authority.
- **The credential.** A new `gateway/store` controller family rides the existing `GatewayAuthGuard` (`projectGatewayKeys` — the same trust path that carries go-live state, schedules, and agent-status pushes today). A store guard adds one resolution hop: gateway identity → project → `created_by` (a new column stamped at creation) → **that user's live permission set, evaluated per call**. A creator who loses `can_manage_skills` mid-session is refused on the next write. No user token ever enters pod env, and nothing needs refreshing across suspends. Standalone is untouched: gateway keys are Keycloak-free and permission resolution follows ADR-0055's static bundle.
- **Chat powers stop at drafts.** The chat creates Draft Revisions and runs validation (results rendered in-conversation); **Publish and Attach remain Store-UI acts** — publish is the blast-radius moment (Dynamic Delivery to every track-latest Attachment) and stays a human click on the one surface where ERRORS/LINTS/FLAGS render. Edit round-trips are agent-pulled through the API; the backend's workspace write surface stays delivery-only, preserving [ADR-0053](0053-dynamic-artifacts-delivered-by-direct-backend-write-plus-dispose.md)'s one-directory-one-writer rule.
- **One profile, both artifact kinds.** A single public Built-in Agent (ships in the standalone mirror) carrying two authoring skills (`skill-authoring`, `agent-authoring`); registry `poolSize` 0 (authoring tolerates a cold start), model initially app-builder's preset. v1 testing is skill-creator's documented degraded path — serial in-session runs, conversational feedback — stated honestly in the prompt (a skill for another agent is tested outside its target context).

## Considered options

- **User-scoped token in pod env** — rejected: a user credential sits in LLM-readable env for the pod's lifetime and needs expiry/refresh across suspends; gateway identity plus server-side resolution yields the same authorization with no new secret.
- **Workspace-mediated submit** (Builder writes files; a human clicks "save"; the backend reads the tree over its storage mount) — rejected: no append-only Draft Revisions from chat, no in-chat validation loop, and the Builder still needs API reads for collision checks and edits.
- **A new non-project chat runtime** — rejected: forks pod lifecycle, proxying, keep-alive, and storage attribution to satisfy what is a presentation rule; hiding the row achieves the UX on the existing chassis.
- **Visible regular Projects** (in workspaces, restricted to the Personal Workspace to close the shared-prompt loophole) — rejected by product decision: authoring is not a workspace artifact, and outside personal workspaces visibility re-opens the loophole the creator check closes.
- **In-chat publish on the user's say-so** — rejected for v1 (additive later): one publish surface keeps one audit shape, and the launching user's `can_manage_*` grant makes the Store click costless.

## Consequences

- `projects` gains `created_by` — stamped for all new projects (generally useful provenance), required for Builder-kind gateway writes.
- The Agent picker excludes the Builder profile: its Projects are never created through the normal new-project flow, so the registry/picker liveness rules of [ADR-0054](0054-built-in-and-custom-agents-coexist-by-scope.md) gain one exclusion.
- Builder-surface visibility mirrors ADR-0055: creating a Builder chat requires `can_manage_skills` or `can_manage_agents`; each write endpoint checks the specific string for its artifact kind.
- Storage attribution is unchanged (Builder chats are tenant projects and appear as such in Admin storage); only listing queries learn to exclude them.
- Glossary: **Skill & Agent Builder** and **Builder chat** added; "Builder Project" retired.
- Deferred, recorded so they aren't re-litigated: in-chat publish, shared Builder chats (cloudflare-os-style build/use roles), parallel with/without-skill benchmarking and description-trigger optimization (both need ephemeral sessions — collides with project↔session 1:1), and per-message actor stamping through the chat proxy.
