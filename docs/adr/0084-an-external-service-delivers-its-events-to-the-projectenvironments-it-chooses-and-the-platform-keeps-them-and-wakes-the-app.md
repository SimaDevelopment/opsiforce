# An External Service delivers its Events to the ProjectEnvironments it chooses, and the platform keeps them and wakes the App

An outside system sends one webhook per registration (a Whapi number, a Mailgun domain, a GitHub repository) to the one address it was given, while any number of ProjectEnvironments may want what it carries. Which of them should hear a GitHub `issues.opened` for `acme/web` depends on what each Project configuration covers and what its people chose to hear. The platform does not read Project configurations for meaning, and it never reads, changes or judges what a service is sent or answers ([ADR-0046](0046-an-external-service-owns-its-api-and-its-service-policy-the-gate-only-identifies-the-caller-finds-the-service-and-forwards-the-call-untouched.md)). Some sources send no webhooks at all and must be polled, or speak over a socket the service holds open.

**The service turns whatever reaches it into Events, picks the ProjectEnvironments that receive each one, and hands it to the platform; the platform checks only that each receiver is connected to the service, keeps the Event for that environment's App and wakes the App to take it.** Concretely:

- **A webhook address per service, on the platform's main host.** An outside system sends to `/api/external-services/webhooks/<id>/<any path>` on the platform's own host, the address services have today: a Custom service's id, because the sender has no caller credential to say which Organization a slug means; a Built-in's slug. The Gate lets every request through with any method, path, header and body and no size or time limit, removes incoming `X-Opsiforce-*` headers (all but `X-Opsiforce-Webhook-Secret`, the header the WhatsApp built-in's numbers are registered with) and the platform's `Cookie`, and adds a `platform` Caller identity naming no ProjectEnvironment. It adds `Content-Security-Policy: sandbox` and `X-Content-Type-Options: nosniff` to the answer and changes nothing else. The pod receives it under `/.well-known/opsiforce/webhook/`, where the SDK runs the service's webhook handler, never a Service route, and refuses it to a `call`. A first path segment `development` after the id reaches the Development copy. The address never changes, so registrations made upstream survive a Default-environment switch and this change.
- **The service checks the webhook.** It verifies the sender's signature or secret itself and answers the sender as the sender expects, including verification handshakes.
- **The service chooses receivers.** It reads every Project configuration it has (`service.projectConfigurations()`, fetched and cached by the SDK) and delivers each Event with the list of ProjectEnvironments that receive it. What a Project hears is decided by fields of its Project form that the service's author designed: the repositories it covers, the chats it listens to, a "Notify on" choice. Delivery works from any code, not only a webhook handler: a poll loop, a schedule, an upstream socket.
- **The platform checks who, not what.** A delivery to a ProjectEnvironment that has no Project configuration for the service, or that is in the other copy's lane (the Development copy delivers only to its Test Project), is refused for that receiver. The platform checks the envelope: the Event type is declared in the Service manifest, `key` and `occurredAt` are present, and the size is within limits. It never reads `data`. It also caps deliveries per receiver: beyond a fixed number of Events per minute from one service to one ProjectEnvironment, that receiver's result is `over-cap` and nothing is stored for it, while the other receivers of the same Event are stored. The cap counts receivers, not content, so a runaway loop fills no App and wakes none without end.
- **Events are declared by type only.** The Service manifest lists each Event type with a title and a description. The shape of `data` is documented in the service's Service skill, which is what an App's Agent reads.
- **One generic store.** Each receiving environment's `external-services.db` holds `events (id, service, type, key, occurred_at, received_at, data, app_delivered_at)` and `event_files`, with the file bytes on disk beside it. `key` drops a resent Event per service, type and environment, so a service may retry any delivery. Events are kept for good; changing a Project configuration never deletes what was delivered.
- **Stored before the sender hears back.** The platform answers a delivery only after storing it and queueing the doorbell, per receiver (`stored`, `duplicate` or refused), so a webhook handler answers the sender with success only when nothing was lost and the sender's own retry covers the rest.
- **The doorbell is durable and wakes the App.** One coalesced job per environment × service wakes the App as Schedules do, reads the undelivered Event ids at ring time, posts `{service, eventIds}` and retries with backoff. A `404` or `501` marks the App as not wired until its next start. The doorbell carries no authentication: its body is ids into the App's own read-only database.
- **Built-in services take the same path.** Incoming email and WhatsApp run in the backend's process and use the same kind of webhook address (by their slug), receiver list and delivery through an adapter: email picks the configuration whose address matches the recipient, WhatsApp the ones listening to that chat on that number.

## Considered options

- **The service answers the webhook with a receiver list, and the platform stores what it lists.** Rejected: the platform would sit inside the webhook, parsing and reshaping the service's answer, and only a webhook could produce an Event.
- **Platform Receive switches per Event type, off by default.** Rejected: a type toggle is the only choice the platform can generate, and real choices (these chats, issues with this label) are the author's design; a Project-form field covers both.
- **The service keeps Events and Apps fetch them through its Service host.** Rejected: Events are the receiving App's data; a service that is disabled, deleted or down must not take an App's history with it, and an App queries its own Events with SQL.
- **Webhooks forwarded fully untouched on the platform's main host.** Rejected: on the host where users' sessions live, it hands every service author a page that a signed-in user's browser visits with the platform's session cookie. Dropping the cookie and sandboxing the answer closes that.
- **A separate webhook host per service (`<id>.external-services.<base>`).** Rejected: it needed a second lane in the Gate, a rule that slugs never look like ids, and moving every registration made upstream (WhatsApp re-registering itself, Mailgun Routes re-pointed by hand, an alias kept for a release), while the main-host path with the cookie dropped and the answer sandboxed already closes the session risk.
- **Refusing a whole delivery with 429 when one receiver is over the cap.** Rejected: one busy receiver would block every other receiver of the same Event.
- **A Data schema per Event type, checked by the platform.** Rejected: the platform would judge content, and a schema nothing else reads drifts from the code that fills it.

## Consequences

- A service with a wrong receiver choice delivers one Project's Events to another connected Project of the same service, as a wrong Service policy would let it act for one; nothing in the platform catches either.
- How much a Project hears is the service's design, up to the per-receiver cap. A source that is legitimately busier than the cap needs its service to batch Events.
- An environment's `external-services.db` grows without limit; an App that only needs recent Events still cannot delete old ones.
- Existing registrations at `/api/external-services/webhooks/<slug|id>` keep working unchanged; nothing upstream has to move.
- Dropping the cookie and adding the sandbox are the one change the Gate makes to a webhook. A service can still serve a static page without scripts or forms under the platform's domain; only holders of `can_manage_tenant_external_services` build services.
