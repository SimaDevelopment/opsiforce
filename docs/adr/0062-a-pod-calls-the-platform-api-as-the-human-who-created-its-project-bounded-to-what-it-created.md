# A pod calls the platform API as the human who created its Project, bounded to what it created

The Skill & Agent Builder must test the child agent it authored by running it in a real Project ([ADR-0056](0056-builder-chats-are-hidden-projects-with-writes-resolved-to-the-launching-user.md)), and nested sessions from webhooks and schedules (#1505) need the identical primitive: a pod calling `/api/v1` on its own. Today it cannot. `CallerSource` is the single-member union `'idp-bearer'`, `PublicApiGuard` builds its `Caller` from oauth2-proxy identity headers ([ADR-0034](0034-public-api-callers-are-idp-bearer-tokens-behind-a-caller.md)), and a pod holds no user credential — by deliberate choice, since a user token in pod env would be LLM-readable for the pod's lifetime and would need refreshing across suspends. What a pod does hold is a gateway key: `projectGatewayKeys` issues one `gw-<uuid>` per ProjectEnvironment, `GatewayAuthGuard` resolves it to `{projectId, projectEnvironmentId, tenantId}`, and five internal controllers already trust that path for schedules, external services, app state and agent status. ADR-0056 chose the resolution rule — gateway identity → Project → creator → that user's live permission set per call — but `projects.created_by` does not exist, the key is handed to the whole container as `SERVICE_GATEWAY_API_KEY` where app code and injected content can read it, and `/api/v1` is a far larger surface than a project's own schedules.

**A pod authenticates to the platform API with a second gateway key of its own, resolves to the human who created its Project, and may act only on Projects it created — with that human's full authority over those.** Concretely:

- **A separate credential for a separate authority.** `project_gateway_keys` gains `purpose` (`service` | `platform-api`). The `service` key is today's, unchanged, in every pod as `SERVICE_GATEWAY_API_KEY`. A `platform-api` key is minted only for Projects whose Agent declares it needs one, and reaches the pod as a distinct env var alongside `OPSIFORCE_API_URL` — `SERVICE_GATEWAY_URL` points at `/api/gateway` and cannot serve. Reusing the one key would have grown the blast radius of every pod on the platform the day this shipped; short-lived exchanged tokens were rejected because a pod can always re-mint, so the window closed is small next to the issue/expiry/refresh machinery ADR-0056 already declined.
- **One door, two credentials.** `CallerSource` gains `'gateway-key'` and `PublicApiGuard` grows a second path: `Bearer gw-…` → key row → Project → `created_by` → that platform user → the permission set the platform last recorded for them. Controllers, the error envelope and the compatibility policy ([ADR-0035](0035-public-api-module-with-uri-versioning-and-additive-compat.md)) are untouched — ADR-0034 named "pod gateway key" as the anticipated second source. The Organization is the key's `tenant_id`, stamped at claim; no `x-tenant-name`. A parallel `/api/gateway/store` family was rejected: two implementations of create-a-Project would drift, and ticket 24 would document a loop no outside caller could reproduce.
- **`can_use_public_api` does not apply.** That permission governs which humans may point a program at the API from outside. Here the platform issued the credential, to a pod it started, running an Agent it ships, on a Project the human was already allowed to create. Requiring it would fail the Builder's test run for a user holding `can_manage_agents`, for a reason no message could sensibly explain. Every per-route permission still applies in full: a delete demands `can_delete_project` from the creator, read from what the platform last recorded for them.
- **Two refusals, both 401.** A key whose Project has `created_by` NULL — every Project existing before the migration — and a key whose `tenant_id` is NULL — an unclaimed pool slot, which `GatewayController` already refuses — are the two ways "there is no human behind this pod" arises, and neither has a safe fallback identity.
- **Routes opt in; the default is deny.** An `@AllowsGatewayCaller()` decorator on the handler, read by the guard, rather than a list in the guard that drifts from the routes it governs. Every future route, including the Skill Store's, is closed until someone deliberately opens it. The opening set is ticket 24's loop and nothing more: `GET /me`, `GET /agents`, `POST /projects`, `GET /projects`, `GET /projects/{id}`, `POST /projects/{id}/environments/{environmentId}/connect`, `DELETE /projects/{id}`. `GET /me` earns its place as how an agent truthfully reports which identity it is acting as.
- **Containment is which Projects, never what may be done to them.** `projects` gains `created_by_project_id` — the Project whose pod made this one, NULL for anything a human made directly — and a gateway caller's reads, connects and deletes are scoped to rows carrying its own Project id. A `DELETE` naming anything else answers 404, matching the API's standing rule that it never confirms a hidden Project exists. Within that set the pod has the creator's *full* authority, including the runtime: `POST …/connect` returns a `baseUrl` under `/api/proxy`, the proxy's ensure hop (`assertAgentSurfaceAccess`) learns to accept a `gw-` bearer and resolve it the same way before running the identical tenant-membership and visibility check, and runtime access is environment-level by [ADR-0034](0034-public-api-callers-are-idp-bearer-tokens-behind-a-caller.md)'s amendment — filesystem, shell, session mutation. A pod that can reach a child's runtime has shell in that child pod, and that is intended: verifying the child wrote `/workspace/app/startup.sh` and serves on `$APP_PORT` ([ADR-0061](0061-the-platform-harness-is-a-built-in-skill-and-an-agents-prompt-is-the-authors-body-alone.md)) is most of what a test run is for. Restricting the runtime to a prompt-and-read subset was rejected: it rebuilds the pinned facade [ADR-0033](0033-public-chat-api-is-a-pinned-subset-facade-over-the-primary-session.md) defined and [ADR-0038](0038-chat-is-native-opencode-through-the-runtime-proxy.md) retired, and blocks the verification that makes the loop worth running.
- **The capability is per Agent, default off.** `agents.json` declares it for Built-in Agents; `agent_settings` ([ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md)) carries it for Custom Agents, set by `can_manage_agents` like the Agent's other knobs. At launch exactly one Agent has it: the Builder. **What the flag defends against is untrusted content reaching a pod with no business calling the API** — an app-builder pod pastes scraped pages, inbound email and uploaded documents into its own context, and must not be convertible into a deputy. **It does not defend against a malicious author, and nothing at this layer can:** an author is an Organization member who already holds these powers under their own name, so a Custom Agent whose prompt calls the API as whoever launched it gains no privilege — it launders attribution and spends budget, both bounded by the ownership scoping above. Restricting the capability to Built-in Agents was considered and rejected: creating a test Project *is* the purpose this primitive exists for, and an approval gate is theatre when the approving permission is the authoring permission ([ADR-0057](0057-authored-skills-and-agents-are-private-or-public-within-one-organization.md)).
- **The chain stops at depth 2.** `created_by_project_id` is the chain, so the cap is one comparison against a named constant: a Project at depth 2 is created without a `platform-api` key. Depth 2 rather than 1 because it keeps testable the exact class of Agent this primitive serves — the Builder creating a test Project for an Agent whose own job is creating Projects — and it bounds a runaway loop at a handful of Projects. There is no rate limiting anywhere in the backend today, so this is the only structural stop; per-chat test counts and budget caps belong to the test-loop decision.
- **The client is a skill with `curl`.** `schedules`, `incoming-email` and `whatsapp` already ship as `SKILL.md` files invoking `curl` against `$SERVICE_GATEWAY_URL` with `$SERVICE_GATEWAY_API_KEY`; the platform-API skill matches them against `$OPSIFORCE_API_URL`. A baked CLI would be a second artifact to version against the API's own compatibility policy, and the token-in-transcript exposure it removes is already accepted for the three shipped skills; a CLI belongs to the separate CLI effort.
- **Provenance is columns, not a ledger.** `created_by` is stamped on *all* new Projects — generally useful, and ADR-0056 already wanted it — and with `created_by_project_id` every row answers who made it and whether a human or their agent did, durably and with no write path of its own. A call-level ledger (extending `gateway_audit_logs`, which records service dispatches) is a different feature serving rate-limiting and forensics, and is deferred until something needs it.
- **Standalone is the same path.** Gateway keys are Keycloak-free, and in `static` mode nginx injects fixed `X-Forwarded-*` headers resolving through the same `getOrCreateUser` ([ADR-0050](0050-local-development-runs-on-tilt-with-a-static-identity-and-no-identity-provider.md)), so the deployment has exactly one platform user and every Project's `created_by` is that user. The resolution hop is identical and needs no branch.

## Considered options

- **Reuse the single gateway key.** Rejected: `SERVICE_GATEWAY_API_KEY` is readable by the agent, by app code the agent writes, and by anything injected into either; ambient authority to act as a human in every pod is not a property to acquire by default.
- **Short-lived tokens exchanged per task.** Rejected: the pod can re-mint at will, so the exposure window barely narrows, while expiry and refresh across suspends is exactly what ADR-0056 declined.
- **A separate `/api/gateway/…` route family for pod callers.** Rejected above: drift, and a loop outside callers cannot reproduce.
- **Full creator authority with no ownership scoping.** Rejected: the permission set answers "may this human do this kind of thing", never "should this pod touch this row"; without scoping one injected prompt reaches `DELETE` on a production Project.
- **Ownership scoping by workspace or by Agent rather than by creating Project.** Rejected: both are coarser than the relation actually needed, and neither makes a test loop self-cleaning.
- **The capability restricted to Built-in Agents.** Rejected above.
- **Depth 1.** Rejected: same implementation cost, and it forecloses testing the one Agent shape most likely to need this API.

## Consequences

- `projects` gains `created_by` and `created_by_project_id`; `project_gateway_keys` gains `purpose`. Pre-migration Projects have NULL `created_by` and their pods cannot hold a platform-api key — acceptable, since the capability is off for every Agent but the Builder and Builder chats are created after the migration.
- `PublicApiGuard` gains a branch and `Caller.source` a second value; every existing consumer of `Caller` keeps working, and `Caller.user` is the creator, not a synthetic identity.
- The runtime proxy's ensure hop gains the same branch, so `/api/proxy` has two credential kinds and one authorization rule.
- The Agent picker and Project creation learn the capability flag so a `platform-api` key is minted only where declared.
- A pod's Projects are ordinary Projects: they appear in the creator's listings, count against Organization storage and budget, and are attributed to the creator with the creating Project recorded beside them.
- Glossary: **Gateway Key** gains a purpose; **Agent Caller** is the `Caller` whose source is a gateway key.
- A pod's permissions are the creator's as of their last forwarded request, not as of this call. The backend has no identity-provider admin client to ask — the standalone requirement above rules one out — so `users.groups` is written on every request oauth2-proxy forwards and read back for the gateway branch. A revocation therefore binds on the creator's next visit to the platform, not on their pod's next call.
- The docs page is `docs/public-api/api-token.md`, which already owns ADR-0034; the write is deferred with the rest of the Agent & Skill Platform pages.
