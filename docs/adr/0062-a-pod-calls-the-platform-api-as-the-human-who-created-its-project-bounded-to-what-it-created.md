# A pod calls the platform API as the human who created its Project, bounded to what it created

The Skill & Agent Builder authors Skills and Agents and tests them in real Projects, so its pod must call `/api/v1` on its own. A pod holds no user credential, because a user token in pod env would be readable by the model and would need refreshing across suspends.

**A pod authenticates to the platform API with a gateway key of its own purpose, resolves to the human who created its Project, and acts with that human's permissions, but only on Projects it created.**

- **A separate key for a separate authority.** `project_gateway_keys.purpose` is `service` or `platform-api`. The `service` key reaches the pod as `SERVICE_GATEWAY_API_KEY` and serves `/api/gateway` only ([ADR-0044](0044-apps-reach-non-llm-services-through-the-backend-owned-service-gateway.md)). A `platform-api` key is minted only for Projects whose Agent has the capability, and reaches the pod as `OPSIFORCE_API_KEY` beside `OPSIFORCE_API_URL` and `OPSIFORCE_RUNTIME_PROXY_URL`.
- **One door, two credentials.** `CallerSource` is `'idp-bearer' | 'gateway-key'`. `PublicApiGuard` takes a `Bearer gw-…` down its second path: key row, then its Project, then `created_by`, then that platform user and the permission set the platform last recorded for them. The Organization is the key's `tenant_id`, and the creator must still belong to it. Controllers, the error envelope and the compatibility policy ([ADR-0035](0035-public-api-module-with-uri-versioning-and-additive-compat.md)) are the same for both sources ([ADR-0034](0034-public-api-callers-are-idp-bearer-tokens-behind-a-caller.md)).
- **`can_use_public_api` does not apply; per-route permissions do.** That permission governs which humans may point a program at the API from outside, and here the platform issued the credential itself. Every route's own permission applies in full: authoring an Agent needs the creator's `can_manage_agents`, a delete needs their `can_delete_project`.
- **Two 401s.** A key whose Project has no `created_by`, and a key with no `tenant_id` (an unclaimed pool slot), are both "no human behind this pod", and neither has a safe fallback identity.
- **Routes opt in, and the default is deny.** A handler opens to a gateway caller with `@AllowsGatewayCaller()`, read by the guard. Any route without it answers `permission-denied` to a gateway caller, so a new route is closed until someone opens it on purpose. The opened groups are what the Builder's loop needs: `/me`, the Project routes, and the authoring routes for Skills and Agents.
- **Containment is which Projects, never what may be done to them.** `projects.created_by_project_id` records the Project whose pod made a Project, NULL when a human made it. A gateway caller's Project listings, reads, connects, restarts and deletes are scoped to rows carrying its own Project id, and any other Project answers 404, as the API never confirms a hidden Project exists. Within that set the pod has the creator's full authority, runtime included: the runtime proxy accepts the same `gw-` bearer, runs the creator's membership and visibility checks, and refuses a Project the calling Project did not create. A pod that reaches a child's runtime has shell in it, on purpose: checking the child inside its pod is most of what a test run is for.
- **The capability is per Agent, off by default.** `agents.json` declares `platformApi` for a Built-in Agent, and `agent_settings.platform_api` carries it for a Custom Agent, set by `can_manage_agents` ([ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md)). The flag stops untrusted content (scraped pages, inbound email, uploads) from turning a pod with no business calling the API into a deputy. It does not defend against a malicious author, and nothing at this layer can: an author already holds these powers under their own name, so such an Agent gains no privilege and only moves attribution and spends budget, both bounded by the scoping above.
- **The chain stops at depth 2.** A Project whose chain of `created_by_project_id` already reaches the limit is created without a `platform-api` key. Depth 2 keeps testable the Agent shape this serves most, the Builder testing an Agent whose own job is creating Projects, and bounds a runaway loop at a handful of Projects.
- **The client is `curl`.** The Builder's skills document the calls as `curl` against `$OPSIFORCE_API_URL`, and its workspace ships thin `curl` wrappers. A baked CLI would be a second artifact to version against the API's compatibility policy.
- **Provenance is columns, not a ledger.** `created_by` is stamped on every new Project; with `created_by_project_id` each row answers who made it and whether a human or their agent did.
- **Standalone takes the same path.** Gateway keys need no identity provider, and in `static` mode the one fixed identity is every Project's `created_by` ([ADR-0050](0050-local-development-runs-on-tilt-with-a-static-identity-and-no-identity-provider.md)).

## Considered options

- **Reuse the single `service` key.** Rejected: the agent, the App code it writes and anything injected into either can read it, so every pod on the platform would gain ambient authority to act as a human.
- **Short-lived tokens exchanged per task.** Rejected: the pod can re-mint at will, so the window barely narrows, at the cost of expiry and refresh across suspends.
- **A separate `/api/gateway/…` route family for pod callers.** Rejected: two implementations of create-a-Project would drift, and the pod's loop would be one no outside caller could reproduce.
- **Full creator authority with no ownership scoping.** Rejected: a permission set answers "may this human do this kind of thing", never "should this pod touch this row"; one injected prompt would reach `DELETE` on a production Project.
- **Scoping by workspace or by Agent rather than by creating Project.** Rejected: both are coarser than the relation needed, and neither makes a test loop clean up after itself.
- **Restricting the capability to Built-in Agents.** Rejected: an approval gate is theatre when the approving permission is the authoring permission ([ADR-0057](0057-authored-skills-and-agents-are-private-or-public-within-one-organization.md)).
- **Depth 1.** Rejected: the same cost, and it rules out testing the Agent shape most likely to need this API.

## Consequences

- A Project with no `created_by` cannot hold a working `platform-api` key.
- A pod's Projects are ordinary Projects: they appear in the creator's listings, count against the Organization's storage and budget, and are attributed to the creator.
- A pod's permissions are the creator's as of their last request through oauth2-proxy, which writes `users.groups` on every forwarded request; the backend has no identity-provider client to ask. A revocation binds on the creator's next visit to the platform, not on the pod's next call.
- The depth limit is the only structural stop on a runaway loop; the backend has no rate limiting.
