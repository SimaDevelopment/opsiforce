# A pod calls the platform API as the human who created its Project, bounded to what it created

The Skill & Agent Builder authors Skills and Agents and tests them in real Projects, so its pod must call `/api/v1` on its own. A pod holds no user credential, because a user token in pod env would be readable by the model and would need refreshing across suspends.

**A pod's call to the platform API resolves to the human who created its Project and acts with that human's permissions, but writes only what its own Project created.** The credential is the Gate's per-call token: a pod reaches `/api/v1` only as the `public-api` External Service ([ADR-0087](0087-the-public-api-is-a-built-in-external-service-and-pods-reach-it-only-through-the-gate.md)).

- **One door, two credentials.** `CallerSource` is `'idp-bearer' | 'call-token'`. `PublicApiGuard` takes a `Bearer gc-…` down its second path: the token's Project, then `created_by`, then that platform user and the permission set the platform last recorded for them. The Organization is the calling Project's, and the creator must still belong to it. A pod's own `gw-` key answers 401. Controllers, the error envelope and the compatibility policy ([ADR-0035](0035-public-api-module-with-uri-versioning-and-additive-compat.md)) are the same for both sources ([ADR-0034](0034-public-api-callers-are-idp-bearer-tokens-behind-a-caller.md)).
- **`can_use_public_api` does not apply; per-route permissions do.** That permission governs which humans may point a program at the API from outside, and here the platform issued the credential itself. Every route's own permission applies in full: authoring an Agent needs the creator's `can_manage_agents`, a delete needs their `can_delete_project`.
- **One 401.** A Project with no `created_by` is "no human behind this pod", and has no safe fallback identity.
- **Routes opt in, and the default is deny.** A handler opens to a pod with `@ExternalServiceOperation('<name>')`, which also makes it a `public-api` Operation. Any route without it answers `permission-denied` to a pod caller, so a new route is closed until someone opens it on purpose. The opened groups are what the Builder's loop needs: `/me`, the Project routes, and the authoring routes for Skills and Agents.
- **Containment is which rows, never what may be done to them.** `created_by_project_id` on `projects`, `skills` and `agents` records the Project whose pod made a row, NULL when a human made it. A pod's Project listings, reads, connects, restarts and deletes are scoped to rows carrying its own Project id, and any other Project answers 404, as the API never confirms a hidden Project exists. Skills and Agents are read creator-wide but written only when they are the calling builder chat's subject or carry its id. Within that set the pod has the creator's full authority, runtime included: the runtime proxy accepts the pod's `service` key, runs the creator's membership and visibility checks, and refuses a Project the calling Project did not create. A pod that reaches a child's runtime has shell in it, on purpose: checking the child inside its pod is most of what a test run is for.
- **Whether a pod may call at all is its Project configuration.** Each `public-api` Operation is a switch, reads on and writes off in a new Project configuration, and a builder chat's are written with the writes it needs when it is created. Switches stop untrusted content (scraped pages, inbound email, uploads) from turning a pod with no business calling the API into a deputy. They do not defend against a malicious author, and nothing at this layer can: an author already holds these powers under their own name, so such an Agent gains no privilege and only moves attribution and spends budget, both bounded by the scoping above.
- **The chain stops at depth 2.** A Project whose chain of `created_by_project_id` already reaches the limit cannot create a Project (`409 chain-too-deep`). Depth 2 keeps testable the Agent shape this serves most, the Builder testing an Agent whose own job is creating Projects, and bounds a runaway loop at a handful of Projects.
- **Provenance is columns, not a ledger.** `created_by` is stamped on every new Project; with `created_by_project_id` each row answers who made it and whether a human or their agent did.
- **Standalone takes the same path.** Call tokens need no identity provider, and in `static` mode the one fixed identity is every Project's `created_by` ([ADR-0050](0050-local-development-runs-on-tilt-with-a-static-identity-and-no-identity-provider.md)).

## Considered options

- **A pod user token in env.** Rejected: readable by the model and by the App it writes, and it needs refreshing across suspends.
- **A separate `/api/gateway/…` route family for pod callers.** Rejected: two implementations of create-a-Project would drift, and the pod's loop would be one no outside caller could reproduce.
- **Full creator authority with no ownership scoping.** Rejected: a permission set answers "may this human do this kind of thing", never "should this pod touch this row"; one injected prompt would reach `DELETE` on a production Project, or publish a version of a Skill the chat was never about.
- **Scoping by workspace or by Agent rather than by creating Project.** Rejected: both are coarser than the relation needed, and neither makes a test loop clean up after itself.
- **Depth 1.** Rejected: the same cost, and it rules out testing the Agent shape most likely to need this API.

## Consequences

- A Project with no `created_by` cannot call the platform API.
- A pod's Projects are ordinary Projects: they appear in the creator's listings, count against the Organization's storage and budget, and are attributed to the creator.
- A pod's permissions are the creator's as of their last request through oauth2-proxy, which writes `users.groups` on every forwarded request; the backend has no identity-provider client to ask. A revocation binds on the creator's next visit to the platform, not on the pod's next call.
- The depth limit is the only structural stop on a runaway loop; the backend has no rate limiting.
