# An Agent's service settings seed a real Project configuration in every new Project

An Agent built for one job (a PR reviewer, an app builder that commits to one repository folder) needs the same service settings in every Project created from it: the repository and folder it works in, pull requests allowed, merging off. A new Project configuration starts from the Project form's defaults, and nothing else is set until a person opens the service in each Project and saves it.

**An Agent carries Service settings (Agent) for each Service skill on its Agent Profile: values for the service's Project-form fields, targets included, never a secret or a generated value. When a Project of the Agent comes to exist, the platform writes a real Project configuration from them over the form's defaults, as if a person had saved it, runs the service's save hook as the platform when the configuration is complete, and delivers the Service skill.** Concretely:

- **Everything but what is each Project's own.** A `secret`, a `generate`d field and a `list` holding one are left out: a shared secret or one generated value in every Project would make Projects indistinguishable to the service. Everything else may be set, including targets — a field whose options come from a call to the service (repositories, boards) or from the Service configuration (a mailbox). The Agent page renders the Project form without the left-out fields; a call-sourced field lists its options live by asking the service **with no Project** (a Project-form `options` call whose Caller identity names no ProjectEnvironment, so `ctx.projectConfiguration` is `null`), which SDK 2.2 added; an older service refuses it and the dialog says to upgrade its SDK. The picked options' labels are stored beside the values (`_labels`) and copied into the Project, so the Project shows names, not ids. A configuration whose required target the settings leave unset "Needs attention", runs no save hook, and the service refuses its calls until someone picks it in the Project; that save runs the hook.
- **Built-in Agents per Organization.** A Built-in Agent's Profile in one Organization holds the Skills that Organization added ([ADR-0051](0051-skills-are-stored-as-immutable-per-file-versions-and-a-built-in-agents-skills-live-on-a-development-profile.md)); its Service settings live on those pins and reach only that Organization's new Projects of the Agent.
- **A snapshot at creation.** Later changes to the settings never reach existing Projects. A field the service adds later takes its default in new Projects until the settings set it, and a field the service no longer declares, or no longer lets an Agent set, is ignored with its label.
- **Every way a Project of the Agent comes to exist:** create (UI, Public API, Workspace), the Agent's Test Project, Project Duplicate and Project Import. The configuration is written before the Agent's files are delivered and the hook runs after, so the two deliveries never race; a Project Duplicate or Import delivers its Service skills before the hook too; a hook failure leaves the usual "Saved, but …" Retry and the Project is still created. Each list item gets its own id in each Project.
- **Only a person sets them.** Setting any Service settings, and listing a field's options for them (from the service or from the Service configuration), needs `can_configure_project_external_services` as well as the Agent permission, checked when the Agent is edited and when Agent Duplicate or Import writes a copy; creating a Project checks nothing again. The platform cannot tell which field widens what a Project may do, so it guards all of them. A Duplicate or Import by someone without that permission drops the copy's Service settings, saying so. The Skill & Agent Builder cannot read or set them through the Public API.
- **Settings travel with the Skill pin:** a Custom Agent's live on the Development profile, move to Production with the Agent's Publish, and Agent Duplicate carries them whole. Agent Export carries only the settings that are not targets, because a repository, a board or a Service-configuration item names something in the exporting Organization alone, and reads which are targets from the Organization's copy of the service even when it is not Available; Import keeps the field keys the importing Organization's service declares and drops the service when it is not Available there, saying so in its notes.

## Considered options

- **Prefill only.** The dialog opens with the Agent's values but nothing is stored until a person saves in each Project. Rejected: every Project still needs a person, which is what the settings remove.
- **Live inheritance.** Projects read the Agent's settings at call time. Rejected: the service would merge two documents on every call, and every Agent edit would fan out a save hook to every Project.
- **Answering option lists as some Project of the Organization.** Rejected: the service would see a caller that is not asking, and a Built-in Agent may have no Project to borrow.

## Consequences

- A Project configuration can exist from the first message with capabilities on and targets picked that no person saved in that Project, and no record names who seeded it: the seeding hook reaches the service as the platform acting for that ProjectEnvironment, never as a person.
- A service's `options` handler must answer with no Project configuration; one written for a Project only (reading `ctx.projectConfiguration` unguarded) fails on the Agent page until its author fixes it.
- Services built on SDK 2.0 or 2.1 cannot list call-sourced options on the Agent page until their builder upgrades the SDK; their other settings work.
