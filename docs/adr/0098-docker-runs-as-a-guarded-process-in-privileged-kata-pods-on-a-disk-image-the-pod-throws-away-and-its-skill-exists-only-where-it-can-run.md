# Docker runs as a guarded process in privileged Kata pods, on a disk image the pod throws away, and its skill exists only where it can run

Much of what an [App](../../GLOSSARY.md) runs ships as Docker images, a Dockerfile or a compose file: the App itself, a service it uses, or a whole product. Agents reach for Docker to run it the way it ships. On a deployment that turns `agentPrivileged` on, which the backend allows only with the `kata-clh-runtime-rs-opsiforce` RuntimeClass, every agent pod is its own virtual machine and privileged means root inside that VM, not on the node. The agent image is the same on every deployment, and every folder the VM receives from the node arrives through virtio-fs, which accepts no extended attributes and no whiteout device files: the pod's own filesystem, a disk-backed `emptyDir` and `/workspace` alike.

**On a deployment with privileged agent pods, the agent container runs `dockerd` as one more `guard`ed process, and Docker keeps its storage on an ext4 filesystem the container builds inside the VM from a sparse file on a pod-local `emptyDir`, thrown away with the pod. A container's durable data is a bind mount under `app/data/`. The `docker` [Built-in Skill](../../GLOSSARY.md) is offered only on such a deployment; everywhere else it is retired exactly like a Built-in Skill that left the image.** Concretely:

- **The daemon is a supervised process, not a container of the pod.** The backend sets `OPSIFORCE_DOCKER=1` on the agent container of every privileged pod, and `entrypoint.sh` then runs `guard docker dockerd …` beside code-server and opencode ([ADR-0009](0009-in-pod-control-process.md)). Its log is `data/logs/docker.log`, read with `process-logs docker`, and every process in the container reaches it at `/var/run/docker.sock`.
- **Docker's storage is built inside the VM at every pod start.** The guest kernel has the loop driver but the container's `/dev` has no loop device nodes, so entrypoint creates them with `mknod`, makes a sparse 20 GiB file on an `emptyDir` with a 21 GiB size limit, formats it ext4, mounts it at `/var/lib/docker` with `discard`, and only then starts the daemon. A container restart inside the same pod checks and reuses the file; a file that will not mount is made again, since it only holds what can be pulled or built again. Every new pod, including one woken from idle suspension, starts with no images. When the storage cannot be prepared, the reason is in the `docker` log and the rest of the pod starts without Docker.
- **The agent image ships Docker Engine, Compose, Buildx and `iptables`** on every deployment; only those with privileged pods run them.
- **Durable data stays inside the `data/` deploy boundary.** Data a container must keep is bind-mounted from `/workspace/app/data/<name>/`, so git ignores it, Publish never carries it, and Duplicate and Export do ([ADR-0004](0004-git-based-incremental-publish.md)). Docker volumes hold only what may be lost.
- **Containers run in the foreground under `guard` from `startup.sh`,** one `guard` per `docker run` or per `docker compose up`, so their output is a process log and restarting the App stops them. A container the App depends on publishes its port on `127.0.0.1`; an App that is itself a container publishes `$APP_PORT` on all addresses.
- **Availability follows the deployment, through retirement.** Where agent pods are not privileged, the backend leaves `docker` out of the Built-in Skills it reconciles and out of every package's skill list, and tells the image script not to lay it, at first boot and in Agent Updates. It is then hidden from the [Skill Store](../../GLOSSARY.md), refused as a pin, absent from the Switch off list, and removed from any workspace that holds it, and it comes back when the deployment turns privileged pods on ([ADR-0051](0051-skills-are-stored-as-immutable-per-file-versions-and-a-built-in-agents-skills-live-on-a-development-profile.md)). The list of such Skills is `privilegedOnlySkills` in `agent-config/package-skills.json`, and one backend provider decides from it and `agentPrivileged` what this deployment offers.
- **Where it is offered, the Built-in Agents that build Apps carry it, and a Custom Agent carries it only by pinning it.** The Platform Skill does not mention Docker.

We chose a supervised process because a separate `docker:dind` container would keep the daemon's log in `kubectl logs`, where the agent cannot see why Docker failed, and would need `/workspace` mounted at the same path in both containers, or `-v /workspace/…` silently binds an empty folder of the other container. We build the filesystem inside the VM because Docker cannot use virtio-fs at all: overlay2 stops with `failed to mount overlay: invalid argument`, and even the copying `vfs` driver fails when it creates a container. The file sits on the pod's own disk because, written through virtio-fs to CephFS, it loses its sparseness: on dev it occupied 20 GB from the first format, took 29 s to format instead of under one, and pulled images twice as slowly, while the pod-local file held about 600 MB after pulling `postgres:17`. Availability goes through retirement because a skill's name and description sit in every agent's skill list: a skill that checks for Docker itself would still offer Docker where it cannot run, and retirement already hides, refuses and removes a Built-in Skill that workspaces must not use.

## Considered options

- **A `docker:dind` container beside the agent container.** Rejected: the log and path problems above.
- **Docker's storage in RAM,** a memory-backed `emptyDir`, the one setup that works without loop devices. Rejected: it spends the VM's memory, about 4 GB on the default pod class, where `postgres:17` alone took about 460 MB.
- **The disk image under `/workspace/.cache`,** so images survive a wake. Rejected: the CephFS cost above, which the Storage page shows and the claim's quota counts.
- **fuse-overlayfs.** Rejected: the container has no `/dev/fuse`, and it is a slower userspace copy of the kernel's overlay, which works on the ext4 file.
- **A Ceph block volume per environment,** so images survive wakes. Not built: it needs a volume lifecycle per environment, and whether Kata attaches a raw block volume to the VM is unverified on runtime-rs, while pulling again costs seconds per image on dev.
- **A pull-through registry cache in the cluster.** Not built: it saves only the download, covers only Docker Hub, and dev stays far under the anonymous pull limit.
- **A separate `agentDocker` setting.** Rejected: it is legal only together with `agentPrivileged`, and nobody needs privileged pods without Docker.
- **A skill shipped everywhere that checks for Docker itself.** Rejected: the reason above.

## Consequences

- Every pod start pulls the App's images again, `postgres:17` in 14 s and `node:24` in 52 s on dev, and rebuilds any image the App builds itself.
- Every pull counts against Docker Hub's anonymous limit for the cluster's one outgoing address, 100 an hour on dev. Once it runs out, containers fail to start in every Project until the window resets.
- Data a container keeps on `/workspace` waits on CephFS for every commit: Postgres managed 175 transactions a second there against 5,047 with its data in RAM, the same storage SQLite Apps already write to.
- Export carries empty folders and folder permissions, because a Postgres data folder that lost its empty folders refuses to start. Duplicate and Export copy a running database with the torn-write risk SQLite already carries ([ADR-0011](0011-duplication-reuses-git-publish-path.md)).
- Containers share the pod's CPU and memory with the agent and the App.
- Turning privileged pods on or off on an existing deployment reaches existing workspaces' skills at the next backend start, with no Agent version bump: the Agent Updates sweep finds any workspace whose owned skills do not match what the deployment offers. Existing pods keep their runtime until they are recreated.
- Agent images on deployments without privileged pods carry Docker's binaries unused.
