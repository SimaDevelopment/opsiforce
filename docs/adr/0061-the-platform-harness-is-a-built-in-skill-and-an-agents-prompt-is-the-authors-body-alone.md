# The platform harness is a built-in skill, and an agent's prompt is the author's body alone

Every agent that runs in an Opsiforce pod depends on the same platform facts — the preview port, the go-live file, where uploads and generated files live, the gateway env vars, the two read-only databases, what must never be installed. Today those facts exist only as prose inside `agent-config/agents/app-builder/agent.md`, interleaved with 200 lines of Vite/NestJS/shadcn guidance; the Makara variant differs in twelve hunks, all of them template stack. A Custom Agent ([ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md)) has an author-written `prompt_body`, no template and no migrations ([ADR-0060](0060-agent-files-are-laid-once-and-shared-with-the-backend-by-ownership-list.md)), and must still know all of it — and opencode builds the system prompt from exactly one file per agent, `/workspace/.opencode/agents/<slug>.md`, which *replaces* its default prompt; `AGENTS.md` and `instructions` reach the model as synthetic messages, not system text. The obvious answer — compose harness text into the author's file at project create — collides with ADR-0058's rule that a Custom Agent's content is written once and never re-derived: a wrong port or a retired env var would be frozen into every existing Project.

**The harness is a built-in skill named `platform`, shipped in the agent image and laid into every workspace; an agent's prompt file carries only what its author wrote; the App contract is three files and a port, satisfied by the template today and by a Custom Agent's own work tomorrow.** Concretely:

- **Two layers, no composition.** The system prompt of any agent is its own markdown body — App Builder's `agent.md` from the image, a Custom Agent's `prompt_body` from its Development or published profile — with `model`, `variant` and `mode` in the frontmatter. Nothing is prepended, appended or templated in. There is no base-persona layer: a Custom Agent does not inherit App Builder's text, and the Builder does not suggest it as a starting point; the prompt is whatever the authoring chat decided. `prompt_body` in ADR-0058 means the whole file body.
- **`platform` is a skill, not prompt text.** It lives at `agent-config/skills/platform/` and `compose-skills.mjs` already copies the shared skills into every package at image build, including the `custom` package ADR-0060 introduces. It is image-owned, so the Agent-Updates `content` Job rewrites it in every existing Project — Custom Agent Projects included, because the Job skips only skill names the backend wrote — and a harness fix is an image bump with no pod restart. It is self-contained: it names `$APP_PORT`, `app/app.meta.json`, `app/startup.sh`, `/workspace/user_uploaded_files/`, `/workspace/generated_files/` and the `/workspace/…` download-link form, `app/opsiforce.env.json` and what Publish does with it, the five platform env vars plus `OPSIFORCE_ENV`, the OpenAI-compatible gateway at `APP_LLM_BASE_URL` and the ban on local models, the read-only `/workspace/data/database.db` and `/workspace/data/external-services.db`, that `websearch` is available, and that one Project is one App. It never says "see `llm-api`", because that skill may not be present; it closes with the capabilities the platform offers through built-in skills an author can add (AI gateway recipes, inbound email, WhatsApp intake, schedules, browser testing, document generation), so an agent asked "can this receive email?" answers correctly. Its description names the port and the go-live file outright, because the description is the only part of a skill the model sees without loading it.
- **Built-in skill names are reserved.** Creating a Skill named `platform`, or any other name the image ships, is refused at creation ([ADR-0059](0059-skills-exist-only-as-published-versions-and-a-built-in-agents-skills-live-on-a-development-profile.md) already refuses collisions at add time), so the collision rules in ADR-0060 never fire for it and no author can remove or shadow it.
- **A Custom Agent starts with `platform` and nothing else.** Every other skill — `llm-api`, `sqlite`, `agent-browser`, `document-generation`, a Store skill — is added on purpose through the Agent's skill list, and Built-in Skills are Store rows, so it is the same act. The Builder knows the built-in catalogue and, when an author describes a capability a built-in covers, offers **reuse** (add it), **extend** (Duplicate it into a private Skill under a new name), or write fresh; Duplicate works from a built-in row.
- **The App contract is `startup.sh`, `$APP_PORT`, `app.meta.json`.** The platform runs an App through four hard-coded points that live in platform code, not the template: `entrypoint.sh` runs `guard webapp /workspace/app/startup.sh`; the proxy routes the preview to `APP_PORT`; `agent-control` probes that port and pushes readiness ([ADR-0015](0015-app-liveness-pushed-not-polled.md)); Publish git-syncs the workspace, recreates the pod and waits for that push. A Custom Agent therefore does not "start its own server": it writes an executable `/workspace/app/startup.sh`, and the platform runs it, restarts it, and re-runs it in the published environment with `OPSIFORCE_ENV=production`. The guard **waits for the file instead of crashing** — `sh -c 'while [ ! -x /workspace/app/startup.sh ]; do sleep 2; done; exec /workspace/app/startup.sh'`, the idiom `startup.sh` itself uses for `.pnp.cjs` — so a workspace without an App idles quietly; today the missing file yields fifty crash restarts over forty-five minutes, then `wait -n` exits the container.
- **Readiness no longer depends on a route.** `agent-control` reads `name` and `description` from `app.meta.json` itself — it already watches the file — and treats *any* HTTP response on `$APP_PORT` as serving; live is serving plus the file existing. `GET /api/app-meta` was built for the template's own tab title ([ADR-0010](0010-app-identity-read-at-runtime.md)) and became the probe only because the old poll loop happened to hit it; it stays in the App Builder template as a private convenience and leaves the platform contract.
- **The port has one source.** `agents.json` already declares `"port": 3000` and nothing reads it; the pod template hard-codes `containerPort: 3000`, `entrypoint.sh` defaults `APP_PORT`, and the backend has its own `appPort`. The registry field becomes the source: the pod template sets `containerPort` and the `APP_PORT` env from it, and the skill tells the agent to read `$APP_PORT`. `app.meta.json` stays `{name, description}` — an agent-written file must not choose the port the platform routes to.
- **Three rules are enforced, the rest is guidance.** `agent-config/opencode.json` keeps its allow-all and adds `deny` rules for writes under `.opencode/**` and `.opsiforce/**` and for writes to `/workspace/data/database.db`; opencode's permission engine blocks a denied call (`BlockedError`) rather than advising against it, and the config rides the image by ADR-0060's allow-list rebuild. Everything else in the harness — never restart the template's dev servers, no landing pages, mobile-first — stays prose, because it is advice about how to build, not a boundary the platform depends on.
- **App Builder loses its copy.** The platform sections leave `agent.md` and App Builder loads `platform` like any other agent; what remains is the persona, the direct-task-versus-app decision, the communication rules, and everything the template makes true — dev servers already running, `yarn add` and PnP, the config-loader snippet, the eight build steps, project structure, the skills table, the ten Rules, verification and the browser flow. "No local models" and "no email" are stated in both on purpose, as behavioural rules App Builder repeats. If App Builder starts forgetting to load the skill, the remedy is a one-line "load `platform` first" in its own prompt, never a second copy of the facts.
- **The Builder's `agent-authoring` skill carries two rules** for [ADR-0056](0056-builder-chats-are-hidden-projects-with-writes-resolved-to-the-launching-user.md): never restate anything `platform` covers, and when the child is meant to build or serve something, write "load the `platform` skill before serving anything" into its prompt, because a model does not always load a skill unprompted; the Builder's test run is what catches a child that skipped it.

## Considered options

- **Compose harness → base persona → custom persona into the one rendered `.md`** — the field's default and the shape the research recommended; rejected because opencode replaces the system prompt with that file, so for a Custom Agent the harness would be frozen with the persona by ADR-0058 and a fix would never reach existing Projects.
- **Harness in a workspace `AGENTS.md`** — injected as a synthetic user-turn message, not system text; the weakest channel the runtime has.
- **Harness injected by an image-shipped opencode plugin (`session.hook("context")`)** — updatable everywhere, but a runtime component on opencode's request path that the platform would own, and the prompt on disk would no longer show what the model sees. The skill channel gives the same update property with machinery ADR-0060 already builds.
- **Markers in the `.md` and a Job that re-splices the harness block** — workable, but a second write path into the author's file and a written exception to ADR-0058 for one block.
- **Custom Agents inherit App Builder's prompt underneath their own** — rejected: the stack is the prompt's business entirely, and a Custom Agent with no template has nothing App Builder's rules describe.
- **A stub `startup.sh` shipped in the `custom` package** — the wait loop moved into a platform file the agent must overwrite, contradicting "no template" in ADR-0060.
- **A declared start command in `app.meta.json`** — `startup.sh` already is a declared start command.
- **Keep `GET /api/app-meta` as a platform rule every App must implement** — a NestJS convention imposed on every stack, and the most likely reason a Custom Agent's App would never show its preview. **A declared health path in `app.meta.json`** stays available as an additive fix if the generalised probe ever declares an App ready before its backend finishes booting.
- **A machine-readable manifest the prompt is rendered from** — nobody in the field renders a whole contract from data; the one variable worth sharing is the port, and the registry already holds it.
- **`platform` + `agent-browser` as the Custom Agent default** — the browser binary is in the pod, but the skill is added like any other and the Builder's test run shows whether it was needed.

## Consequences

- **Corrected on 2026-09-22.** Until agent image 0.20.0 the build composed the *whole* shared pool into the `custom` package, so every Custom Agent Project carried all shared built-in Skills on disk and pinning one changed nothing at runtime. `compose-skills.mjs` now lays only `platform` into `custom`; every other Skill, built-in or authored, reaches a Custom Agent's workspace as a pinned Skill written by the backend from its Store row. A Custom Agent workspace created before that image loses the image-owned copies on its next content sweep and keeps only what was pinned.

- **ADR-0058 stands**; `prompt_body` is confirmed as the whole file body and no exception to "never re-derived" is needed, because nothing platform-owned is ever written into that file. **ADR-0060 is amended**, not superseded: the `custom` package ships the `platform` skill (as every package does), the init step for a Custom Agent creates an empty `/workspace/app` and `git init`s the workspace so Publish has a repository to sync, and `entrypoint.sh` waits for `startup.sh`. **ADR-0015 stands** with a narrower probe; **ADR-0010 stands** as a template decision. **ADR-0059's** name reservation extends to image-shipped skill names. **ADR-0056** receives the two `agent-authoring` rules above.
- The agent image changes in one bump: the `platform` skill, the slimmed `agent.md` for both packages, the three `deny` rules, the entrypoint wait, and `reporter.go` reading `app.meta.json` and probing without a route — the last two need `requiresPodRecreate`. The backend changes: `pod.template.ts` reads the port from the registry, Skill creation refuses reserved names, Duplicate accepts a built-in source, and the Builder's catalogue is the built-in Skill rows it already has.
- A harness fix is an image bump followed by the `content` sweep; existing Projects of every agent kind receive it without a restart. Only reasons to recreate a pod remain the binaries — `agent-control`, the entrypoint.
- A Custom Agent's App is publishable the day it is built: the production pod runs its `startup.sh` under `OPSIFORCE_ENV=production` exactly as it runs App Builder's, and readiness fires as soon as anything answers on `$APP_PORT`. For App Builder's template that "anything" may be Vite before NestJS has finished booting, so Publish may report ready a few seconds early and a backend-only crash is no longer visible as *serving down*; accepted, with the health-path field as the recorded remedy.
- The model sees the harness only after loading the skill. The description carries the two facts that must survive a model that never loads it — the port and the go-live file — and the Builder's rule to instruct children to load it exists for the same reason.
- **Glossary**: **Platform Skill** and **App contract** enter `CONTEXT.md`; **Harness** is not a term — the thing is a skill.
- This ADR has no home page under `docs/` yet; the feature is unbuilt, and the page is owned by the map's PRD ticket, as for ADR-0060.
