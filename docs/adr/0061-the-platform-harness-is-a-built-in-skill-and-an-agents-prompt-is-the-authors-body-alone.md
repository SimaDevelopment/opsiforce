# The platform harness is a built-in skill, and an agent's prompt is the author's body alone

Every agent in an Opsiforce pod needs the same platform facts: the port, the go-live file, where files live, the gateway, the read-only databases, what never to install. opencode builds an agent's system prompt from exactly one file, `.opencode/agents/<slug>.md`, which replaces its default prompt, and a Custom Agent's file is written once at create and never re-derived ([ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md)). Composing platform text into that file would put a copy of it inside every author's prompt, frozen there.

**The platform facts live in a built-in skill named `platform` that ships in every package. An agent's prompt file carries only what its author wrote. The App contract is `startup.sh`, `$APP_PORT` and `app.meta.json`, which any stack can satisfy.**

- **Two layers, no composition.** An agent's system prompt is its own markdown body — App Builder's `agent.md`, or a Custom Agent's `prompt_body` — with `model`, `variant` and `mode` in the frontmatter. Nothing is prepended, appended or templated in. There is no base persona: a Custom Agent does not inherit App Builder's text. `prompt_body` is the whole body.
- **`platform` is a skill, not prompt text.** It lives at `agent-config/skills/platform/`, and `compose-skills.mjs` copies it into every package, `custom` included. It covers the App contract, the upload and generated-file folders and the download-link form, `app/opsiforce.env.json` and what Publish does with it, the platform environment variables, the gateway at `APP_LLM_BASE_URL` and the ban on local models, the two read-only databases, web search, and that one Project is one App. It never points at a skill that may be absent, and it closes with what the platform offers through built-in skills an author can add. Its description names the port and the go-live file, because the description is all a model sees before loading the skill.
- **Who refreshes `platform`.** On a Built-in Agent's Project the image owns it, so the Agent-Updates `content` Job rewrites it with no pod restart. A Custom Agent pins `platform` like its other Skills: the backend writes the pinned Version at create, and the image's copy yields to it under ADR-0060's collision rule. `platform` cannot be removed from an Agent's Skills.
- **Built-in skill names are reserved.** Creating a Skill with any name the image ships is refused, so no author can shadow `platform`.
- **A Custom Agent made with New agent starts with `platform` and nothing else.** Every other Skill is added on purpose; a Duplicate starts with its source's Skills. Built-in Skills are Store rows, so adding `sqlite` is the same act as adding an authored Skill. The Builder checks the built-in catalogue first and offers reuse (add it), extend (Duplicate it into a private Skill under a new name; Duplicate works from a built-in row), or a fresh Skill. A Custom Agent whose Template is a snapshot of the web-app starter gets `web-app` and the stack skills `web-app` lists, and no other Agent gets `web-app`.
- **The App contract.** `entrypoint.sh` runs `guard webapp` on `/workspace/app/startup.sh`; the proxy routes the preview to `$APP_PORT`; `agent-control` probes that port and pushes readiness ([ADR-0015](0015-app-liveness-pushed-not-polled.md)); Publish syncs the workspace through git, recreates the pod and waits for that push. An agent writes an executable `startup.sh`, and the platform runs it, restarts it, and re-runs it in a published environment with `OPSIFORCE_ENV=production`. The `webapp` guard waits for an executable `startup.sh` instead of crashing, so a workspace without an App idles quietly.
- **Readiness needs no route.** `agent-control` treats any HTTP response on `$APP_PORT` as serving, and reads `name` and `description` from `app.meta.json` itself. Live is serving plus the file. `GET /api/app-meta` is the starter's own convenience ([ADR-0010](0010-app-identity-read-at-runtime.md)), not part of the contract.
- **One port source.** The registry's `port` in `agents.json` sets the pod's `containerPort` and `APP_PORT`, and the backend reads its `appPort` from it too. `platform` tells the agent to read `$APP_PORT`. `app.meta.json` holds `{name, description}` only, so an agent-written file never chooses the port the platform routes to.
- **Three rules are enforced; the rest is guidance.** `agent-config/opencode.json` allows everything and denies edits under `.opencode/**` and `.opsiforce/**` and to `data/database.db`. opencode's permission engine blocks a denied call. Everything else in `platform` is prose, because it is advice about how to build, not a boundary the platform depends on.
- **The workspace is durable and the pod is not.** `platform` states, for any stack, what a pod recreate wipes and what `/workspace` keeps; that `startup.sh` is the one repeatable recipe, with dependencies ensured idempotently, state under `app/data/`, and every long-running process under `guard` in the foreground; and that Publish carries no `data/`. It names no particular service. The Builder's restart check in a Test Project ([ADR-0063](0063-the-builder-tests-a-child-agent-by-conversing-with-it-in-one-throwaway-project.md)) is what proves a child honoured it.
- **Observability is in `platform`.** The tables of `/workspace/data/database.db` (`app_requests`, `process_logs`, `process_events`) and the ready-to-run boot, failure and crash queries are true of any stack, so they live in `platform`. `app.db` modelling and migrations stay in the `sqlite` stack skill. An agent told the database exists but not how to read it opens a browser on a crashed App and reports a UI bug, and the Builder grades what a child reports.
- **`web-app` holds the starter's know-how.** The running dev servers, adding packages, the build order, the structure, the starter's rules and how to verify an App are the shared built-in skill `web-app`. App Builder's prompt says "Load the `web-app` skill before touching the app" and keeps the persona, the direct-task-versus-app decision, the communication rules and its behavioural rules. One text serves App Builder and every Custom Agent on the starter, and it updates like any skill.
- **`web-app` expects the starter already laid.** App Builder's Projects get the starter on first boot from their package template. A Custom Agent's Project gets it only through its Template, a snapshot the Builder copied and edited ([ADR-0073](0073-a-custom-agents-template-is-a-folder-per-environment-copied-into-every-new-project.md)). `web-app` never lays it: it checks that `app/` holds the starter and, when it does not, stops and tells the user what it found.
- **A building Agent's body keeps rules, and the Template holds the result.** The Builder gives every Agent that runs an App a short Architecture section of three to six rules every Project keeps as it grows: what may never be added a second of, where new parts go, what every App of the Agent shares. They are rules to keep, never changes to apply. The body is the one text every Project reads, frozen at create. `web-app` says which parts of the starter are plumbing, which are the normal work, and which change only on a decision. Know-how longer than a few lines is a Skill the body names.
- **Another stack is a skeleton in the Template, and a stack Skill carries know-how.** When the starter cannot fit, the Builder writes the skeleton into the Template and runs it before saving. Every stack Skill the Builder writes carries decisions and contracts — libraries by name with no version pins, formats and routes, a style guide, what `startup.sh` runs, anti-patterns, a paced definition of done — and never files for the child to copy. Its `scripts/` are tools the agent runs, such as an optional read-only checker, never code the App ships.
- **Makara composes without `web-app`.** `agent-config/package-skills.json` excludes `web-app` and `dates` from the Makara package, which keeps its whole prompt. `compose-skills.mjs` and the backend both read it, so the Store never lists either on Makara, and an Organization pin on either is delivered like any other Organization Skill.
- **`agent-authoring` carries two rules.** The Builder never restates anything `platform` covers. When a child builds, serves or delivers anything, its body says "Load the `platform` skill before you build, serve or deliver anything, and check your work the way it and `## Done looks like` say before you call it done", and what finished means for that Agent goes in its `## Done looks like`. A model does not always load a skill unprompted, and the Builder's test run catches a child that skipped it.

## Considered options

- **Compose harness, base persona and custom persona into the one `.md`** — the field's default. Rejected: the author's prompt would carry platform text it did not write, frozen at create, where a separate skill keeps one source.
- **The harness in a workspace `AGENTS.md`** — it reaches the model as a synthetic user-turn message, not system text, the weakest channel the runtime has.
- **An image-shipped opencode plugin (`session.hook("context")`)** — a runtime component on opencode's request path that the platform would own, and the prompt on disk would not show what the model sees.
- **Markers in the `.md` and a Job that re-splices the harness block** — a second write path into the author's file.
- **Custom Agents inherit App Builder's prompt underneath their own** — the stack is the prompt's business, and an Agent off the starter has nothing App Builder's rules describe.
- **A stub `startup.sh` in the `custom` package** — a platform file the agent must overwrite, when the guard's wait already covers a missing App.
- **A start command declared in `app.meta.json`** — `startup.sh` already is a declared start command.
- **A health route every App must implement** — imposes one stack's convention on every App, and is the likeliest reason a Custom Agent's preview would never appear. A declared health path in `app.meta.json` stays available if the probe ever declares an App ready too early.
- **A machine-readable manifest the prompt is rendered from** — the one value worth sharing is the port, and the registry already holds it.
- **`platform` plus `agent-browser` as every Custom Agent's default** — the skill is added like any other, and the Builder's test run shows whether it is needed.
- **A Skill per changed layer, loaded after `web-app`, as the default** — a one-line decision (a different database, an extra worker) is made once in the Template, and the Architecture section keeps it.
- **A per-Project decisions file (`app/AGENTS.md`)** — the architecture is decided once per Agent, and the body already reaches every Project unchanged.
- **Keeping App Builder's prompt whole and copying its stack text into `web-app`** — two copies drift.

## Consequences

- A harness fix is an image bump. Built-in Agent Projects receive it through the `content` sweep with no restart. A Custom Agent Project keeps the `platform` Version pinned when it was created, and a Custom Agent's new Projects get the fix once its pin is upgraded. Only the binaries — `agent-control`, the entrypoint — need a pod recreate.
- A Custom Agent's App is publishable once it is built: the production pod runs its `startup.sh` under `OPSIFORCE_ENV=production`, and readiness fires as soon as anything answers on `$APP_PORT`. On the starter that may be Vite before NestJS finishes booting, so Publish may report ready a few seconds early, and a backend-only crash does not show as serving down.
- The model sees the platform facts only after loading `platform`. Its description carries the port and the go-live file for a model that never loads it. If App Builder stops loading `platform` or `web-app`, the remedy is the one-line load in its prompt, never a second copy of the text.
- A Custom Agent on the starter runs the snapshot its Template holds. Later changes to App Builder's starter reach it only when its author asks the Builder to merge them in, and a `web-app` Version that has moved past the snapshot is re-pinned in the same step.
