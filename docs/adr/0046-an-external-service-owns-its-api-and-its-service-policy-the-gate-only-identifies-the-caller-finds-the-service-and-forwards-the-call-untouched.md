# An External Service owns its API and its Service policy; the Gate only identifies the caller, finds the service and forwards the call untouched

An External Service speaks to an outside system with that system's credentials on behalf of a Project's Agent or App. The clients that do that work are git, gh, kubectl, vendor CLIs and SDKs, which speak the outside system's own API: Git Smart HTTP, GitHub's REST and GraphQL paths, Kubernetes watches and streamed logs. The rules that matter are written in those requests' paths, bodies and protocol streams: which repository, whether a push targets the default branch, whether every commit carries the Project's co-author. A platform that admits calls by a named Operation with a JSON input can neither carry those clients nor judge those rules, and a service built behind it had to escape through its App's public host to work at all.

**The platform lets a call through or refuses it only on who is calling and which service is addressed. It never reads, changes or judges what was asked or what comes back. An External Service owns its API and its Service policy: it reads the calling ProjectEnvironment's Project configuration and decides every request itself.** Concretely:

- **The Gate refuses two things.** A caller whose credential identifies no ProjectEnvironment gets 401. A call addressed to a service that is not there for the caller's Organization (unknown, disabled, deleted or never published) gets 404. Everything else is forwarded to the service's running copy (its Default environment, or Development for the builder's Test Project) together with the caller's identity.
- **A service is reached at its Service host.** Every External Service answers at the root of `<slug>.external-services.<base>`, the same name in every Organization. The Gate finds the service from the caller's Organization and the slug, never from the name alone, so two Organizations' `github` services share a name and never meet. The name does not change once the service is published: callers write it into git remotes, kubeconfigs and App code, and that code keeps working in any Organization that has a service of that slug. The host is public like an App's; nothing passes it without a credential that identifies a ProjectEnvironment.
- **No request checks in the platform.** The platform has no Operation names, switches, read/write/destructive kinds, input schemas, bounds or size caps. The Gate reads the credential to learn who is calling and the address to learn which service; it does not judge path, query, headers or body. The edge in front of it resolves `.` and `..` path segments (Traefik's path sanitizing, kept on), so a service judges the path that is actually forwarded, and the SDK's refusal of unsafe paths is defence in depth for whatever reaches a service unresolved.
- **The service learns who is calling only from the platform.** The Gate finds the caller's Gateway Key by its shape in whichever request header the client put it (a `token`, `Bearer` or `Basic` `Authorization`, or any custom header; never the URL or body), so it supports no list of clients, and its 401 carries a `Basic` challenge. It removes that header and every incoming `X-Opsiforce-*` header and adds the Caller identity: a JWT signed with the receiving copy's own Gateway Key, naming the kind, the Organization, Project, ProjectEnvironment and environment, and expiring within minutes. The kind says only who made it: `call` for traffic through the Service host, `platform` for the platform's own calls, which go from the backend straight to the pod and name a ProjectEnvironment only when made for one. Only the platform sets it. The SDK refuses any request without a valid Caller identity before any route runs, and an External Service's Projects are not served on the Apps host, so reaching a service's pod some other way grants nothing. The platform configures no client in pods; each service's Service skill teaches its callers how to point their tools at the Service host.
- **No answer checks in the platform.** Status, headers and body stream back as the service sent them: no buffering, no status or header allowlists, no rewriting, no check for echoed secrets. The one exception is what the platform renders itself: answers to its own Form calls are re-read against the platform's shape and size limits and shown as plain text, but never checked for echoed secrets either.
- **Connected means configured, and the service refuses the rest.** A ProjectEnvironment is connected to a service when it has a Project configuration for it. The service receives the caller's configuration or none, and the SDK refuses a caller with none before the service's code runs, with a message an Agent can relay to its user.
- **Available decides listing only.** A service whose Service configuration leaves a required field of its Service form empty is not offered for Projects to connect; it still receives calls, and answers them itself.
- **The platform keeps everything about who and what was configured.** It identifies callers, routes to the right copy of the service, wakes and holds its pod, stores and encrypts both configurations, renders their Forms and enforces who may edit them, delivers the Service skill to connected ProjectEnvironments, and makes its own calls for Form option lists, info, buttons and after-save hooks. Those calls carry the unsaved Form values in their body, reach named handlers under `/.well-known/opsiforce/`, a path the SDK answers before any Service route and only for the `platform` kind, and never pass through Service routes.
- **A Built-in External Service is a committed folder.** `packages/opsiforce/external-services/<slug>/` holds its Service manifest, code and Service skill. The backend loads every folder at boot and refuses to boot on one that fails its check. Adding a built-in is a folder and a commit.
- **When a Service policy is wrong, the platform's brakes act on who and which service, never on what was asked.**
  - **Disable** stops a service on the next call. The Gate forgets its cached service at once and answers 404 with a message an Agent can relay. The service's pods are deleted, so streams in flight are cut too.
  - **Disconnect** removes one ProjectEnvironment's Project configuration. The SDK then refuses that environment as not connected, and every other Project keeps working.
  - **Rotate Gateway Key** gives a ProjectEnvironment a new key, revokes the old one at once and restarts its pod. The Gate also answers 401 for the key of a disabled Project.
  - **Publish runs two probes** against the Development copy and refuses unless that copy rejects both: a request with no Caller identity, and a request with a valid identity for a ProjectEnvironment that has no Project configuration. The platform reads no code. It tests only that the guard everything else relies on is in place.
  - **The Publish review is for a human, and blocks on nothing it shows.** Missing or stale test results are warnings at its top. A route newly open to all callers (`allowAll`) shows in the code diff; the review reads no routes of its own. The External Service Builder's Publish note says what changed and what each new or changed route lets through under which setting. The code diff between the Default environment's commit and Development's is there for whoever reads code.
  - **The SDK refuses to send a secret.** An answer of a route the service handles itself, or of a Form or hook handler, that contains the value of a secret field of its Service configuration fails instead of reaching the caller. Proxied answers pass untouched.
  - **The upstream is the second line.** The builder proposes the outside system's own protections next to the narrowest credential (a GitHub ruleset that lets `main` change only through a merged pull request), and the outside system's audit is the independent record of what a service did. The platform keeps no record and sends no alert.

## Considered options

- **Keep admission at the Gate and add pass-through routes for clients that need them.** Rejected: two places enforce, and the pass-through carries exactly the traffic whose rules matter, so the Gate's checks would cover the easy calls and miss the important ones.
- **The Gate also refuses a caller with no or an incomplete Project configuration, or a service that is not Available.** Rejected: these are the service's answers to give, worded for the caller's client. The SDK's default refusal of an unconfigured caller keeps the guarantee without the platform judging the call.
- **The service declares its own routes and guards under a platform path prefix.** Rejected: clients such as git and gh expect the outside system's paths at the root of a host, and a prefix breaks them as it breaks Apps on subpaths.
- **Turn the edge's path sanitizing off so that the SDK answers dot-segment paths as not supported.** Rejected: the resolved path is the one forwarded and judged, so it is as safe, and the setting belongs to the entrance every App and the main host share.
- **Name the host after the Default environment's id, as Apps are.** Rejected: a switch of the Default environment changes it and breaks every saved remote, kubeconfig and App that used the old one.
- **Name the host after the service's id.** Rejected: stable, but code and Agents copied to another Organization or deployment point at a service that does not exist there, and built-ins would need ids fixed by hand. Resolving the slug per pod into per-service variables would restore portability at the cost of pod restarts or a file kept in sync.
- **A token per service instead of the Gateway Key.** Rejected: an Agent that can be made to print one token can print them all, and a variable per connected service means pod restarts or a file kept in sync.
- **Forward the Gateway Key and let the service ask the platform who it belongs to.** Rejected: every service, written by any Organization admin, would collect the keys of every Project that calls it and could act as those Projects elsewhere.
- **Tell the service who is calling in plain headers, proven by the receiving pod's own key on the wire.** Rejected: a service that proxies by copying incoming headers sends its own long-lived key to the outside system; a signed identity that expires in minutes and checks out only at one copy is worth nothing there.
- **Keep a caller-set label saying whether the Agent or the App called.** Rejected: both run in one pod with one key, so nothing can prove it, and signing it would make it look trusted.
- **A kind per platform call (`form`, `inbound`, …).** Rejected: the path already names the handler, and a Service policy only ever sees `call`, so a finer kind would tell no one anything new.
- **Run the platform's Form calls through the Service routes, with the policy branching on the kind.** Rejected: a Form must list everything the service can see so a user can add to the Project's choice, while the Project's own calls are limited to that choice; one policy serving both is a rule every author must remember.
- **A second port on the service pod for the platform's own calls.** Rejected: any pod in the cluster can reach either port, so the Caller identity is checked on both anyway, and a second listener reaches the App's port model, the builder's probe and every local setup.
- **Configure common clients such as git in every pod.** Rejected: the platform stays free of tool-specific knowledge; how to reach a service is the service's to teach in its Service skill.
- **Reach the hosts only from inside the cluster.** Rejected: it protects only against a leaked Gateway Key being used later from outside, at the cost of a second entrance and in-cluster DNS in every deployment.
- **Rate, size or duration limits at the Gate.** Rejected: a clone, a watch and a log stream are long and large by nature, and a shared upstream quota is the service's to divide between Projects. The platform cannot tell a runaway Agent from a busy one.
- **Block Publish on missing or failing tests.** Rejected: the test report is a file the builder writes, so a block would catch forgetfulness, not a wrong policy, and would overrule the human who is reviewing.
- **Make the reviewer confirm each flagged change.** Rejected: confirmations get clicked through. A note that explains the change and a diff that proves it serve the reviewer better.
- **A Gate-side block list per ProjectEnvironment and service.** Rejected: removing the Project configuration already makes the SDK refuse, which Publish's probes verify, and keeps the Gate free of state about connections.
- **A separate permission to build and to Publish, or a second person to Publish.** Rejected: most Organizations have one admin who could not staff it.
- **The platform records or alerts on calls.** Rejected: it would have to read what was asked. The outside system's own audit is independent of the service's code, and the platform's is not.

## Consequences

- Any client works against a service as it would against the outside system; the service reproduces as much of that system's API as it chooses to offer.
- Less is caught centrally. A bug in a Service policy lets through a request the old Gate would have refused. It is stopped by the outside system's own protections where the builder set them up, and is meant to be caught earlier by the policy's tests and the human review at Publish. Once found, it is contained by Disconnect, Disable and key rotation. A service that echoes a secret through its own handler is stopped by the SDK. One that bypasses the SDK fails Publish's probes, but a proxied answer that carries a secret is not caught.
- The platform cannot tell a policy refusal from any other error status unless the service tells it.
- Tenant checks come from the caller's credential and the service it addresses, never from what the request says.
- A webhook from an outside system carries no caller credential, so a Service host cannot route it; webhooks reach the service at its Webhook address on the platform's own host, named by its id instead of its slug ([ADR-0084](0084-an-external-service-delivers-its-events-to-the-projectenvironments-it-chooses-and-the-platform-keeps-them-and-wakes-the-app.md)).
- A leaked Gateway Key reaches its Project's services from anywhere until someone rotates it or disables its Project. A service never holds a caller's key, and a leaked Caller identity is useful only at one copy of one service for a few minutes.
- A client that can carry a credential only in the URL or the body, or cannot be pointed at another host, cannot call a service directly; the service's Service skill offers another way.
- The SDK moves to a new major version, and services built on the previous one are rebuilt, not supported ([ADR-0081](0081-a-custom-external-service-carries-its-own-copy-of-the-sdk-and-upgrades-it-only-when-asked.md)).
