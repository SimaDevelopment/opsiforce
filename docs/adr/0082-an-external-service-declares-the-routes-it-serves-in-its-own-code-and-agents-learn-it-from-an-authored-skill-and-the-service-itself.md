# An External Service declares the routes it serves in its own code, and Agents learn it from an authored skill and the service itself

An External Service passes an outside system's own API to its callers ([ADR-0046](0046-an-external-service-owns-its-api-and-its-service-policy-the-gate-only-identifies-the-caller-finds-the-service-and-forwards-the-call-untouched.md)): gh and git reach a GitHub service as if it were GitHub, curl reaches a Trello service with Trello's paths. The platform does not know which requests a service serves, so it can neither describe them nor refuse the rest. An Agent still has to learn three things before it works: how to point its client at the service, which of the outside system's requests this service serves and how it changes them, and what the calling Project's configuration allows. A service's builder left alone with a GitHub token wrote an allowlist of eight REST routes scattered through `if`s, refused everything else with one generic message, and wrote a skill that never named the eight.

**A service declares what it serves as an ordered table of routes in its own code, through the SDK, and the SDK serves only what the table matches. Agents learn a service from three sources that never repeat each other: the `platform` skill (how to reach any service), the service's authored Service skill (what it is for, how to call it, how it differs from the outside system's own docs), and `GET /.well-known/opsiforce` on the Service host, which the SDK answers from the same table plus the caller's Project configuration.** Concretely:

- **Proxy first.** A route normally passes the request to a named upstream (its base URL, an optional mount such as GitHub's `/api/v3`, and a function adding the upstream's credentials), streamed both ways, optionally filtering the answer or rewriting the request. A route may instead refuse, to block part of what a wider route passes, or be handled by the service itself, only when there is nothing to pass through (a database, a SOAP system); a handled route's input and answer are described in the Service skill, as the outside system's own docs describe a proxied route.
- **Default deny.** Routes are matched top to bottom and the first match wins. A request no route matches is refused by the SDK as not supported. Every route carries a policy, and allowing everything is the explicit `allowAll`. "Pass the whole API through" is one `* /**` route with its policy.
- **Each route says what it does.** A route carries a one-line summary and the Project-form fields that govern it. A route that changes the request or the answer says so in its summary ("only the allowed repositories", "adds the Project's footer"), because an Agent otherwise assumes it behaves exactly like the outside system.
- **Two kinds of refusal, in the client's own format.** Not supported: no route matched. Not allowed: a route's policy refused, naming the setting and who can change it. A GitHub service answers in GitHub's JSON so gh prints it; a Trello service answers in plain text as Trello does.
- **The `platform` skill is written once for every service.** Its External Services section says how to reach `<slug>.$EXTERNAL_SERVICES_HOST` with the Gateway Key in a header and never in a URL, to read `/.well-known/opsiforce` before planning work with a service, and to relay a refusal's message to the user.
- **The Service skill is authored.** Each External Service carries one `SKILL.md` in its own folder, agreed with the person building it: what the service is for, how to set up the client (gh, git, curl, a vendor CLI), which outside API it passes and where that API's docs are, how calling it here differs (host, credentials the service adds, what it filters or refuses), and its conventions. It never lists routes by hand.
- **`/.well-known/opsiforce` is the live, per-caller view.** The SDK answers it from the route table in memory: the upstreams (name, API, real base URL, mount), every route (pattern, action, upstream, summary, governing fields, `allowAll` when it is), and the caller's Project configuration with labels and secrets masked. It does not mark routes allowed or refused, because a policy decides from the actual request. The `/.well-known/` prefix (RFC 8615) is reserved on every host for metadata, so it never shadows an outside system's path.
- **The platform shows routes and never decides on them.** The service page and the Publish review read `/.well-known/opsiforce` from the service's running copies and show the routes and their difference between Development and the Default environment. The review flags each route newly open to every connected caller (`allowAll`), the one widening the SDK states about itself, and asks for no confirmation. A copy that is not running shows no routes.
- **A Skill with one author.** The platform keeps the Service skill as a Skill in the Store named `service-<slug>` and marked by its service (one per service, deleted with it), built-in for a Built-in External Service and the Organization's for a custom one. A new version is laid only when the document changes: at boot for a built-in, for a custom service whenever the files of its Default environment's `app/` change. The Store, the skill builder and the Public API refuse every edit to it, and the Store refuses any other skill named `service-*`. No Service skill ships in the agent image.
- **Always the latest version.** An Agent Profile that carries a Service skill follows its newest version, unlike any other Skill: the text describes a live service.
- **Given per Agent or per Project, never as access.** An Agent carries it only when someone adds it on the Agent page, per Environment for a Custom Agent and per Organization for a Built-in Agent. A ProjectEnvironment with a Project configuration for a service gets its skill whatever its Agent carries, and may Switch it off ([ADR-0085](0085-a-project-environment-switches-skills-off-by-a-stored-choice-and-the-chat-bar-derives-the-rest.md)).
- **Live in existing Projects, for every Agent kind.** Adding or removing a Service skill on an Agent, a new version and a service becoming or ceasing to be Available reach Projects that already run that Agent. In a Custom Agent's Project this is an exception to [ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md)'s snapshot at create; its prompt, model and other Skills stay as created.

## Considered options

- **A hand-written OpenAPI document in the service's folder.** Rejected: it drifts from the code like any document; it cannot describe a family of proxied paths ("everything under `/repos/{owner}/{repo}/`") without copying the outside system's whole specification; and it has no place for which setting governs a route. OpenAPI suits only routes a service invents, and their schemas already live on those routes.
- **A generated `routes.json` beside `service.json`, read by the platform without running the service.** Rejected: every reader can ask the running service instead, and a copy kept in sync by a check is one more thing to drift. Its only gain, routes shown while a copy is stopped, is not worth it.
- **Routes listed in the Service skill, by hand or generated into it.** Rejected: by hand they drift on the first edit; generated, they duplicate `/.well-known/opsiforce`, which the Agent reads anyway.
- **A docs link on each route or upstream.** Rejected: the outside system's docs are only useful together with how this service differs from them, which only the authored skill can say.
- **The backend answering `/.well-known/opsiforce` from stored configuration.** Rejected: the backend does not know the routes, and the Agent would need a second address beside the Service host.
- **Precomputing allowed or refused per route for the caller.** Rejected: a policy decides from the request itself (which repository, which branch), so the answer does not exist before the request.
- **A Service skill generated from the manifest.** Rejected: how to set up gh or git, the conventions a service enforces and how an App receives its Events cannot be generated.

## Consequences

- An Agent makes one call to `/.well-known/opsiforce` before planning work with a service in a chat.
- A builder writes the route table, its policies and the Service skill, and a human approves all three before Publish.
- The service page and the Publish review depend on the service's copies running to show routes; the Default environment's copy never sleeps ([ADR-0083](0083-a-custom-external-services-default-environment-never-sleeps-its-state-lives-in-that-environments-workspace-and-is-copied-on-a-switch-and-its-webhook-url-belongs-to-the-service.md)).
- The shape of `/.well-known/opsiforce` is a contract between the SDK and the platform and changes only with an SDK major.
- Deleting a service removes its skill from every Agent that carried it.
