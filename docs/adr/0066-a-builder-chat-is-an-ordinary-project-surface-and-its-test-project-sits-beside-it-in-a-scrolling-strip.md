# A Builder chat is an ordinary Project surface, and its test Project sits beside it in a scrolling strip

[ADR-0064](0064-builder-chats-are-kind-stamped-projects-prompted-by-their-creator-with-pods-that-never-destroy.md) carried a Builder chat on a `kind`-stamped Project so it would stay out of every project list, and [issue 44](../../.scratch/agent-skill-platform/issues/44-builder-ui-and-rail-chat-list.md) built it a slim page of its own — a bespoke header, an inline title input, a five-item menu, and a button that swapped the whole pane between the chat and its test Project. Hiding the row from a list was a data decision; the bespoke page was not asked for and followed by habit. The result is a surface that looks unlike the thing it is: the chat has no Files, Code or DB tab over a workspace it demonstrably has, no Restart for a pod it demonstrably runs, and a menu whose word for stopping a pod is *Archive* while the identical action on every ordinary Project is *Disable*. [Issue 56](../../.scratch/agent-skill-platform/issues/56-fixes-and-cleanups-from-the-45-run.md) replaced the navigation with an in-place toggle and left the question open in as many words: *"Which surfaces the embedded view offers is the design call."*

**A Builder chat renders the ordinary Project chassis, and the chat and its test Project are laid out as a two-pane horizontal strip that scrolls when the panes no longer fit.** Concretely:

- **One chassis, gated by condition rather than forked by kind.** `ProjectView`, `ProjectHeader` and `ProjectActionsMenu` serve both panes. The full tab set — Chat, Files, Code, DB — applies unchanged, including its existing double gate on `can_view_code_tab` / `can_view_db_tab` and on whether the pod reports a router. No `kind` discriminator reaches the frontend: where an action does not apply it is suppressed by the condition that already describes why. Move to is hidden because a `kind`-stamped row has no `workspace_id` to move between and its sharing is [ADR-0065](0065-a-builder-chat-is-private-or-public-and-one-gate-enforces-it-on-every-runtime-surface.md)'s chat visibility instead; Duplicate and Export are hidden on a `test` row because a throwaway snapshot has no coherent copy and its zip would carry live environment-variable values ([ADR-0017](0017-project-export-is-a-faithful-full-workspace-zip.md)) for something deleted on the next run.
- **The strip, not a splitter.** Two panes, a draggable divider between them, a minimum width of `min(420px, 100%)` each, scroll-snap to pane boundaries, chevron arrows on hover-capable pointers and swipe on touch. When both panes fit, the divider behaves exactly as a splitter; when they do not, the strip scrolls and the arrows appear. The arithmetic is why: at 1440px, less the app sidebar and the Store rail, roughly 944px remains for two panes — and the test Project's preview column declares a 320px minimum of its own inside the right pane, so a splitter that forced both panes to share the width would deliver two panes that are each slightly too narrow with no way to say which one you are reading. The same component serves a phone, where the pane minimum resolves to the viewport and the strip becomes a two-page swipe deck.
- **One pane until there is a live test Project.** Most chats never start a test — a Skill chat has nothing to test — and the pod creates the test Project through the public API when the conversation reaches it, not the reader through a button, so an empty right pane would advertise an action nobody performs while halving every Skill chat's composer. A Disabled chat resolves to the same single pane by the same rule: its pods are gone, so nothing is live.
- **A static label per pane, and no editable title in a header.** Two panes each carrying a kebab that contains Delete cannot both be nameless. `ProjectHeader` gains a leading label slot: the left pane reads *Builder chat* with its kind, visibility and disabled badges, the right pane the test Project's title. Renaming stays out of the header — a chat is renamed from its rail row, and a test Project, which has no rail row, from its own pane kebab.
- **The preview belongs to the test Project, not to the strip.** It stays the right-hand column inside the right pane exactly as on any Project, and the strip scrolls once, at the moment a preview first opens, to bring that pane fully into view. Nothing collapses or reappears as the divider moves. The chat gets no preview column of its own: it authors Markdown definitions, not a running App, so the column would be permanently empty and would put a second `ProjectPreviewPanel` on one page for no gain.
- **Divider position persists globally; scroll position does not.** Width is a preference about how someone likes to work and should not reset per chat. Where they had scrolled to is state, and restoring it means a reload lands on a test Project with the chat off-screen. The strip always opens on the chat.
- **The Store rail becomes collapsible.** Its fixed 224/240px is the largest reclaimable span on the page and the difference between arrows appearing constantly on a laptop and almost never. It collapses on the reader's instruction and persists, the way the app sidebar already does — never automatically when a pane opens.
- **`ProjectHeader` stops resolving its Project from the list.** It reads `useProjects()` and finds by id, and `GET /projects` excludes `kind IS NOT NULL` by construction ([ADR-0064](0064-builder-chats-are-kind-stamped-projects-prompted-by-their-creator-with-pods-that-never-destroy.md)), so inside a test pane the lookup has always missed: the header's badge never rendered and the menu received no Project, falling back to the title *Untitled project* in every export and duplicate job entry. `GET /projects/:id` already answers correctly for a hidden row through `findOneUnlessHidden`, which resolves reachability by walking to the governing chat; the missing piece is a `useProject(id)` hook, which goes through `createAppQuery` per [ADR-0043](0043-read-queries-go-through-createappquery-not-the-stock-tanstack-adapter.md).

## Considered options

- **A resizable splitter, two panes always summing to the available width** — rejected on the arithmetic above. It is the house pattern and would have reused `createResizablePanel` with no new interaction, but it has no answer for the moment the panes stop fitting except to make both unusable, and no way to express "I am looking at the test Project right now".
- **Keeping the `'chat' | 'test'` toggle as the sub-`md` fallback** — rejected by the owner. It would have preserved a state machine that already works, but two layouts is two layouts; a strip whose pane minimum is viewport-relative degrades into a swipe deck without a second code path, and the phone case is then the same component rather than a second one to keep in sync.
- **A third top-level pane for the preview** — rejected: the preview is the test Project's own column and describing it as a sibling of the Project it belongs to would have made the strip's panes mean two different things.
- **A shared page-level header with one kebab over both panes** — rejected: it reproduces the toggle's ambiguity about which Project an action applies to, in a layout whose entire purpose is that both are visible at once.
- **A focused-pane model, where only the focused pane shows its kebab** — rejected: least clutter, but it hides actions behind a click and invents an interaction pattern that exists nowhere else in this frontend.
- **Auto-collapsing the app sidebar and Store rail when the split opens** — rejected: it moves chrome the reader did not ask to move and fights them when they restore it.
- **Threading a `kind` prop through `ProjectView` to fork the chassis** — rejected: every suppression here has a truer reason than *because it is a Builder chat*, and a kind prop would invite the next one to be hidden for no reason at all.

## Consequences

- The strip is the first horizontally-scrolling surface in this frontend with paging affordances; `overflow-x-auto` appears today only on the mobile rail, and there is no `scrollBy`, no `scroll-snap` and no chevron rail to copy. `createResizablePanel` and `ResizeHandle` carry the divider, but the scroll-and-arrow behaviour is new code with no in-repo precedent and no installed library — neither Kobalte nor `@corvu/drawer` ships a splitter, and `@corvu/resizable` is not a dependency.
- Two `ProjectView`s are visible at once for the first time. They were already *mounted* at once — the toggle only flipped `display`, deliberately, so switching would not reload the preview iframe or reconnect the runtime — but visibility is what exposes the document-scoped helpers around the embed, which [ADR-0067](0067-the-embeds-dom-helpers-are-scoped-to-their-host-element-not-the-document.md) settles as a prerequisite.
- The word **Archive** leaves the Builder surface. A chat and a test Project are *Disabled*, matching the action they have always performed; **Archive** narrows to the Store sense, where an Agent or a Skill is hidden from the catalog and no pod stops. The rename reaches the Store's builder filter chip, the `/store/builder` empty-state copy, the badge on chat rows, the delete dialog's escape hatch and its toast. `agents.archived` and `skills.archived` are untouched.
- The `ProjectHeader` lookup fix is not cosmetic: it is why a test Project's export and duplicate entries have been filed under *Untitled project*.
- The composer note moves into the chat pane and shows only until the first prompt is sent. In a permanently visible pane it would be furniture, and deleting it outright would lose a genuinely useful explanation on an empty chat.
- The Store rail's collapse is independently useful and ships before the strip, as does [ADR-0067](0067-the-embeds-dom-helpers-are-scoped-to-their-host-element-not-the-document.md). The chassis swap ships before the strip too: the toggle keeps working while the panes become correct.
- Glossary: no new term. **Disable (Project)** is recorded in `CONTEXT.md` as the canonical word for stopping anything that runs, explicitly not a synonym for Archive, and the **Builder chat** entry no longer says *archived*.
