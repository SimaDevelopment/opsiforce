# Skill Store and Custom Agent authoring ride four flat scope-partitioned permissions

The dynamic catalog ([ADR-0051](0051-skill-catalog-append-only-store-tables.md)–[ADR-0054](0054-built-in-and-custom-agents-coexist-by-scope.md)) needs an authorization answer, and the house model constrains the shape: opsiforce has no roles — only flat `can_*` permission strings issued through Keycloak groups, user-global by construction, with cross-Organization capability marked by a `platform_` name segment and deliberately excluded from the admin bundle ([ADR-0027](0027-platform-scope-routes-opt-out-of-tenant-resolution.md)). The reference platforms surveyed for this feature converge on "publish is a separate grant from create/use" (LibreChat `SHARE` vs `SHARE_PUBLIC`, CrewAI's explicit publish permission, Copilot Studio submit→admin-approve, AWS Agent Registry's publisher/curator/consumer personas) — but that split only earns its keep when non-admins author, which v1 does not allow.

**Authoring rides four flat permissions, strictly partitioned by scope; consuming needs none. Global authoring is operator-direct, and operator access to tenant content is by membership, never elevation.** Concretely:

- **Four new strings.** `can_manage_skills` and `can_manage_agents` govern the caller's current Organization's rows and join the `opsiforce_admin` bundle. `can_manage_platform_skills` and `can_manage_platform_agents` govern global rows (`tenant_id IS NULL`), get standalone Keycloak groups excluded from the admin bundle, and are granted alongside ordinary Organization membership, per the ADR-0027 pattern. "Manage" spans the artifact's whole authoring surface: create/edit Draft Revisions, publish, archive, revoke, and — for skills — attach/detach and `.skill` import.
- **Consuming is permission-free.** Any member browses the published Store, inspects content, and uses attached Skills in Projects. Drafts and archived artifacts are visible only to the scope's manage-permission holders.
- **Strict partition, no hierarchy.** Neither string opens the other scope's writes — the first permission in the system to imply another would be this one, and it doesn't. When an operator needs hands-on work inside a customer Organization, they are added to that Organization's Keycloak group (temporarily if need be): permissions being user-global, their tenant-scope grants light up there, they act as a visible member through the one normal API path, and provenance stays clean. This is the kubeopencode principle the research recommended adopting — the API enforces scope purely from the caller's own tenant identity, no side-channel elevation.
- **No tenant→global promotion flow in v1.** Platform-permission holders author global artifacts directly through the same API (scope chosen at creation). The fully pre-researched approval state machine (submitted → approved/rejected, flag acknowledgment, name edit-distance review, ERROR re-check — `research/skill-validation-security.md` "Scope-escalation gates") stays parked until tenant-authored content has a reason to cross tenants.
- **Revoke (Skill Version) is scope-bound, not a platform power.** Revoking withdraws one published Version from pod delivery on the next sync, existing Attachments included — deliberately the opposite delivery semantics of Archive/Deprecated (ADR-0051), which never touch existing Attachments. An Organization revokes Versions of its own Skills (the self-service emergency stop for a bad `.skill` import); the platform revokes global ones. The rogue-tenant case — dangerous content the owning tenant's admins won't remove — is handled by the membership playbook above, not by a cross-scope reach.
- **One matrix for every door.** The form UI, the raw API, and the Builder chat all resolve to the calling user's permission set; a member without `can_manage_skills` cannot author through any of them. The Builder pod's credential (ticket 13) must therefore resolve to the launching user's permissions, nothing wider.
- **Standalone collapses to instance-admin.** All four strings are plain permissions, so `auth.mode: static` grants them via the Helm values list (all four enter the default static bundle — a single-operator install *is* the platform) and `SSO_GROUP_MAP` maps customer-IdP groups onto them with no code change.

## Considered options

- **Per-action grants (LibreChat's `USE/CREATE/SHARE/SHARE_PUBLIC` matrix; create-vs-publish split)** — rejected for v1: the split matters only when authors and publishers differ, and v1 gates authoring end-to-end behind the same admin-tier grant. Loosening later (a `can_create_skill_drafts` tier) is additive; tightening after members have authored is not.
- **One combined platform permission (`can_manage_platform_catalog`)** — rejected: the platform pair mirrors the tenant pair, keeping one mental model (skills grants vs agents grants) on both sides of the partition.
- **Cross-scope Revoke (platform revokes tenant Versions — the VS Code kill-bit shape)** — rejected for v1 in favor of the membership playbook; every researched revocation precedent is platform-reaching-into-user-space, so if practice demands it the cross-scope route is a purely additive later change.
- **Platform permission as superset (author into any tenant)** — rejected: tenant-scoped routes require membership via `TenantGuard`, so a literal superset needs a parallel `@PlatformScope()` write surface duplicating every authoring endpoint on a fail-open guard system, and it would introduce the first permission hierarchy. Membership composition yields the same operational capability with zero new machinery.
- **Per-Organization permission grants ("skill admin in org A, member in org B")** — rejected: permissions are user-global by construction (ADR-0027); per-tenant grants would fork the machinery under all 30 existing permissions, not just these four. Recorded as a known limitation; a future effort of its own if a real customer needs it.

## Consequences

- Each new permission has five sync points: Pulumi `permissions.ts`, a Pulumi group, backend `Perms`, the frontend constant, and the Helm static-auth list — four strings × five places, in one change (the `can_view_queue_dashboard` static-list drift is the cautionary tale).
- Every new store/agent controller takes a **class-level** `@RequirePermission` with per-route relaxation for member-readable endpoints, never the reverse — the global guard is fail-open, and the schedule controller once shipped open because of it.
- Revoke routes address a Version by id; the global-scope one is `@PlatformScope()` (no tenant resolution), the tenant-scope one rides the normal tenant path and checks row ownership.
- `skill_versions` gains a revoked marker that the ADR-0053 delivery delta filters out; Attachment rows are untouched by a revoke.
- Known limitation on record: a holder of `can_manage_skills` holds it in every Organization they belong to.
