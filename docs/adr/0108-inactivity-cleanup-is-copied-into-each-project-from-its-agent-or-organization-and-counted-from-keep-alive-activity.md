# Inactivity cleanup is copied into each Project from its Agent or Organization and counted from Keep-alive activity

Agents such as the Makara and Opsiforce builders create Projects that are heavy on storage and pods, and keeping every one of them forever costs money nobody chose to spend. An Organization needed Projects of such an Agent to be disabled, and later deleted, once nobody has used them for a while, without the existing idle timeouts (which only suspend a pod for minutes) changing meaning.

**Every Project carries its own [Inactivity cleanup](../../GLOSSARY.md) — Disable after and Delete after, durations in hours or days from 1 hour, empty meaning never — copied once at creation as a pair: its Agent's own pair when it has one, otherwise the Organization's default. An hourly job disables, then deletes, ordinary Projects whose last [Keep-alive activity](../../GLOSSARY.md) is older than those counts, through the same Disable (Project) and delete a user runs.** Concretely:

- **Layers, copied once.** The platform default seeds each new Organization's default like the idle timeouts and budgets do; an Agent may set its own pair; a Project copies the resolved values at creation and owns them from then on, which is also how [Resources](../../GLOSSARY.md) and the idle timeouts reach a Project. Lowering an Agent's count therefore never reaches its existing Projects, so one edit cannot disable or delete hundreds of Projects at the next sweep.
- **An Agent's own pair is stored like its Resources.** A Custom Agent's sits in `agent_inactivity_cleanup`; a Built-in Agent's sits in `tenant_agent_inactivity_cleanup` for each Organization that chose one, over a platform pair in `agent_inactivity_cleanup`, and the Agent Settings dialog edits both kinds of Agent, as it does Resources since [ADR-0093](0093-an-agent-sets-the-resources-and-ready-projects-of-the-projects-created-from-it.md). A setting an admin tunes belongs in the database where each Organization owns it, not in `agents.json`, where only an image release changes it and every Organization gets the same.
- **A row decides the whole pair.** A layer with a row gives the Project its pair, an empty count meaning never, so an Agent can keep its Projects forever under an Organization default; a layer with no row hands over to the next one down, ending at the Organization's default. Each layer's pair is validated when it is saved, so a pair taken whole always has Delete after later than Disable after; mixing counts across layers could give a Project a Delete after shorter than its Disable after, which no one ever chose.
- **Last activity is both kinds of Keep-alive activity.** It is the latest `project_environments.last_active_at` of the Project, which chat, the editor, file access, App traffic, scheduled runs, webhooks, incoming email and pod startup already write — anything that wakes the Project — or the Project's creation when no environment ever ran. A Project whose App is in daily use is never cleaned up for want of chat.
- **Delete after counts from the same last activity, not from the disable.** With 14 and 28 a Project is disabled on day 14 and deleted on day 28, so the two numbers read as the plain days they name, and a Project that skipped the disable (because Disable after is empty) is still deleted on time. That is why Delete after must be the larger number.
- **Enable restarts the clock.** Enabling a Project writes its environments' last activity, so a Project brought back is not disabled again at the next sweep.
- **Only ordinary Projects.** A Project with a `kind` — a Builder chat, a Test Project — lives and dies with what it serves, and a pool slot has no Organization yet, so neither is ever swept.
- **Setting counts needs the right to do it by hand.** On a Project or an Agent, Disable after needs `can_disable_project` and Delete after needs `can_delete_project`, so a member who cannot delete a Project cannot schedule its deletion either, directly or through the Agent others create Projects from. An Agent's Duplicate, Export and Import carry its own pair like its Resources only for a copier holding both, since a pair decides both counts; anyone else's copy follows its Organization's default.

## Considered options

- **Minutes as well, with a sweep every few minutes.** Rejected because a frequent sweep costs a query every few minutes for precision cleanup never needs; with hours and days and a 1-hour minimum, the hourly job acting up to an hour late stays within the unit people chose. The counts are stored in milliseconds like the idle timeouts, so the forms share their units.

- **A Built-in Agent's counts in `agents.json`, as `podClass` once was.** Rejected for the reason Resources left it: no Organization could tune a Built-in Agent and every change needed an image release.
- **Empty counts on an Agent meaning "follow the Organization".** Rejected because an Agent could then never say "never" under an Organization default; a row's presence says whether a layer decides, as with Resources.

- **Follow the Agent live, as Limits follow the platform value.** Rejected because a change would reach every existing Project at once, and for a setting that deletes work that is the wrong blast radius; Projects keep their own copy, as with Resources.
- **Reuse the idle timeouts as the disable clock.** Rejected because an idle timeout suspends a pod that wakes on the next visit and runs in minutes, while Disable after stops a Project until someone enables it and runs in days.
- **Count only Prompts.** Rejected because a Project whose App serves visitors every day would be disabled under them.
- **A new activity column on `projects`.** Not needed: `project_environments.last_active_at` is already written on every kind of Keep-alive activity.
