# Organization limits are key/value rows that follow the platform value unless overridden

An Organization needed a ceiling on how many Projects it may hold, with more ceilings of the same shape expected later. The platform sets the value new Organizations follow; Organizations that already existed are left unlimited; and no Organization may raise its own.

**Each Limit is a row keyed by `limit_key`: `global_limits` holds the platform value, a `tenant_limits` row overrides it for one Organization, and the check runs inside every creating transaction under a per-Organization, per-key advisory lock.** Concretely:

- **Rows, not columns.** Every Limit has the same shape — a key, a non-negative integer or none, and a count — so one row per key lets one lock-and-check, one usage read and one Settings page serve every Limit. A column per Limit on `tenant_settings` was rejected because each new Limit would repeat the same column, validator and endpoint; typed columns stay the right shape for `tenant_settings`, whose settings differ in kind.
- **Follow the platform unless overridden.** An Organization with no `tenant_limits` row is held to the platform value live, so changing it reaches every Organization nobody has set by hand, and a row always marks a deliberate exception. Copying the platform value at Organization creation, as the timeout and budget Defaults do, was rejected because a later platform change would then reach only Organizations created after it, and a copied value is indistinguishable from a chosen one. Organizations that existed when a Limit is introduced get a NULL row in its migration, which is how they stay unlimited. "Existed" means a `tenants` row, which is created on an Organization's first sign-in, so an Organization known to the identity provider that had never signed in gets the platform value; that is accepted because such an Organization holds nothing the Limit could strand.
- **Keys live in code and in a `CHECK`.** The registry is the source of truth, because the part of a Limit that matters — how it is counted — is code. Both tables carry `CHECK (limit_key in (...))`, so a mistyped key cannot be stored and silently ignored. A Postgres enum was rejected because values cannot be dropped without rebuilding the type; a definitions table was rejected because it would describe only half of a Limit. The migration that adds a Limit already exists to set its platform value, so extending the `CHECK` there costs nothing.
- **A Platform-scope permission, outside the admin bundle.** `can_manage_platform_limits` has its own Keycloak group and is never in `OPSIFORCE_ADMIN_GROUP_PERMISSIONS`, so an Organization's administrators cannot lift their own Limits.
- **The Projects Limit counts enabled `kind IS NULL` Projects, and enabling one is checked like a create.** The Limit exists to bound pods and spend, and a disabled Project has no pod and spends nothing, so disabling one frees its slot; re-enabling takes the slot back under the same lock and check, which is what stops a disable-then-enable round trip from walking around the Limit. Counting disabled Projects was rejected because it would make an Organization delete work it only wanted to park. A Custom Agent costs a Builder chat plus a Test Project, and counting them would spend Project slots on plumbing no user sees as a Project; they are already bounded to one Test Project per chat. Pool slots carry no Organization until claimed, so they are never counted.
- **A lock in every creating transaction, not a pre-check.** Create, duplicate, import, the pool claim and enable each lock before counting, so two creates at `limit - 1` cannot both pass. The pool claim's catch-and-fall-back rethrows the refusal rather than retrying the slow path.
