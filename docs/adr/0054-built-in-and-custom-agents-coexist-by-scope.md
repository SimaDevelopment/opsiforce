# Built-in and custom agents coexist by scope in one agents table

Custom Agents ([ADR-0052](0052-custom-agent-anatomy-and-model-presets.md)) are rows in the same `agents` table the registry reconciler owns today. That table was built for a single writer: `name` is globally unique, the reconciler upserts on it, the picker returns every row unfiltered, and every pod-facing consumer (init container `AGENT_NAME`, Agent-Updates sweep, pool warm-up) assumes a row's slug resolves in the merged registry and in the image's `/opt/agents/`. Each assumption breaks once tenant-authored rows share the table: the reconciler's conflict target would let a future platform release that ships a built-in agent with a slug a tenant already used silently rewrite the tenant's row (an identity merge across tenancy), a registry-retired built-in row stays pickable and crash-loops its init container (`cp -a /opt/agents/<slug>` under `set -e`), the sweep would skip every Custom-Agent project as "agent missing from registry", and pool sizes would have two homes.

**Baked and custom agents coexist by scope: uniqueness, reconciliation, and liveness are all evaluated per scope, and everything image-owned resolves a Custom Agent through its Base Agent.** Concretely:

- **Scoped slug uniqueness.** The global unique on `agents.name` is replaced by uniqueness per tenant — `(tenant_id, name)` for tenant rows plus a partial unique index on `name` where `tenant_id IS NULL` for the global scope (built-in rows and global Custom Agents share the global scope). ADR-0052's reservation of built-in slugs at creation time stands; this constraint covers the reverse race, where a *later* platform release ships a built-in slug a tenant already published (tenant names in standalone installs are unknowable at platform-authoring time — the same residual race ADR-0053 resolves for skills).
- **The reconciler conflicts only within the global scope.** Its upsert targets the global partial index (rows with `tenant_id IS NULL`), stamps `origin = 'built-in'`, and never touches tenant rows. A colliding future release therefore inserts a new global row that *coexists* with the tenant's same-named row — never hijacks it. The tenant may see two same-named agents in the picker; disambiguation (a built-in/custom badge) is prototype-ticket UX.
- **Built-in liveness is registry membership, read where it is consumed.** The reconciler stays additive (never deletes, never deactivates). The Agent picker and project-create validation offer a built-in row only while its slug is in the merged registry; a Custom-Agent row is offered only when its `status` is active *and* it has at least one published `agent_profile_versions` row. Existing Projects keep resolving any row by id regardless — the additive guarantee is unchanged. Rolling back a release that pulled an agent self-heals: the row was never mutated.
- **Custom-Agent Projects resolve through `base_agent_id` for everything image-owned.** `AGENT_NAME` at pod creation is the Base Agent's slug, the workspace ledger is kept under the Base Agent's name, and the Agent-Updates sweep compares against the Base Agent's template version and runs the migrate Job as the base. Custom agents never enter `agents.json` and have no template version of their own; the dynamic sync ([ADR-0053](0053-dynamic-artifacts-delivered-by-direct-backend-write-plus-dispose.md)) overlays prompt, preset, and skills on top after every image-side write.
- **`pool_size` is one column, mirrored on boot for built-in rows.** The reconciler copies each registry entry's `poolSize` into the row on every boot, so the registry stays authoritative for built-in agents by construction (an admin edit to a built-in row's pool is overwritten at next boot); admin edits are honoured on custom rows only, per ADR-0052. The pool service reads the column universally — one read path.
- **The standalone seam holds with no new machinery.** Slug reservation checks the merged registry (public ∪ private) server-side and fails with a generic "name unavailable" so private names never leak through error text. In standalone the merge yields public-only, so a slug that is private in SaaS is takeable there — acceptable, the private agent never ships there and scopes keep the rows distinct. `base_agent_id` must reference an agent present in *this install's* merged registry, validated at creation — which also stops a DB imported into standalone from referencing a base it doesn't ship.

## Considered options

- **Platform-wins shadowing on slug collision** (LibreChat's deployment-dir skills overriding same-name DB skills) — rejected: an agent row is an identity Projects reference, not content to shadow; hiding the tenant's agent behind the platform's would reroute nothing but confuse everything. Coexistence keeps both identities intact.
- **Reconciler stamps registry-absent built-in rows `archived`** — rejected: mutates rows the reconciler promised to leave alone, needs an un-stamp path for release rollbacks, and duplicates state the registry already expresses. Read-time membership is the same fact with no second copy.
- **Pool read-path branching (registry for baked, column for custom)** — rejected: two read paths forever for one concept. Mirror-on-boot keeps registry ownership with a single consumer path.
- **Column-authoritative pool sizes seeded once from the registry** — rejected: silently converts built-in pool sizing from a code rollout into a runtime knob, against [ADR-0008](0008-agent-model-owned-by-agent-config.md)'s agent-config-wins posture.
- **Teaching the image/sweep about custom slugs** (staging custom agents in the image, or per-custom template versions) — rejected: custom agents deliberately have no image presence; the base *is* the workspace's built-in identity and ADR-0053's overlay already carries the custom delta.

## Consequences

- Migration: drop the global unique on `agents.name`, add the composite and partial unique indexes, add `tenant_id`, `origin`, `status`, `pool_size`, `base_agent_id`; the reconciler's conflict target moves to the global partial index and stamps `origin`/`pool_size`.
- `AgentService.findAll` stops being the picker query: listing becomes scope- and liveness-aware (merged-registry membership for built-in rows; status + published-version existence for custom rows) and tenant-filtered.
- The Agent-Updates sweep and pod templating gain one resolution hop (`origin = 'custom'` → `base_agent_id`); the "agent missing from merged registry → skip and log" guard now applies only after that hop, and the init-container crash trap cannot occur for Custom-Agent projects.
- A retired built-in agent disappears from the picker the moment the registry drops it, with its row — and every existing Project on it — intact. Whether such Projects deserve a nudge to migrate is future work, not v1.
- The picker can legitimately show two same-named agents (tenant custom + later-shipped built-in global); the store/picker UI owes them a provenance badge (prototype ticket).
