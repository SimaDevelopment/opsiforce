# Custom agents are base-anchored profiles picking from a model-preset catalog

Tenant-created Agents need an answer to what a tenant may author and what stays platform-owned. [ADR-0008](0008-agent-model-owned-by-agent-config.md) settled the sharpest edge of that line for built-in agents: the model lives in `agent-config`, in lockstep with its per-model `limit`/`variant` config in `opencode.json`, and is not a tenant knob — precisely because a model selected apart from its config invites mismatches. Custom agents reopen the question: a tenant authoring an agent reasonably wants some say over the model, and a field survey (`.scratch/agent-skill-platform/research/agent-version-storage.md`) found that platforms exposing an unvalidated model choice are the ones citing it as a defect, while platforms hiding it entirely are the curated consumer products.

**A custom agent is identity + prompt + skill attachments over a base agent, and its model is a reference into a platform-vetted preset catalog.** Concretely:

- **Base-anchored.** Every custom agent carries an immutable `baseAgentId` naming a built-in registry agent (initially `app-builder`). The base supplies everything the author does not write: runtime image behaviour, tool and permission posture, the starter template (always inherited — no template choice in v1), and pool semantics. There is no field-level override mechanism; the split is fixed.
- **Model presets.** `agent-config/model-presets.json` ships named bundles of model + variant + limits, pre-validated and deployment-aware (the standalone build lists presets its codex-proxy path supports). A custom agent stores a preset **key**; delivery resolves the key at render time, falling back to the base agent's preset if the key is missing from the running distribution. Publishing validates the key against the catalog. Upgrading what a preset resolves to rolls every agent referencing it — model rollouts remain a platform act. This *extends* ADR-0008 rather than superseding it: `agent-config` still owns which models exist and their config; the database only ever holds a pick among them.
- **Versioned like skills.** Custom-agent content follows [ADR-0051](0051-skill-catalog-append-only-store-tables.md)'s append-only discipline in `agent_profile_versions`: every save a new draft revision, publish stamps the next integer version and freezes the row, restore drafts a new revision from an old one (copy-forward, history never rewritten), live = highest published version, no pointer column. The version row is the **whole authored definition** as real columns — `prompt_body`, `description`, `model_preset` — matching the survey's unanimous finding that versioning systems snapshot the full definition, model included. Identity and operations stay mutable on the `agents` row: immutable slug, renameable display name, `tenant_id` (NULL = global, permission-gated), `status`, `origin`, `base_agent_id`, `pool_size`.
- **Slugs mirror skill names.** Auto-derived kebab-case, unique per tenant, all built-in registry slugs (public ∪ private, checked server-side so private names never leak) reserved, immutable once created.
- **Pools are platform capacity, not tenant anatomy.** `pool_size` exists uniformly on every agent row but defaults to 0 for custom agents and is settable only by platform admins in v1. Tenant custom agents ride their base agent's shared pending pool: every pool claim runs a specialization push (the claiming tenant's skill-attachment delta always; prompt + preset additionally for custom agents; one dispose), so a dedicated warm slot would buy seconds at the cost of a tenant-exclusive idle pod. Global custom agents are tenant-neutral, so warming them is legitimate where an admin opts in.
- **End-states mirror skills.** `archived` (tenant for own agents, platform admin for global ones) hides the agent from the picker and new-project flow, drains its pool, and leaves existing Projects running unchanged. Hard delete exists only for never-published agents.

## Considered options

- **No model choice (inherit the base's model)** — the openwork/cloudflare-os/GPT-Builder posture. Rejected as the end state: the preset catalog costs the same schema (inherit is a one-entry catalog) and the product wants the tuning surface; kept as the v1 catalog's likely size.
- **Free-pick model strings** — rejected: reintroduces exactly the model-without-its-config mismatch ADR-0008 exists to prevent, now multiplied by tenants; the survey's two unvalidated-model systems both treat it as a defect.
- **Freestanding custom agents (full profile per row, platform defaults fill gaps)** — rejected: hands tenants infra fields (image behaviour, permissions, template) the platform must own, and every researched anatomy that works reduces the tenant-authored part to prose + attachments.
- **Model as a live column outside version history** — rejected: no surveyed system does it, it splits one artifact across two write disciplines, and the concern it addressed (rollback dragging the model along) is already solved by copy-forward restore.
- **One JSON blob per version** — rejected for the same reasons ADR-0051 rejected archive blobs: the definition is three queryable fields, listings and diffs read them constantly, and blob systems end up duplicating parsed fields beside the blob.
- **Per-custom-agent tenant-set pool sizes** — rejected for v1: mechanically sound (claims match by agent id, so reachability enforces exclusivity) but economically wrong as self-service — it makes agent creation a free cluster-capacity lever; revisiting as an admin/quota-gated knob later is purely additive.
- **Tenant-authored starter templates** — ruled out of this effort entirely (recorded on the wayfinder map): copy-on-use template stores are a documented drift trap, and templates would need their own versioning/validation story.

## Consequences

- ADR-0008's statement that the model is "uniform across every tenant and project" no longer holds verbatim — uniformity now lives at the preset level. The glossary's **Agent Model** entry is rewritten in the same change, and **Model Preset**, **Custom Agent**, **Base Agent** are added.
- The pending-pool claim flow gains a mandatory specialization step (skill-attachment delta for every claim, not only custom agents) — specified in the pod-delivery work, which also owns verifying the claim-recovery window around the new push.
- The agent reconciler and Agent picker must coexist with DB-origin agent rows (`origin` column distinguishes them); that surface is the registry/reconciler-coexistence work.
- Built-in agents are untouched: their content never enters `agent_profile_versions` (git and the image stay the single source of truth per ADR-0051's content-class rule), and their registry-carried model fields keep working unchanged; migrating the registry's `model`/`variant` pairs to named presets can happen incrementally.
- Adding tenant-facing knobs later (a curated template picker, quota-gated pool sizes, tools/temperature exposure) is additive schema work, not a redesign.
