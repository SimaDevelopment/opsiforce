# A Custom External Service's default environment never sleeps, its state lives in that environment's workspace and is copied on a switch, and its webhook URL belongs to the service

A Custom External Service is a Project whose published ProjectEnvironments each run the service's code, and a Default environment (External Service) setting picks which one callers reach. Unlike an App, a service is called mostly by things no human is watching: Apps' Schedules, other Apps, and webhooks from outside systems (GitHub waits 10 seconds for an answer and does not redeliver).

**The default environment of a published, enabled Custom External Service is exempt from idle sleep; its `ctx.state` lives in that environment's workspace, and switching the default environment copies it over the new default's while the service's calls are held; the inbound webhook URL belongs to the service, not to any environment, so callers, stored state and incoming webhooks move together.** Concretely:

- **Never asleep.** Both idle timers are skipped for the default environment. If its pod is down anyway (crash, restart, node drain), the Gate wakes it with `ensureEnvironment` and holds the call for up to 60 seconds, then answers `504`; the platform's own form calls and hooks answer `503 service-starting` with `Retry-After: 5` instead. Non-default environments, which only test calls reach, wake on demand and sleep as usual.
- **State in the environment's workspace.** The service pod keeps `ctx.state` itself, in the SQLite file `data/service-state.db` of its ProjectEnvironment's workspace (rollback journal, since the volume is shared), so every environment, Development included, has its own; `data/` is never committed, so a Publish never carries Development's into a published environment. The SDK opens the file for each operation, so a file the platform replaces or deletes is never read through a stale handle.
- **A switch quiesces the service, then copies.** Switches of one service run one at a time under a Postgres advisory lock. The platform refuses its own new calls to the service's Default lane (form calls, hooks) with `503 service-reloading` and `Retry-After: 2`, while the Gate's answer to a caller or an incoming webhook waits for the hold to end and is then routed to the new default, because a sender such as GitHub does not redeliver: one whose hold outlasts the Gate's 60 s hold is answered `504`. The switch waits up to 30 s for the calls already dispatched to the old default to finish (else the switch answers `409 service-busy` and nothing changes), copies the old default's file over the new default's with `VACUUM INTO` a staged file that is synced and renamed into place, moves the default, and lets calls through again. Nothing writes either file meanwhile: the old default has no call in flight, the new one serves the service only from the moment the default moves, and a platform call routed to the old default before the switch but dispatched after it is refused with `503 service-reloading` rather than run there. After a switch from Production to Staging, Staging sees the Trello webhook ids Production registered and does not register them again; switching back copies Staging's over Production's the same way, and an old default with no file leaves the new one empty.
- **An environment-free webhook URL.** A Custom service receives webhooks at `/api/external-services/webhooks/<external_service_id>` on the platform's host ([ADR-0084](0084-an-external-service-delivers-its-events-to-the-projectenvironments-it-chooses-and-the-platform-keeps-them-and-wakes-the-app.md)), so registrations made upstream stay valid across a switch and incoming events follow the default.
- **A switch is a Publish for consumers.** The switch dialog shows the same impact report as Publish (ADR-0079), Available is checked again against the new default's Service form, and only published non-Development environments can be chosen.

## Considered options

- **Waking on demand only, as Apps do.** Rejected: every cold start loses webhooks from senders that do not retry, and an unattended Schedule pays the start-up time on every quiet week.
- **Answering `503` at once and waking in the background, as the proxy does.** Rejected for the same lost webhooks.
- **A store per environment with nothing carried on a switch.** Rejected: after a switch the new default holds none of the upstream registrations, registers them again, and the outside system delivers every event twice.
- **Copying while the old default keeps serving.** Rejected: a write after the copy is lost, and a write into a file being replaced lands on the unlinked one.

## Consequences

- Every published, enabled Custom External Service costs one always-running pod; there is no Organization limit on them in v1.
- Disabling the service's Project is the way to stop that pod, and it stops the service.
- A switch makes the service briefly unavailable: callers wait, and the platform's own calls get `503 service-reloading`, for as long as the in-flight calls take to finish and the file takes to copy. The hold and the in-flight count live in the backend process, which runs as one replica.
- `ctx.state` goes with the workspace: its size is bounded only by the environment's storage, deleting the service's Project removes it with the environments' folders, and a built-in, which runs in the platform with no Project, has none.
