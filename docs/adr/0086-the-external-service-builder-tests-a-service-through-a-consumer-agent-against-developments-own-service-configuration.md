# The External Service Builder tests a service through a consumer Agent, against Development's own Service configuration

A Custom External Service exists to be used by other agents and Apps, through docs its author wrote (the Service skill and `GET /.well-known/opsiforce`, [ADR-0082](0082-an-external-service-declares-the-routes-it-serves-in-its-own-code-and-agents-learn-it-from-an-authored-skill-and-the-service-itself.md)) and through the clients those callers already use (curl, gh, git, an SDK). The Gate forwards their calls untouched, so the service's own Service policy is the only thing deciding what passes ([ADR-0046](0046-an-external-service-owns-its-api-and-its-service-policy-the-gate-only-identifies-the-caller-finds-the-service-and-forwards-the-call-untouched.md)). The External Service Builder wrote the docs and the policy, so its own reading of them proves little ([ADR-0063](0063-the-builder-tests-a-child-agent-by-conversing-with-it-in-one-throwaway-project.md)'s argument). Development runs in the builder's own pod, and the Organization's one Service configuration is what every published environment reads.

**The External Service Builder tests a service from three sources: policy unit tests for every pass-through group, its own calls to the Service host as its chat's Test Project, and at least one conversation with the Test Project's consumer Agent. The Test Project's calls reach the service's Development, which reads its own Service configuration and receives webhooks at its own address, and both reach only that Test Project. Live upstream calls are opt-in, and writes reach only targets the author named in the Test Project's Project configuration. The Publish dialog shows the test report and the builder's Publish note, fills any Service configuration field the new version needs before callers see it, and blocks only when Development fails the platform's two probes of the SDK's guard ([ADR-0046](0046-an-external-service-owns-its-api-and-its-service-policy-the-gate-only-identifies-the-caller-finds-the-service-and-forwards-the-call-untouched.md)).**

## Testing

- **The Test Project.** One per builder chat, created and refreshed by the ADR-0063 mechanics, on App Builder or a Custom Agent the brief names. Its calls to the service's Service host reach Development; every other caller reaches the Default environment (External Service). Its Project configuration for the service is created with it, which gives it the Service skill whatever its Agent carries ([ADR-0082](0082-an-external-service-declares-the-routes-it-serves-in-its-own-code-and-agents-learn-it-from-an-authored-skill-and-the-service-itself.md)), and its Service skill is Development's.
- **The builder's own routes.** The builder has no Public API. It works through `$SERVICE_GATEWAY_URL/_builder` with its pod's Gateway Key, answered only for the pod of the service's own builder chat: the service's slug, Service host and Webhook address (read live, since the slug can change until the first Publish), Development's empty required Service-form fields, the Test Project and its Gateway Key; create, Update and Reset of the Test Project; reading and saving the Test Project's Project configuration to set up a scenario; form calls as the Test Project (Project form and Service form); and the Test Project's `events`. Setting a Project's External Service configuration stays out of the Public API, where every Agent Caller could be given it.
- **Unit tests** (the SDK test kit: a fake caller, a fake upstream, memory `ctx.state`) run on every change. For every pass-through group: one request allowed and one refused for each setting that governs it; every filtered list; every narrowed request; one request outside every group answers *not supported*; each refusal names its setting. They do not assert the upstream's answer shapes, which a proxy passes through untouched. The SDK's own refusals of not-connected and incomplete callers are the SDK's tests, not each service's.
- **The builder as the Test Project.** With the Test Project's Gateway Key, the builder calls the Service host with the clients the brief names (curl, gh, git), exactly as a consumer would, and replays the allowed and refused cases live before it involves the person. Its calls are the Test Project's calls.
- **Conversation.** At least one prompt written like a user's, which the person sends in the Test Project's pane beside the chat: only an agent that did not write the Service skill shows whether the skill, `/.well-known/opsiforce` and the refusals are enough to work from.
- **Evidence.** Rows in Development's Call log ([ADR-0092](0092-an-external-service-keeps-its-own-call-log-and-usage-and-the-platform-only-reads-them.md)) by request id, unit test output and `events` rows; never the consumer's prose. Otherwise ADR-0063's loop: expectations written first, prompts word for word, one source per verdict line, stop after two rounds that turn no failure into a pass.
- **Update and Reset.** Update (Test Project) delivers the Service skill again from Development; `/.well-known/opsiforce` and the Service configuration are live already. Reset (Test Project) also empties its `events`, deregisters Development's webhooks through the save hook and deletes Development's `ctx.state`; Development's Call log and Usage stay, since the last test report points into them.

## Development's own Service configuration and webhooks

- **Two Service configurations for a Custom External Service.** One is read by every published environment, the other only by Development. It starts empty or from an explicit "Copy from Production", secrets sealed again. Publish never copies it. Built-in External Services have one; they have no Development.
- **Development's Webhook address**, `/api/external-services/webhooks/<external_service_id>/development/…` on the platform's host, is matched only against the builder chat's Test Project: Development delivers Events only to it ([ADR-0084](0084-an-external-service-delivers-its-events-to-the-projectenvironments-it-chooses-and-the-platform-keeps-them-and-wakes-the-app.md)). The builder replays recorded payloads by posting to it, signed with Development's own secret. Before the first Publish it is the only address that receives anything.

## Live calls

- Upstream calls happen only once someone fills Development's Service configuration. Without it, every live line is *not checked*.
- Reads run against whatever it points at. Writes reach only targets the brief names: the Test Project's Project configuration holds only those (`repositories: [acme/sandbox: write]`), so the service's own policy refuses everything else, which the live refusal lines prove. A destructive call acts only on what the same round created. No named target: write and destructive lines are *not checked*, with that reason.

## Publish

- `yarn external-service-cli report` writes `/workspace/.cache/service-test-report.json` (commit, manifest hash, lines with result, source and request ids from Development's Call log), refusing a malformed one. The Publish dialog reads it from Development's files and shows it beside the route-table and skill diffs and the [ADR-0079](0079-a-changed-service-manifest-reads-old-configurations-tolerantly-and-a-publish-writes-each-new-fields-default-into-them.md) impact report: counts, "Changed since the test: `src/groups/merge.ts`", "Not tested", "Never called the real upstream". It warns, at the top of the dialog, and never blocks.
- The builder writes a Publish note with every version, as `app/PUBLISH.md` in plain Markdown. It says what changed and, for each new or changed group, what that group lets through and under which setting. It also names the outside system's own protections the person set up, or that it has none. The dialog shows the note first, warns when it is missing, and offers the collapsed code diff of `app/` between the Default environment's commit and Development's.
- The dialog lists every field the new Service form requires that the Service configuration callers use lacks, with inputs and a per-field "Copy from Development" off by default. Publish stays disabled until that configuration validates, and the values are saved with the Publish. The first Publish is the same dialog with every field listed.

## Considered options

- **The builder's own calls alone, with no conversation.** Rejected: nobody reads the delivered docs with a context that did not write them.
- **Only the consumer Agent sends live traffic.** Rejected: every allowed and refused case costs the person a prompt, and a refusal the builder could replay with one curl waits on a conversation.
- **A path-prefixed forwarding probe on the builder's routes, with a backend-signed identity for the Test Project.** Rejected: it serves curl only; gh and git need the Service host's root, which is exactly what has to be proven.
- **Giving the builder the Public API instead of its own routes.** Rejected: saving a Project's External Service configuration would become a Public API power that any Agent Caller could be given.
- **One Service configuration shared by Development and the published environments.** Rejected: saving through Development's form rewrites a `was`-renamed key, the published code finds its field missing and every consumer is refused as incomplete before anything is published; a Rotate while testing rotates what callers use.
- **A Service configuration per environment, carried forward by Publish.** Rejected: it carries a test login's credentials over the ones callers use.
- **Vitest and MSW in the template.** Rejected: two more dependencies in every vendored service, and the SDK's caller and configuration handling re-implemented as mocks.
- **Only live tests, no kit.** Rejected: slow, spends upstream calls, and cannot reach paths such as Trello's `429`.
- **Fakes only, never the real upstream.** Rejected as the only option: fakes encode what the builder believes about the API. Trello's `HEAD` check of a webhook callback URL, its `key`/`token` query parameters and gh's `/api/v3/meta` check would surface first in Production.
- **Tests asserting the upstream's answer shapes.** Rejected: a proxy passes the answer through, so they test the fake upstream and grow without catching a policy bug.
- **Replaying webhooks only, through a dry-run endpoint that stores nothing.** Rejected: the save hook's upstream registration and the doorbell into an App would go untested until Production.
- **Asking the human before every live write.** Rejected: it trains the human to approve unread.
- **Blocking Publish on a missing or stale report.** Rejected: a one-line fix would cost a full round, and the person publishing holds the decision.
- **Publishing first and filling new fields afterwards.** Rejected: the service stops being Available and every consumer is refused until someone does.
- **Filling new fields ahead of Publish in the configuration callers use.** Rejected: a second place to do the dialog's job that nobody knows to visit.

## Consequences

- A builder chat with Development's Service configuration filled holds working upstream secrets in the builder's pod, which is why building requires `can_manage_tenant_external_services` ([ADR-0078](0078-an-external-service-fetches-its-configurations-from-the-backend-by-the-caller-identity-and-holds-them-only-in-memory.md)).
- The builder holds its Test Project's Gateway Key, which also reaches the Default environment of any other service that Test Project connected.
- A provider that allows one webhook URL per app (a GitHub App) needs a second app for Development.
- Test calls are ordinary rows in Development's Call log.
- A non-default published environment, reached only by test calls, reads the Service configuration callers use.
