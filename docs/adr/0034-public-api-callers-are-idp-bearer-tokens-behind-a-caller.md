# Public API callers authenticate with IdP bearer tokens through oauth2-proxy, modelled as a per-request Caller

Status: accepted (2026-09-10) — the guard shipped on `feature/public-api`; amendments below

The public API needs machine authentication on day one, and the platform has no credential store of its own: identity comes from the deployment's IdP through oauth2-proxy, which already accepts bearer JWTs (`--skip-jwt-bearer-tokens`) and forwards user, email and groups as headers on every backend request. Building platform-issued API tokens first would add a table, hashing, scopes, a UI and a freshness problem before a single consumer exists.

v1 therefore accepts **the IdP-issued bearer token** on `/api/v1/*` and nothing else: zero new storage, the same headers as the browser path, so the caller holds exactly the Organization memberships and permissions they have in the UI. Two oauth2-proxy flags make the path deterministic: `--api-route=^/api/v1/` so a missing or expired token is a 401 rather than a login redirect, and a skip-auth rule for the unauthenticated `GET /api/v1/auth/config`, which tells a client the mode, issuer and client id to use. In standalone `static` mode the API is anonymous-admin, network-trusted like the rest of that mode.

Controllers never read those headers. A `PublicApiGuard` builds a **`Caller`** per request — in memory, no storage — with a `source` discriminator (`idp-bearer` today), the user (kind `user` or `service-account`, detected by Keycloak's fixed `service-account-` username prefix), the selected Organization, the caller's Organizations and their permission set. Reused domain services keep taking their existing tenant and user contexts, derived from the Caller by two helpers, so the domain layer does not change. `Caller.user.id` is the IdP subject; the platform user id is what `/me` returns.

The Organization is selected with the **existing `x-tenant-name` header**, implicit when the caller belongs to exactly one, a 400 listing the choices when several and none named, one indistinguishable 403 for a wrong or unknown name. The existing tenant and permission guards ride unchanged; the public guard runs after them and adds the entry permission `can_use_public_api` (admin bundle by default), the multi-Organization strictness, and the service-account rule: service accounts get no Personal workspace and their Projects default to Public placement.

## Considered options

- **Platform-issued API tokens now.** Deferred to the map's fog: storage, scopes and revocation are a full effort, and nothing forces them before the CLI has exercised bearer auth.
- **A new `X-Organization` header.** Rejected: a second wire vocabulary for the one thing the UI already sends; header names are wire vocabulary, not user-facing copy, so the glossary's "never say tenant" rule does not bite.
- **Opting the public routes out of the global guards.** Rejected: duplicates tenant resolution for no gain; the public guard only tightens.
- **Naming the object `Principal`.** Rejected: framework jargon; `Caller` says what it is and survives later kinds (API token, pod gateway key).
- **No entry permission.** Rejected: adding one later breaks every token holder; starting with it and granting it to admins costs nothing.
- **Mirroring Makara's token relay.** Rejected: a different product's constraint, not ours.

## Consequences

- Every Keycloak client that issues tokens for the API needs an audience mapper; that is deployment configuration, not code.
- Service accounts become first-class users on their first request without a Personal workspace, which changes `getOrCreateUser`.
- Later caller kinds extend `source` and add a guard; controllers stay untouched.
- A standalone deployment that wants an authenticated API runs `oidc` mode against its own IdP; there is no broker in standalone.

## Amendments

- **`can_use_public_api` gates the platform API only.** Since [ADR-0038](0038-chat-is-native-opencode-through-the-runtime-proxy.md), chat is native opencode reached through `/api/proxy/{environmentId}`, and that path is gated by Organization membership and per-user Project visibility — identical for a browser and for a program, and unable to tell them apart. A caller without `can_use_public_api` cannot call `/api/v1`, but if they can open the Project in the app they can reach its runtime, because it is the same door. Runtime access is environment-level: filesystem and shell operations, session mutation, model switching and integration or credential operations, not prompt-only access.
- **Two internal exception subclasses.** The public filter has to turn a guard's denial into the right Error — `organization-forbidden` for a tenant refusal, `permission-denied` (naming the permission) for a missing one — and both guards raised a bare `ForbiddenException` whose only distinguishing mark was its message. Rather than match on message text, `TenantAccessDeniedException` and `MissingPermissionException` were introduced as subclasses that carry the fact. Both extend `ForbiddenException` with the same status and message, so the internal API's wire shape is unchanged; only the public filter reads the new type.
- **`can_delete_project` gates both surfaces.** The decision only added the entry permission `can_use_public_api`. Deleting a Project had no permission of its own — the internal route was gated by ownership alone — and a public delete needed one. The new constant was applied to the internal delete route in the same change so the two surfaces cannot drift.
- **`GET /api/v1/auth/config` is removed (2026-09-11).** The amendment below had kept the route as a constant `static` answer with a reserved shape. Nothing consumed it, the constant told a client nothing the deployment did not already tell it, and it was the only unauthenticated route, which meant a `@Public()` exemption, an oauth2-proxy skip-auth rule and a four-file sub-module for one literal. All of that is gone; a client discovers its IdP from deployment configuration. The route was never published outside `feature/public-api`, so the compatibility policy does not bind. Should an `oidc` branch return, it comes back as a new additive route under the policy.
- **The platform user is resolved once, in the guard.** The decision had controllers derive tenant and user contexts from the Caller through two helpers and resolve the platform user in a service each route called; in practice the helpers were never used and the upsert ran on nearly every request, sometimes twice. `PublicApiGuard` now performs the single `getOrCreateUser` and `Caller.user` carries both `id` (the IdP subject) and `platformId`; the helpers and the resolving service are deleted.
- **`auth/config` reports `static` unconditionally; the two CLI env vars are gone** (superseded above). The decision had `GET /api/v1/auth/config` read `PUBLIC_API_ISSUER_URL` and `PUBLIC_API_CLI_CLIENT_ID` and switch between `oidc` and `static`. Nothing ever set them: no deployment configured a value, and [task 12](../../.scratch/public-api/issues/12-task-keycloak-clients-for-cli-and-bot-in-local-realm.md) deliberately left the CLI and service-account Keycloak clients unprovisioned, so the `oidc` branch was unreachable and the route advertised a client id that did not exist. Both variables and their Helm wiring were removed and the service now returns the `static` constant. **The response schema is unchanged** — `mode` keeps both enum values and `issuer`, `clientId` and `grants` stay in the shape, nullable and empty — because the compatibility policy forbids removing or retyping a published field, and because restoring the `oidc` branch should be a change to one service, not to the contract. The route itself stays: it is the only unauthenticated route, and telling a client whether this deployment expects a token is worth a call whatever the answer is. Token *acceptance* was never governed by these variables; that is oauth2-proxy's `--skip-jwt-bearer-tokens`, which is unaffected.
