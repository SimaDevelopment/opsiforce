# The Public API is a Built-in External Service that `/api/v1` itself serves, and pods reach it only through its Service host

A pod acts on the platform as its Project's creator ([ADR-0062](0062-a-pod-calls-the-platform-api-as-the-human-who-created-its-project-bounded-to-what-it-created.md)). A key that let a pod call `/api/v1` on its own would be a second door beside the Gate, all or nothing per Agent and invisible in the Call log, and nothing would say what that Project's people meant its pod to do. An External Service enforces its own Service policy behind a Gate that only identifies the caller and finds the service ([ADR-0046](0046-an-external-service-owns-its-api-and-its-service-policy-the-gate-only-identifies-the-caller-finds-the-service-and-forwards-the-call-untouched.md)), so the Public API's policy belongs beside the routes it guards.

**The Public API is the Built-in External Service `public-api` ("Opsiforce Public API"). A pod calls `/api/v1` paths as they are on its Service host, `public-api.external-services.<base>`, with its ordinary Gateway Key; the Gate forwards the call into the backend, `PublicApiGuard` takes the Caller identity as the pod's credential, and the service's policy beside the routes reads the caller's Project configuration.** Concretely:

- **In the backend's process, no pod.** The Gate forwards `public-api`'s caller lane into the backend through the adapter that also serves incoming email and WhatsApp, with a Caller identity the backend signs with a key of its own, since there is no pod key to sign with. A pod-hosted Public API would need a credential carrying the creator's platform authority in its environment, which no service code is given.
- **The Caller identity is the credential.** `PublicApiGuard` takes it as a second source beside IdP bearers: it checks the signature with the built-ins key, the expiry and that it was made for `public-api`, then resolves the creator as ADR-0062 says. The calling pod never sees it, and the main host's edge removes incoming `X-Opsiforce-*` headers as the Gate does. A pod's `gw-` key answers 401 on `/api/v1`.
- **Routes open by decorator, and the default is deny.** One decorator per route, `@ServiceRoute`, carrying the route's summary and `allowedBy` (the Project-form fields that govern it), opens it to a pod. A route without one answers *not supported* to a Caller identity, so a new route stays closed until someone opens it on purpose. The decorated routes are the service's Service routes, and `/.well-known/opsiforce` is built from them.
- **The Project form says what kind of work a pod may do.** Having a Project configuration connects the environment, and a connected environment may read. Five fields, all off in a new configuration: *Edit Agents and Skills* (create, duplicate and version Skills; edit Agents, their profile, template and skills), *Create Agents*, *Create Projects* with *Created Projects limit* (5), *Manage created Projects* (connect, restart, and update or reset a Test Project) and *Delete created Projects*. Which rows stays containment's (ADR-0062). A refusal is the API's own problem answer naming the setting and who may change it. No field picks Projects: containment already limits a pod to the Projects it created.
- **The cap counts what exists.** *Created Projects limit* counts every Project whose `created_by_project_id` is the calling Project and that still exists, of any kind and whether disabled or not; only a delete frees a slot. At the cap `POST /projects` answers `409` ("This Project may create at most 5 Projects … ask someone who can configure this Project's External Services to raise it"). The depth-two chain limit and the Organization's Projects limit stay platform rules.
- **The runtime door reads the same configuration.** The runtime proxy at `OPSIFORCE_RUNTIME_PROXY_URL` keeps accepting a pod's key for a Project it created, and only while the caller's `public-api` configuration has *Manage created Projects* on: the backend is this service, so this is its own policy reading its own configuration.
- **A builder chat is configured when created.** The Builder writes a new `skill-agent-builder` chat's `public-api` configuration before its first delivery: *Edit Agents and Skills*, *Create Projects* (5) and *Manage created Projects* on, *Create Agents* and *Delete created Projects* off, a list kept beside that code rather than in `agents.json`, which also gives the chat `service-public-api` from its first message. Any other Project sets its own.
- **Recorded like any service, by the backend.** Every request with a Caller identity is a Call log row and counts in Usage, written by the backend into tables kept for Built-in External Services only and read in the same shape as a pod's ([ADR-0092](0092-an-external-service-keeps-its-own-call-log-and-usage-and-the-platform-only-reads-them.md)); Usage adds `projects_created` and `skill_versions_published`. Human calls to `/api/v1` are not recorded.
- **Humans call `/api/v1` directly.** IdP bearers call it with `can_use_public_api`; `/api/v1/openapi.json` and `/api/v1/docs` stay public and describe the same paths a pod calls. `skill-agent-builder`'s scripts call paths (`api.sh POST /projects`), and the `service-public-api` Service skill teaches the API, its docs and how calling it from a pod differs.

## Considered options

- **A pod running the Public API like a Custom External Service.** Rejected: it would call `/api/v1` with a credential carrying the creator's authority inside a pod, run an always-on copy in every deployment, and keep in `ctx.state` the provenance the database already holds.
- **A route table written in the service's folder, or one catch-all route.** Rejected: a table drifts from the controllers, and a catch-all opens every later route, administrative ones included.
- **One switch per route.** Rejected: a Project decides what kind of work its pod does, and containment decides which rows.
- **A field picking the Projects a pod may see.** Rejected: narrowing among Projects created on the fly picks nothing, and naming other Projects would undo containment.
- **A call token for every service.** Rejected: hands a tenant's code the creator's platform authority.

## Consequences

- The upgrade maps every stored `public-api` configuration's Operation switches to the five fields once, a field on when any of its Operations was on and *Created Projects limit* at 5, and drops the switches; the boot pass delivers the Service skill to environments missing it.
- Nothing carries the Public API to a Custom Agent: it reaches one only when an editor adds `service-public-api` on the Agent page and its Projects connect `public-api`.
- Skills and Agents a builder chat created before the upgrade have no `created_by_project_id`; only their own builder chat (as subject) can write them.
- The Public API's Service manifest declares only its identity and its Project form.
