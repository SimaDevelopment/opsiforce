# Backend tests are grouped by area under `test/`, and test-only code never lives under `src/`

Status: accepted (2026-09-10) — decided on `feature/public-api`; the move lands as its own commit on that branch

The backend's fifteen test files sit flat in `backend/test/`, distinguished only by a filename prefix — eleven of them begin `public-api-`. The prefix is doing a directory's job. The obvious fix is the one NestJS's own docs prescribe, "keep your test files located near the classes they test", and it does not fit: eleven of the fifteen files import from two to four different `src` areas, and two import from none at all. `public-api-session-write.test.ts` enters at `POST /v1/projects/:id/session/prompt` and lands in `src/project`, `src/project-environment` and `src/pod`; colocating it means picking one of three arbitrarily. **Zero of the fifteen are unit tests.** Twelve boot a Nest testing module over a real Postgres, and the other three test the harness itself, the module graph, and the frozen chat schemas against recorded payloads. The suite was deliberately keyed to *boundary* rather than to module ([testing.md](../development/testing.md)), so a layout keyed to source-file location would be describing the wrong thing.

Tests are therefore grouped **by area under `test/`**, one level deep, and a subdirectory appears only when an area has three or more test files. Today that means one directory: `test/public-api/` holds eleven files with the prefix dropped, while `agent-session`, `domain`, `fake-pod` and `module-graph` stay flat at `test/` until they multiply. Helpers follow the same rule one level down — the six reachable only from public-API tests move to `test/public-api/support/`, leaving `test/support/` holding the nine that are genuinely cross-area, so the directory becomes an honest claim rather than a bag. Fan-in decides membership, not taste, and it is **transitive**: `app.ts` is imported by ten test files and all ten are public-API; `project-fixtures` and `fake-pod` are pulled in by `agent-session.test.ts` too, so they stay central; and `proxy-identity` stays central despite every *direct* importer being a public-API test, because `project-fixtures` imports it and `agent-session.test.ts` imports that. A helper belongs to an area only if nothing outside the area can reach it. Recorded fixtures stay at `test/fixtures/opencode/`, tied to the opencode pin and its bump runbook rather than to any test.

**Test-only code never lives under `src/`.** A colocated `*.test.ts` would in fact be safe today — `tsconfig.build.json` excludes it by the `**/*.test.ts` *pattern* — but helpers are excluded only by the `"test"` *directory* entry, and they import `vitest`, `@testcontainers/postgresql` and `@nestjs/testing`, all devDependencies that the production install (`yarn workspaces focus --production`) drops. An in-`src` helper would compile into `dist/` and ship in the image. Keeping the exclusion a one-word directory entry means it cannot be sidestepped by a filename, and it keeps the oxlint relaxation of `no-explicit-any` and `no-console` geographically visible instead of fenced only by glob. The corollary for future unit tests: when a test really is one-module-scoped, colocation beside its source file is permitted; its helpers still are not.

Naming stays `*.test.ts`, against the ecosystem's near-universal `.spec.ts`, because the repo already diverged and both are blessed by Nest. `nest-cli.json` gains `generateOptions.spec: false` so `nest g` cannot seed a `.spec.ts` sibling. **Fast and container-backed tests are not split.** Measured on the real suite: 15 files and 270 tests run in 71.8s; the three container-free files run in 12.9s, of which 95% is import and transform of the Nest module graph and 4% is assertions. The Testcontainers Postgres costs about 3s, identical whether three files run or fifteen. A Docker-free lane would buy three seconds, and no layout removes the thirteen.

## Considered options

- **Colocate every test beside a `src` module** (the framework's own advice). Rejected: for eleven of fifteen files the "module it tests" is two to four modules, and for two it is none. Each file's home would be less true than its current name.
- **Colocate only the genuinely unit-scoped tests, keep the rest flat.** Rejected as the *primary* rule because the set it governs is empty today — kept as the corollary above, so it applies the day a unit test exists.
- **Mirror `src/` as a deep tree** (`test/public-api/session/write.test.ts`). Rejected: `../../../src/…` imports, and a directory per file for the four singletons.
- **Path aliases (`@test/*`) to hide the depth.** Rejected: the repo has no `paths` anywhere, adding one means editing `tsconfig.json` and `vitest.config.mts` in step, and Nest documents the drift hazard. Two dots is not a problem.
- **Rename `support/` to `helpers/`, or split it into `harness/`/`fakes/`/`fixtures/`.** Rejected: "helpers" misdescribes a 415-line fake HTTP server and a Nest testing-module factory; a split by kind gives four directories for nine central files, several of which straddle two kinds, and re-deepens the imports we just declined to alias. `support/` is vague because the set is heterogeneous, which is the argument for it.
- **Split fast from container-backed via Vitest projects.** Rejected on measurement, not difficulty — see the numbers above. Verified in `vitest@5.0.0` source that the split is also *easier* than it looks: `initializeGlobalSetup` only initialises projects owning a queued spec (`node/core.ts:1274-1282`), so a non-root `integration` project's container start is both once-only and conditional, with no rewrite of the `setup/env.ts` seam. It is still three seconds.

## Consequences

- The restructure is a `git mv` plus one `sed` over 78 import lines and **no configuration change at all**: `include: ['test/**/*.test.ts']` is already recursive, `globalSetup`/`setupFiles` point at `test/setup/` which does not move, oxlint's test override is keyed on filename glob, and every helper filesystem path is a cwd-relative literal.
- The rule binds the whole opsiforce backend, not just the public API — the suite is already mixed, so a public-API-only rule would need an immediate exception. It does not bind the frontend.
- `test/support/` now means "used by more than one area". An import reading `../../support/…` versus `../support/…` says which kind of helper was reached for.
- Revisit the no-split decision when CI exists and needs a Docker-free lane, or when the container-free set passes about ten files. Not before.
- Suite speed is a separate concern with a different lever. The run is 88% waiting — deliberate 10s and 20s timeout assertions — and `fileParallelism` is off because all files share one Postgres, so overlapping those waits is the prize; `isolate: false` was measured at 3.2s of 72s and is not.
