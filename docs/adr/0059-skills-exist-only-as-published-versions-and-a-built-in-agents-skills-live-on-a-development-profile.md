# Skills exist only as published Versions, and a Built-in Agent's Skills live on a profile at the Development environment

[ADR-0051](0051-skill-catalog-append-only-store-tables.md) gave Skills an append-only draft layer — rows in `skill_versions` without a version number *were* the drafts — and put an Agent's Skills in a standalone `agent_skill_attachments` table with `pinned_version_id NULL` meaning track-latest. [ADR-0057](0057-authored-skills-and-agents-are-private-or-public-within-one-organization.md) then retired track-latest and the Attachment vocabulary, and [ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md) deleted the standalone table outright, hanging Skills off `agent_profile_skills(profile_id, …)` and removing versions from the agent side entirely. That left two holes this decision closes: a **Built-in Agent has no Agent Profile**, so ADR-0058's schema had nowhere to put the one skill set that still reaches existing Projects; and Skills were left as the only artifact in the platform still carrying a draft tier, inherited from a design that no longer exists around it.

**The Skill catalog stores published Versions and nothing else — the Builder conversation is the draft — and a Built-in Agent carries its Organization's Skills on a single Agent Profile parked at that Organization's Development environment.** Concretely:

- **No draft tier.** Three tables: `skills` (the mutable parent), `skill_versions` (immutable, integer-numbered, one per publish), `skill_version_files` (per-file content rows, path/content/size/binary — ADR-0051's decision 1, reconfirmed). There is no draft table, no draft file table, no draft columns and no NULL-means-draft row, so `skill_versions` means exactly one thing: frozen, validated, pinnable. **A Skill cannot exist unpublished.**
- **Saving is publishing, and the conversation holds the work in progress.** Authoring happens in a Skill & Agent Builder chat or the Store's form; the unsaved state lives there, exactly as ADR-0058 put an Agent's unsaved state in the Builder conversation or the form buffer. "I am happy with this" runs the validation gate and mints the next Version. A failed gate refuses the write and returns its errors to the conversation, which iterates — openwork's create-then-read-back-verify loop.
- **`skills.latest_version_id` is maintained in the publish transaction** and is the sole input to the **update available** state: an Agent's Skill shows it when its `skill_version_id` differs from the Skill's `latest_version_id`. Never computed from an author-typed field — the Claude Code plugin trap, where an unbumped `version` silently strands every consumer on a cached copy.
- **Upgrading a pin is explicit and per `(agent, skill)`.** No bulk upgrade and no "upgrade everywhere" in v1; Dify's workspace-wide plugin upgrade is the documented anti-pattern, and a bulk lever is auto-update wearing a human's hand.
- **Skills created inside an agent-authoring chat are ordinary Skills.** There is no agent-embedded kind, no `owner_agent_id`, and no second lifecycle. "Belongs to that agent only" is delivered by `visibility = 'private'` plus ADR-0057's coherence rule, which already refuses to put a private Skill on a public or Built-in Agent.
- **A Built-in Agent's Skills sit on one `agent_profiles` row per Organization, at the Environment with `is_default = true`** — Development, guaranteed to exist by `EnvironmentService.ensureDefaultForTenant`. `environment_id` stays NOT NULL, the profile gains no `tenant_id` and no `origin` column, and the Organization is read through `environments.tenant_id` exactly as for a Custom Agent. `prompt_body`, `model` and `variant` are NULL on these rows and ignored: a Built-in Agent's content is the image's.
- **That row is Organization-wide despite its Environment.** Its Skills reach every Project on that Agent in the Organization, on every Environment, because Built-in Agent content is re-supplied at delivery. The Environment is where the row is parked, not what it scopes.
- **Three guards keep the convention true.** **Publish (Agent)** is refused for a Built-in Agent — the only act that could mint a second profile row for one. The add- and remove-skill paths resolve Development themselves and never accept an Environment from the caller. And if the default Environment ever becomes settable, built-in profiles must move with it.
- **Built-in profiles are created lazily.** No migration and no backfill: a missing row means "this Built-in Agent carries no Skills here", which is true for every Organization on day one and for every one that never adds a Skill. The first add upserts the row; reads are a left join yielding the empty set. There are no Custom Agents to migrate — every row in `agents` today is a reconciled built-in.
- **Built-in Skills are global rows.** `tenant_id` is nullable on `skills`, NULL for `origin = 'built_in'`, under `CHECK (origin = 'custom' ⇒ tenant_id IS NOT NULL)` — the shape `agents` already has, reconciled once from the image rather than copied per Organization.
- **A Skill's `name` must be unique within one Agent's skill set**, refused at add time with the conflict named. opencode v2 resolves same-named skills by deterministic last-wins on directory name, with `skills[]` loaded after `.opencode/skills`, so a collision silently drops one of two Skills the UI still lists.
- **`forked_from` is dropped from `skills`**, following ADR-0058 dropping it for agents. **Duplicate (Skill)** produces a new private Skill whose first Version copies the source's files, and records nothing about where it came from.
- **`.skill` export is member-free**, gated only by the ordinary visibility read; **import** stays behind `can_manage_skills`. Export protects nothing the Store UI and the Project workspace do not already expose.
- **The API never names a profile.** `GET /agents/:agentId/skills`, `PUT /agents/:agentId/skills/:skillId` (add or re-pin), `DELETE /agents/:agentId/skills/:skillId` — the backend routes to the Development-parked row for a Built-in Agent and to the Development profile for a Custom one. The Environment appears only where it is a real choice: `POST /agents/:agentId/publish { environmentId }`.

## Considered options

- **Keeping ADR-0051's append-only Draft Revisions** — rejected: the restorable-checkpoint history it bought has no counterpart anywhere else in the platform now that agents have none, and it makes `skill_versions` mean two things separated by a NULL while `skill_version_id` is a pin that must never point at unfrozen content. The iteration history it preserved already exists, in better form, as the Builder chat transcript.
- **A single mutable draft slot per Skill** (Bedrock's DRAFT; ADR-0051 rejected it as a second write discipline) — rejected again, for the opposite reason: with the conversation as the draft, the slot would be a third place work-in-progress could live, and the two would disagree.
- **Two tables for an Agent's Skills** — a profile-scoped child for Custom Agents and an Organization-scoped `agent_skills` for Built-in ones. Rejected by the owner: the row, the API and the UI are identical, and ADR-0057's promise of one mechanism should hold in the storage too.
- **A nullable `environment_id` plus `tenant_id` and a denormalized `origin` on `agent_profiles`**, so NULL states "not scoped to an Environment". Rejected once the hazard it defended against was measured and found not to exist: nothing in the backend writes `environments.isDefault` — `create()` hardcodes `false`, `update()` has no such field, and only `ensureDefaultForTenant` sets it — and Development is seeded `isProtected: true`, which `remove()` refuses to delete. The option cost a nullable discriminator every Custom Agent query must exclude, a denormalized tenant with three sources of truth, and an extra column existing only to make a CHECK expressible.
- **Parking built-in profiles by backfill migration** rather than lazily — rejected: it writes `tenants × built-in agents` empty rows that carry no information and adds a provisioning step for every new Organization.
- **An `owner_agent_id` for agent-embedded Skills** — rejected: it buys hiding a Skill from a list only its creator can see, at the price of a second lifecycle. OpenAI's GPT Builder is the one surveyed product with a truly embedded model, and the competitor sweep records its lack of a reusable cross-GPT primitive as "a real weakness".
- **Allowing an Agent to pin a draft** — moot once drafts are gone, and rejected on its merits beforehand: ticket 18 found that every named pointer in the market sits on an immutable snapshot except dedicated *test* pointers. The test-pointer case belongs to [ticket 24](../../.scratch/agent-skill-platform/issues/24-builder-tests-child-agent-in-real-project.md), which ADR-0058 already licensed to introduce one.
- **Keeping `forked_from` on Skills** for Store lineage — rejected for symmetry with agents, accepting Flowise's documented failure mode (copies with no provenance that silently drift) as a cost that only bites in the marketplace case, which is out of scope.

## Consequences

- **Supersedes [ADR-0051](0051-skill-catalog-append-only-store-tables.md)'s clauses 3, 6 and 7** — append-only draft revisions, `agent_profile_versions` for agent content (already retired by ADR-0058), and the `agent_skill_attachments` table with track-latest pins. Its per-file content rows, name immutability, offline validation gate, one-shot import with provenance columns, and unbounded version retention all stand.
- **Supersedes two clauses of [ADR-0057](0057-authored-skills-and-agents-are-private-or-public-within-one-organization.md)**: its `forked_from` column on `skills`, and "Drafts follow the artifact" — a private artifact's drafts being creator-only is now a property of the Builder chat's own visibility, owned by [ticket 13](../../.scratch/agent-skill-platform/issues/13-builder-chat-profile.md). Its **Delete** clause loses its first limb: there are no never-published drafts, so Delete covers an archived Skill, refused while any Agent carries it.
- **Completes [ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md)'s schema** rather than changing it — the proposed tables are adopted verbatim, with the Built-in Agent's row placed inside them.
- **The Builder chat becomes durable storage, not a convenience.** It is now the only place unfinished Skill work exists, so losing a chat loses the work. [Ticket 13](../../.scratch/agent-skill-platform/issues/13-builder-chat-profile.md) owns resumable per-kind chat history and must decide it as a durability requirement.
- **Version numbers count deliberate acts.** Each is a human saying the Skill is ready, so "update available" stays a meaningful signal rather than firing mid-edit — the property that made dropping drafts safe.
- **No work-in-progress survives outside a conversation.** A Skill cannot be parked half-finished in the Store, and there is no form-only path to save without publishing. Accepted: the gate is what makes a Version trustworthy, and a Store full of unvalidated shells is the thing the gate exists to prevent.
- **A tripwire on the default Environment.** Making `environments.is_default` settable would silently strand every Built-in Agent's skill set at the old Environment while delivery kept reading it. Any change there must move built-in profiles with it.
- **One invariant carries the built-in side**: a Built-in Agent has at most one `agent_profiles` row per Organization and it is always at `is_default`. Repository-layer enforcement, the same place ADR-0058 put "only the Development row may be updated" — with overwrite semantics there is no immutable row for a database constraint to protect.
- **Glossary**: **Draft Revision** is deleted; **Agent Profile**, **Skill Version**, **Publish (Skill)**, **Duplicate (Skill)**, **Delete (Skill)** and **Skill & Agent Builder** are rewritten.
- This ADR has no home page under `docs/` yet; the feature is unbuilt, and the page is owned by the map's PRD ticket.
