# A Builder chat is private or public like everything else in the Store, and one gate enforces it on every runtime surface but the App

[ADR-0064](0064-builder-chats-are-kind-stamped-projects-prompted-by-their-creator-with-pods-that-never-destroy.md) derived a chat's reach from `kind IS NOT NULL` plus `created_by`: hidden by construction, with no way to share, which is why the Store's own copy had to say *"only the member who started one can open it"*. Verifying that guarantee on a live stack during [issue 45](../../.scratch/agent-skill-platform/issues/45-test-loop-end-to-end-verification.md) also measured the gate that was meant to hold it up: `ensureEnvironment()` ran its access assertion inside `if (surface === 'agent')`, so a tenant member who learned a chat's id reached code-server on its workspace (`surface=vscode` → 201) and its observability database (`surface=db` → 201). The Go proxy authorizes nothing of its own, so the backend was the only gate, and for three surfaces out of four there was none.

**A Builder chat carries the Store's own two-state visibility — `private` by default, `public` to the whole Organization — and the ensure hop applies one gate to every surface that arrives through the platform's identity proxy.** Concretely:

- **`projects.chat_visibility`, read only for kind-stamped rows.** The column sits beside `kind` and `created_by` rather than on a table of its own, mirroring `skills.visibility` and `agents.visibility`. It is `not null default 'private'`, so an ordinary Project carries a value it never consults: [ADR-0064](0064-builder-chats-are-kind-stamped-projects-prompted-by-their-creator-with-pods-that-never-destroy.md)'s reading still holds for those rows, where visibility is derived from `workspace_id` and `workspace_members`. The name says *chat* precisely because `project-visibility.ts` already means the workspace-derived thing.
- **Public means writable.** Two people prompting one chat is the point of sharing it, not a hazard to design around — a Builder chat is a working session, and a colleague who can read but not steer is not much use. Someone who does not want a second driver keeps the chat private. The UI is expected to make concurrency legible, not to prevent it.
- **Reversible, unlike a Skill or an Agent.** [ADR-0057](0057-authored-skills-and-agents-are-private-or-public-within-one-organization.md) makes widening one-way because a published version is already pinned inside other people's work. A chat publishes nothing by being shared, so nothing is stranded by un-sharing it, and the dialog says so in as many words — the difference from the Skill dialog has to read as deliberate.
- **The creator alone flips it, not `can_manage_agents`.** Sharing is a decision about your own working session; a permission that lets a colleague publish your half-finished chat is a different feature from the one being asked for. Every other verb the shared list already carried — archive, restore, delete — stays where [ADR-0064](0064-builder-chats-are-kind-stamped-projects-prompted-by-their-creator-with-pods-that-never-destroy.md) put it.
- **The test Project inherits, and is not separately flagged.** It exists only as the chat's current experiment, and a superseding create replaces it, so whoever may open the chat may open what it is testing. One SQL predicate resolves the governing row — a chat is governed by itself, a `test` row by its `created_by_project_id` — and every caller of it, the ensure hop included, reads that one answer. A test row's own `chat_visibility` column is never consulted, and because deleting a chat nulls its children's `created_by_project_id`, an orphan resolves to no governing row and stays private rather than falling back to itself.
- **One gate, every surface but the App.** The assertion moves out of the `surface === 'agent'` branch, `assertKindStampedCreator` becomes `assertKindStampedVisibility`, and tenant membership, `isProjectAccessible` and the chat predicate now run for `agent`, `vscode` and `db` alike. The runtime answers a refused caller **403** and the API answers the same caller **404**: [ADR-0064](0064-builder-chats-are-kind-stamped-projects-prompted-by-their-creator-with-pods-that-never-destroy.md)'s asymmetry is between the runtime and the API, not between surfaces.
- **The App surface is left to [ADR-0007](0007-per-environment-app-auth.md), because the ensure hop cannot honestly gate it.** The `vscode`, `db` and preview-app IngressRoutes target the proxy's oauth2-proxy port, so the forwarded identity on those hosts is written by the identity proxy. The apps hostname routes from Traefik straight to the app proxy, where `x-forwarded-user` is whatever the caller typed — a creator check there would be spoofable rather than protective, and requiring an identity at all would answer 401 to every `public` App in the product. Both hostnames arrive as `surface: 'app'`, so the exemption is by surface and therefore covers the preview host too, which does carry a real identity. Settled by the owner on 2026-09-21.
- **The proxy's ensure cache is keyed by identity on those surfaces too.** `handleSubdomain` passed an empty `authKey`, so one cache entry served every caller for the TTL and a per-caller decision would have been made once and replayed. It now hashes the same forwarded-identity headers `handleAgent` does. A gate the cache answers for is not a gate.

## Considered options

- **Extend the creator predicate to the other surfaces and stop there** — rejected: it fixes the measured hole while leaving the model with no way to share, which is the half of the complaint the code cannot express. The two halves are one decision because what the gate admits is exactly what the model says a non-creator may reach.
- **Gate the App surface on forwarded identity like the others** — rejected: it 401s every `public` App, and on the apps hostname the header it would trust is caller-supplied, so it buys the appearance of a control and not the control.
- **Put chats and test Projects behind `managed` App Auth so the App surface *could* be gated** — deferred: it closes the hole properly by giving those hosts a real identity, at the cost of a Traefik Middleware and IngressRoute per chat. Worth revisiting if a chat's App surface ever becomes a feature rather than an accident.
- **A separate `chat_visibility` table, or reusing `workspace_id`** — rejected: a chat is `workspace_id` NULL by construction ([ADR-0064](0064-builder-chats-are-kind-stamped-projects-prompted-by-their-creator-with-pods-that-never-destroy.md)), and a two-state flag that only ever has one row per chat is a column.
- **A read-only public state, so a colleague may read a transcript but not prompt it** — rejected, and it is the option [ADR-0064](0064-builder-chats-are-kind-stamped-projects-prompted-by-their-creator-with-pods-that-never-destroy.md) deferred. It needs a GET-only mode in the chat proxy, which is a new mechanism rather than a predicate on an existing one, and the owner's reason for sharing a chat is a second driver, not an audience.
- **`can_manage_agents` may share any chat** — rejected: the holder can already archive and delete one, but those are list hygiene, while publishing someone's unfinished thinking to their colleagues is theirs to decide.
- **A separate visibility on the test Project** — rejected: it is the chat's current experiment and nothing else, and two flags that must agree are one flag plus a bug.

## Consequences

- **Deferred on 2026-09-22: the gate runs on the `agent` surface only.** Widening it to `vscode` and `db` was reverted the day after it landed, because in local static auth mode nothing writes a forwarded identity on those hosts and the ensure hop answered 401 to the chat's own creator. The per-identity cache key in `handleSubdomain` went with it. Re-applying both, with the static-mode headers on every subdomain server block, is its own ticket.

- **Replaces one clause of [ADR-0064](0064-builder-chats-are-kind-stamped-projects-prompted-by-their-creator-with-pods-that-never-destroy.md), and leaves its status untouched.** "The list is shared; the transcript is not" becomes "the list is shared; the transcript is, when its creator says so". Everything else in that ADR — the kind-stamped carrier, the four listing sites, the pod's verb boundary, archive-is-`disabled` — stands, and its accepted gap that "a chat's transcript is unreadable by anyone but its creator" is now the private case rather than the only case.
- **Schema**: `projects` gains `chat_visibility` (`not null default 'private'`, checked `in ('private','public')`). Every existing chat comes up private, which is what it already was.
- **`ownHiddenProjectsWhere` becomes `reachableHiddenProjectsWhere`** and grows an `exists` on the governing chat. Five call sites had each written the creator-only rule out by hand — `isProjectAccessible`, `findOneUnlessHidden`, `getState`, the public API's `findOwnHidden`, and the ensure hop — and all five now ask `isHiddenProjectReachable` instead, so a sixth state would be one edit. That scattering is the same hazard [ADR-0064](0064-builder-chats-are-kind-stamped-projects-prompted-by-their-creator-with-pods-that-never-destroy.md) flagged for its four listing sites, arriving on the by-id paths.
- **`POST /builder/chats/:id/visibility`** joins the internal Builder routes, creator-only, both directions. The pod has no `/api/v1` route for it: widening is still a human act at a surface that renders the audience.
- **Whoever may open a chat may delete its test Project**, where that was creator-only. It is the reversible act the test loop performs on every run, and refusing it to a second driver would make a public chat unusable by them.
- **Accepted gap**: a chat's App surface is ungated on both the apps and the preview hostnames, so a member who learns a chat's id can reach whatever its pod happens to serve on the app port. The Builder template ships no `app/` and no go-live, so today that is nothing; a test Project whose child Agent builds an App is the case to watch, and the deferred `managed` App Auth option above is how it would be closed.
