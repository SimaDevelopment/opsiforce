# A Builder chat is a kind-stamped Project that belongs to one Skill or Agent, and who opens it follows that subject

The Skill & Agent Builder authors Skills and Custom Agents by conversation, and every piece of chat runtime (pods, keep-alive, the chat proxy, storage attribution, gateway keys) hangs off a Project. Authoring is not a workspace artifact, and an author comes back to the thing they are working on, not to a conversation.

**A Builder chat is a Project stamped with a `kind` that keeps it out of every list. It belongs to exactly one Skill or Custom Agent, its subject, and a subject has at most one chat. Whoever may see the subject may reach its chat, and the chat's pod may create and edit but never destroy.**

- **One Built-in Agent.** `skill-agent-builder` is one entry in `agent-config/agents.json` with `poolSize` 0 and `platformApi` on. The Agent picker never offers it ([ADR-0054](0054-built-in-and-custom-agents-share-one-agents-table-told-apart-by-origin.md)). A chat's `kind` is `skill_builder_chat` or `agent_builder_chat`, following its subject, and a Test Project is `test` ([ADR-0063](0063-the-builder-tests-a-child-agent-by-conversing-with-it-in-one-throwaway-project.md)).
- **`kind` is what hides it.** A chat and a Test Project have `workspace_id` NULL, which is the Organization-wide Public area. Nothing else on the row can conceal them, so every listing query filters on `kind IS NULL`, `visibleProjectsFilter` included.
- **The subject is named first.** New agent and New skill ask for a name and create the entry before the chat: an Agent with an empty Development profile, or a Skill with no Version. The link lives on the subject as `builder_chat_id` on `agents` and on `skills`: nullable, unique, and `on delete set null`. `POST /builder/chats` opens the subject's chat or makes one and claims it with a conditional update. When two first openings race, the loser's Project is removed. Opening needs the matching `can_manage_*` permission and a Custom subject the caller may edit. A disabled subject gets no new chat.
- **Reach follows the subject.** A kind-stamped Project is reachable by its creator, or by anyone to whom its governing chat's subject is visible. A chat governs itself, and a Test Project is governed by its `created_by_project_id`. One predicate, `isHiddenProjectReachable`, answers this for every by-id path. The runtime gate runs it in the proxy's ensure hop for the `agent` surface only. A refused caller gets 403 at the runtime and 404 at the API.
- **The pod asks what it is editing.** `GET /me` answers `builderSubject` for the gateway key of a chat's pod, so the Builder reads the live name and state. The backend never originates a prompt, and the chat opens empty.
- **The pod is bounded by verb.** It calls `/api/v1` as its creator through [ADR-0062](0062-a-pod-calls-the-platform-api-as-the-human-who-created-its-project-bounded-to-what-it-created.md)'s gateway caller. For Skills and Agents that means every artifact the creator may reach, but only the reversible acts: create a Skill, publish its Versions, duplicate a Skill, write an Agent's Development profile, add, remove and re-pin its Skills, and `PATCH` a display name or an Agent's description. Publish (Agent), making anything public, Disable and Delete have no gateway route and stay in the Store. The limit is by verb because a Skill Version that Agents across the Organization pin is not cheap to lose, and a Builder chat is where pasted documentation and fetched pages land. What the Builder creates is private to its creator.
- **A chat lives as long as its subject.** An Agent's chat holds the draft `template/` its Template is saved from ([ADR-0073](0073-a-custom-agents-template-is-a-folder-per-environment-copied-into-every-new-project.md)), so the product never deletes a chat on its own: the chat page and the Project kebab offer no Delete, and deleting the subject deletes its chat with its Test Projects. `DELETE /projects/:id` itself has no kind check. A chat is never duplicated or exported, because a copy would belong to nothing.
- **What ships in the image.** The Builder's prompt says who it is and how a conversation runs. Facts live in its skills: `platform`, `skill-authoring` and `agent-authoring`, plus the shared app-building skills, which it loads only to judge what a child gets. The template has no `app/`. It holds `scratch/`, the offline validator, the `.skill` packager and `scripts/api.sh`.
- **The test loop is documented shell.** `agent-authoring` keeps the exact `curl` calls in a reference file. The Builder records its Test Project's id in `scratch/`, because lists never show kind-stamped rows.

## Considered options

- **Two Built-in Agents, `skill-builder` and `agent-builder`.** Rejected. There is one artifact pipeline, so a split buys a list facet at the price of two prompts, two templates and two registry versions. `kind` buys the facet for one column.
- **A non-project chat runtime.** Rejected. It forks pod lifecycle, proxying, keep-alive and storage attribution to meet what is a presentation rule.
- **Chats as visible Projects in a workspace.** Rejected. Authoring is not a workspace artifact.
- **A user token in the pod's environment.** Rejected. A user credential would sit in LLM-readable env for the pod's life and need refreshing across suspends. The gateway key resolved to the creator gives the same authorization with no new secret.
- **Links on the chat row (`projects.subject_agent_id`, `projects.subject_skill_id`).** Rejected. Two nullable columns and a check on every Project, for a fact only the Builder reads. One column per subject table keeps uniqueness a plain index.
- **Creating the chat first and the subject on its first publish.** Rejected. An unfinished chat would have nowhere to be found but a list of chats.
- **Full creator authority over Skills and Agents from the pod.** Rejected. One injected instruction could delete the Organization's Skill catalog.
- **Scoping artifacts to the chat that created them.** Rejected. It breaks opening the Builder on an entry a colleague made.
- **In-chat Publish (Agent) or widen-to-public.** Rejected. Widening is one-way ([ADR-0057](0057-authored-skills-and-agents-are-private-or-public-within-one-organization.md)), and publishing overwrites an Environment's content ([ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md)). Both belong on the surface that shows the target and its audience.
- **A read-only transcript mode for colleagues.** Rejected. It needs a GET-only mode in the chat proxy, which is a new mechanism, and a colleague who may see the subject may already work in its chat.
- **A helper CLI around the test loop.** Rejected. Each thing it would buy is recoverable in documented shell, and it would tie the Builder's version to every change in the gateway allow-list.

## Consequences

- Every new listing query must filter on `kind`. One that forgets shows every author's chats and Test Projects to the whole Organization.
- The `vscode`, `db` and `app` surfaces do not run the reach gate. A member who learns a chat's environment id reaches its code-server and its observability database.
- A chat widens when its subject is made public, and never narrows on its own.
- A Skill the Builder creates for an Agent it is writing has no chat until someone opens the Builder on it.
- Storage attribution is unchanged: chats and Test Projects are tenant Projects and appear under their Organization in Admin storage.
