# A Custom Agent holds one definition per Environment, and a Project keeps the files it was created with

[ADR-0052](0052-custom-agent-anatomy-and-model-presets.md) gave Custom Agents integer versions in `agent_profile_versions`, a model-preset catalog, and an immutable Base Agent, and [ADR-0053](0053-dynamic-artifacts-delivered-by-direct-backend-write-plus-dispose.md) reached existing Projects by re-deriving content on mutation. The owner's 2026-09-17 redirection removed versioning outright: a Custom Agent has **Environments**, an author edits one and **publishes** to another, and a Project keeps the definition it was created with — nothing propagates. A field survey of nineteen systems (`.scratch/agent-skill-platform/research/agent-environments-and-snapshot-semantics.md`) found every named pointer in the market sitting on an immutable snapshot; this decision deliberately does not, because the *snapshot here is the Project's workspace*, which makes the database's copy redundant rather than authoritative.

**An Agent Environment is one of the tenant's existing Environment rows; a Custom Agent holds exactly one mutable definition per Environment; publishing overwrites the target; and a Project's durability comes from its workspace files, never from a database pin.** Concretely:

- **No parallel registry.** Agent Environments *are* the rows in `environments` — Development, Production, and any custom target an admin added (`backend/db/schema.ts:203`). One registry, one settings page, one vocabulary: Apps publish to Environments and so do Agents, disambiguated by object exactly as **Publish (App)** and **Publish (Skill)** already are. Environments are referenced by id and their names are display-only.
- **One definition per Environment, and Development is the editable one.** `agent_profiles` holds exactly one row per `(agent_id, environment_id)`. Editing an Agent is an `UPDATE` of its Development row; nothing is minted and no history accumulates. Publishing copies `prompt_body`, `model`, `variant` and the skill rows from Development onto the target row, **overwriting** whatever was there. With Development and Production, an Agent has two rows for its whole life.
- **No versions, releases, drafts, or snapshots in the database.** There is no version number, no internal sequence, no `is_current` flag, no append-only publication table, and no separate draft entity — Development *is* the draft, as it is in Bedrock, Lex, Dialogflow, Dify, Agentforce, Retool and n8n under that name. The unsaved state lives in the Builder conversation or the form buffer; Save is the write.
- **Snapshot-at-create is a delivery property, not a schema one.** A Custom Agent's content is written into the Project's workspace once, at creation, and **never re-derived** — not on pod recreation, not on Restart, not on Agent Updates. A Built-in Agent's content *is* re-supplied at delivery, so its Skills continue to reach that Organization's existing Projects. Because the workspace is therefore the sole record of what a Project runs, `projects` gains **no** column referencing a profile.
- **The default environment is per Agent.** `agent_settings.default_environment_id` names the Environment new Projects are created from, set by `can_manage_agents` ([ADR-0057](0057-authored-skills-and-agents-are-private-or-public-within-one-organization.md)), validated to belong to the Agent's tenant. Development is a permitted choice — the fast-iteration mode, where each new Project simply picks up whatever Development holds at that moment. `agent_settings` also carries `pool_size` (mirrored from the registry on boot) and is where later per-Agent knobs land.
- **Model is a validated pair, not a preset key.** A profile stores `model` and `variant` — the shape `agent-config/agents.json` already uses (`"openai/gpt-5.6-sol"`, `"high"`) — validated on save against `agent-config/models.json`: the provider exists, the model exists within it, and the variant is one of that model's `reasoning_options`.
- **No Base Agent and no fork lineage.** A Custom Agent is a persona over the platform's single agent chassis; `agent-config/agents.json` contains exactly one agent, so an immutable `base_agent_id` would be a column with one possible value. **Duplicate** copies an Agent without recording what it copied from.
- **Skills ride the profile in a child table.** `agent_profile_skills(profile_id, skill_id, skill_version_id)` serves the Development row and every published row alike, so publishing copies rows rather than serialising a blob. A child table rather than a JSON column because both hot reads are reverse lookups an index must serve: *which Agents carry this Skill* (ADR-0057's in-use refusal on **Delete (Skill)**) and *is a newer Skill Version available*.
- **Picker liveness has two clauses.** A Custom Agent is offered for new Projects when the caller's `visibility` allows it (ADR-0057) **and** a profile exists for its `default_environment_id`. Built-in Agents are always offered. Both clauses are net-new filtering: `AgentService.findAll()` and the public API's listing are unfiltered selects today.
- **Identity is never snapshotted.** Name, description, `visibility`, `created_by` and `archived` live on the `agents` row and are read live, so a rename or a private→public transition reaches every Project at once. Only behaviour — prompt, model, variant, Skills — is per-Environment.
- **Deleting an Environment is refused** while any profile references it or any Agent names it as a default, with the refusal naming them — the shape **Delete (Skill)** already uses.

## Considered options

- **Immutable publications with a pointer per Environment** (the survey's unanimous shape: Bedrock alias→version, Dialogflow environment→version, Langfuse label→version, Vercel domain→deployment, Claude Managed Agents' session pin) — rejected once content stopped being re-derived at delivery. Immutable rows, an ordering column, a current-row marker, reference-counted retention and a pin on `projects` all existed to let the database answer "what is this Project running"; the workspace answers it instead, and the remaining benefit did not carry five structures.
- **A separate `agent_environments` registry**, seeded Development/Production per Organization — rejected: it duplicates a registry the product already has and asks an Organization to configure two lists that would almost always agree. The accepted cost is that adding a custom App Environment also creates an Agent publish target.
- **Storing the editable definition on `agents` beside immutable profile rows** — rejected: `prompt_body`, `model` and `variant` would be declared twice and copied by hand, so every future column would have to be added in three places.
- **Model presets** ([ADR-0052](0052-custom-agent-anatomy-and-model-presets.md)) — rejected: the indirection means a frozen definition does not actually freeze its model, and the catalog is a second thing to maintain over `models.json`. Accepting the direct pair means a model leaving the catalog is a per-Agent fix with no central lever.
- **A stored `is_current` flag or a `seq` ordering column** — moot once publishing overwrites: there is only ever one row per pair, so there is nothing to order and nothing to mark.
- **Forbidding Development as a default environment** (the survey's position — only dedicated *test* pointers target a mutable draft, as in Bedrock's `TSTALIASID` and Lex's `TestBotAlias`, and Dialogflow's draft-auto-deploy carries an explicit warning) — rejected: with content written once at create, a Project created from Development is as durable as any other, so the hazard the survey documents does not arise here.
- **Keeping a pin on `projects`** — rejected: it could only point at a mutable row, so it would confidently report the wrong prompt for any Project whose Environment had since been republished. A field people trust and that is wrong is worse than its absence.

## Consequences

- **Retires [ADR-0052](0052-custom-agent-anatomy-and-model-presets.md).** Its `agent_profile_versions` append-only versioning, "live = highest published version", model-preset catalog and `model-presets.json`, and immutable base-anchoring are all gone. Carried forward unchanged: slugs are auto-derived kebab-case, unique per Organization, reserving every built-in registry slug, immutable once created; `pool_size` exists uniformly and defaults to 0 for Custom Agents; `archived` is the reversible end-state and hard delete exists only for never-published Agents.
- **Retires the agent half of [ADR-0053](0053-dynamic-artifacts-delivered-by-direct-backend-write-plus-dispose.md)** — no mutation-triggered sync reaches a Custom Agent's existing Projects. The Built-in-Agent half survives: a change to a Built-in Agent's Skills still propagates by delivery.
- **Retires the `forked_from` clause of [ADR-0057](0057-authored-skills-and-agents-are-private-or-public-within-one-organization.md) for Agents.** The Skill-side column is ticket 08's to keep or drop.
- **Publishing destroys the target's previous content.** There is no rollback of a published Environment and no copy of what it held: recovering a good prompt after a bad publish means retyping it or reading it out of an existing Project's workspace. Existing Projects are unaffected, so the blast radius is only Projects created between the bad publish and the fix. Accepted for v1 against the survey's pitfall #9 — bounded or missing history is *"cheap to keep and expensive to reconstruct"*, and Copilot Studio's absent agent history makes a support ticket the recovery path.
- **The database cannot answer what a Project is running.** No pin, so *which Projects are on the old prompt* and *group Projects by definition* are unanswerable without reading workspaces, and support on an old Project is workspace archaeology. Populating a pin later is non-breaking — a nullable column simply starts carrying a value.
- **Two questions are handed to [ticket 10](../../.scratch/agent-skill-platform/issues/10-pod-delivery-propagation.md)**, which owns delivery: whether the persona files sit inside or outside the workspace `.gitignore` boundary — inside, a **Publish (App)** carries them to the target automatically; outside, a published Environment receives none — and what Duplicate, Export and Import do with them, since an Export imported into another deployment carries files whose Agent does not exist there.
- **The schema above is a proposal to [ticket 08](../../.scratch/agent-skill-platform/issues/08-storage-scoping-lifecycle.md)**, which owns the physical storage model and may rename or merge tables. It may not change these semantics.
- **[Ticket 22](../../.scratch/agent-skill-platform/issues/22-agent-prompt-composition-and-platform-harness.md) gets simpler**: with no Base Agent there is one platform harness to generalise, not one per base. [Ticket 24](../../.scratch/agent-skill-platform/issues/24-builder-tests-child-agent-in-real-project.md) owns how the Builder tests unpublished content — the `TSTALIASID` case — and may reintroduce a frozen copy of Development as an explicit test mechanism.
- **One invariant carries the model**: only the Development row may have its content updated. Every other row is written only by a publish. Enforced in the repository layer, since with overwrite semantics there is no immutable row for a database constraint to protect.
- **Glossary**: **Model Preset** and **Base Agent** are deleted; **Agent Profile**, **Publish (Agent)** and **Default environment** are added; **Environment**, **Agent Model**, **Custom Agent**, **Duplicate (Custom Agent)**, **Agent Skills** and **Dynamic Delivery** are rewritten.
- This ADR has no home page under `docs/` yet; the feature is unbuilt, and the page is owned by the map's PRD ticket.
