# A Custom Agent holds one definition per Environment, and a Project keeps the files it was created with

An Organization authors Custom Agents, edits them, and publishes them to Environments without disturbing Projects that already run them. The question is what a Custom Agent is made of, and where the record of "what does this Project run" lives. Here the record is the Project's workspace, because the Agent's content is written there once at create. That makes a database copy redundant.

**A Custom Agent is an identity plus one mutable Agent Profile per Environment (instructions, Agent Model, Skills) and at most one Template per Environment. Publishing overwrites the target Profile and Template, and a Project's durability comes from its workspace files, never from a database pin.**

- **Anatomy.** The author writes the identity (display name, description) and, per Profile, `prompt_body`, `model`, `variant` and Skills, and per Environment at most one Template ([ADR-0073](0073-a-custom-agents-template-is-a-folder-per-environment-copied-into-every-new-project.md)). Nothing else is tenant-authored: the image behaviour, tool and permission posture, and the files a pod boots from besides the Template are the image's one `custom` package, shared by every Custom Agent ([ADR-0060](0060-agent-files-are-laid-once-and-shared-with-the-backend-by-ownership-list.md)). `prompt_body` is the whole agent body ([ADR-0061](0061-the-platform-harness-is-a-built-in-skill-and-an-agents-prompt-is-the-authors-body-alone.md)). A Custom Agent records nothing it was copied from; Duplicate creates a new private Agent with no link to its source.
- **Slugs.** The slug is derived from the display name as kebab-case, is unique within the Organization, cannot be a built-in registry slug ([ADR-0054](0054-built-in-and-custom-agents-share-one-agents-table-told-apart-by-origin.md)), and never changes. The display name and description can be edited.
- **Create.** A new Custom Agent is private, and gets a Development Profile with an empty prompt, the registry's default model (or the one given), and the `platform` Skill. An Agent may exist with an empty Development Profile.
- **Agent Environments are the Organization's Environments.** A Profile's environment is a row in `environments`: Development, Production and any custom one an admin added. There is no second registry. Apps and Agents publish to the same list, and the object tells the two senses of Publish apart.
- **One Profile per (Agent, Environment), and only Development is edited.** `agent_profiles` holds one row per `(agent_id, environment_id)`. Editing is an `UPDATE` of the Development row, and the service refuses to write content to any other row except through Publish.
- **Publish overwrites.** Publish (Agent) copies `prompt_body`, `model`, `variant` and the Skill rows from Development onto the target Environment's Profile, creating it if missing and overwriting whatever was there, and gives the target Development's Template. A publish that changes nothing is a no-op. Development itself is never a publish target.
- **No versions, drafts or snapshots in the database.** There is no version number, no sequence, no current-row flag and no publication history. The Development Profile is the draft.
- **The snapshot is taken at create.** The backend lays a Custom Agent's Template and writes its prompt and the Skills its Profile carries into the Project's workspace from its Default environment (Agent), or from Development for a Test Project, once, and never re-derives them: not on pod recreation, restart, Agent Updates, or a later edit or publish. What the image itself ships follows [ADR-0060](0060-agent-files-are-laid-once-and-shared-with-the-backend-by-ownership-list.md). `projects` holds no reference to a Profile.
- **The Default environment (Agent) is per Agent.** `agent_settings.default_environment_id` names the Environment new Projects are created from. It is never Development, which is the Builder's workshop, because a default there would hand ordinary Projects whatever the Builder saved last: a new Custom Agent defaults to Production and is absent from the picker until its first Publish (Agent), and Settings and the Publish dialog refuse Development. A holder of `can_manage_agents` changes it to any other Environment of the Agent's own Organization. `agent_settings` also holds the Agent's `platform_api` flag ([ADR-0062](0062-a-pod-calls-the-platform-api-as-the-human-who-created-its-project-bounded-to-what-it-created.md)).
- **The model is a validated pair.** A Profile stores `model` and `variant`, the same shape `agents.json` uses, and every save checks them against `agent-config/models.json`: the provider exists, the model exists within it, and a variant, when given, is one of that model's effort values.
- **Skills ride the Profile in a child table.** `agent_profile_skills(profile_id, skill_id, skill_version_id)` serves Development and published Profiles alike, so Publish copies rows. It is a table rather than a JSON column because both hot reads are reverse lookups an index serves: which Agents carry this Skill, and is a newer Skill Version available.
- **Identity is read live.** Name, description, `visibility` and `created_by` live on the `agents` row, so a rename or a move to public reaches every Project at once. Only behaviour (prompt, model, variant, Skills) and the Template are per Environment.
- **Deleting an Environment is refused** while any Profile sits on it or any Agent names it as its Default environment (Agent), and the refusal names those Agents.

## Considered options

- **Immutable published versions with a pointer per Environment.** Rejected: the rows, ordering, retention and a pin on `projects` would all exist to let the database answer "what is this Project running", and the workspace answers it.
- **A separate `agent_environments` registry.** Rejected: it duplicates a registry the product has and asks an Organization to keep two lists that almost always agree. The accepted cost is that a new App Environment is also an Agent publish target.
- **Free model strings, unvalidated.** Rejected: a model chosen apart from its config is the mismatch [ADR-0008](0008-agent-model-owned-by-agent-config.md) exists to prevent. The accepted cost is that a model leaving the catalog is fixed per Agent, with no central lever.
- **Letting authors set image behaviour, permissions or tools.** Rejected: those are fields the platform must own, and the author's part of every working agent design is prose, Skills and starting files.
- **A pin on `projects`.** Rejected: it could only point at a mutable row, so it would report the wrong prompt for any Project whose Environment was republished since.

## Consequences

- Publishing destroys the target's previous content. There is no rollback of a published Environment. Existing Projects are unaffected, so the damage is limited to Projects created between a bad publish and its fix.
- The database cannot answer what a Project runs. Grouping Projects by definition, or finding which run an old prompt, needs a read of their workspaces.
