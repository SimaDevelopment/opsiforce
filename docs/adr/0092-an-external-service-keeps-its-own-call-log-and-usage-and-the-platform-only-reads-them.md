# An External Service keeps its own Call log and Usage, and the platform only reads them

The Gate forwards a call to an External Service untouched and sees only its envelope: who called, which service, method, path, status, size and duration ([ADR-0046](0046-an-external-service-owns-its-api-and-its-service-policy-the-gate-only-identifies-the-caller-finds-the-service-and-forwards-the-call-untouched.md)). The envelope cannot say what happened. A `git push` the service refuses for a missing co-author is answered the way git expects, as `200` with `ng` lines, so a platform record of it reads exactly like a push that went through. Only the service knows which of its Service routes matched, whether it forwarded, answered or refused, and why. A service also decides for itself what else is worth counting — pull requests opened, cards created — and only its code sees those happen.

**The platform keeps no record of the calls an External Service receives and no count of what it did. The service's SDK writes one Call log row for every request that reaches it, the platform's own calls included, and keeps the service's monthly Usage, both in one file in the service's workspace; the backend reads that file whenever a screen shows them.** Concretely:

- **One writer, inside the pod.** The SDK writes `data/service-records.db` (SQLite, rollback journal, a fixed schema that is part of the service contract) beside `ctx.state` in the environment's workspace, for every request: Service routes, `GET /.well-known/opsiforce` and the `/.well-known/opsiforce/` form and hook calls alike. Service code can add fields to a row; it cannot skip one. The SDK removes rows older than 30 days.
- **What a row holds.** Request id, time, the Caller identity's kind, Project, ProjectEnvironment and environment, method, the path without its query, the matched route's summary or the handler's name, an **outcome** — `proxied`, `handled`, `not supported` (no route matched), `not allowed` (a route's policy refused) or `failed` (the service's code threw or its upstream did not answer) — the policy's reason, status, bytes in and out, duration, and the service's own fields. Never a header, a body, a query string or a person.
- **The backend reads, never stores.** It opens the copy's `data/service-records.db` read-only from the workspace volume, retrying a read that meets a write in progress, and shows a ProjectEnvironment only its own rows where a screen is about one. Who may see is the backend's existing read permission for each screen. The service needs no endpoint for it, and the screens work while its pod is asleep, starting or failing.
- **Where it is shown.** The service page shows a service's calls per environment (Default or Development); the Project configuration dialog shows a ProjectEnvironment its own. Nothing is woken to read them; the Default copy never sleeps anyway ([ADR-0083](0083-a-custom-external-services-default-environment-never-sleeps-its-state-lives-in-that-environments-workspace-and-is-copied-on-a-switch-and-its-webhook-url-belongs-to-the-service.md)).
- **Usage, beside it.** The SDK keeps, in the same file, one number per UTC month, Project (or none, for work no caller asked for), ProjectEnvironment and counter. Four counters are built in and cannot be turned off — `requests`, `not_allowed` and `failed`, counted from `call` requests only, and `events`, counted for each receiving ProjectEnvironment from the Events the platform stored for it. The rest the service declares in its code, each with a name, a label and an optional description, and increments with `ctx.count(name, n)` in a request or `service.count(name, n, { projectEnvironment })` outside one. A counter only goes up, is never used to enforce anything — a limit the service enforces lives in `ctx.state` — and keeps its past months under its last label after it leaves the code. Nothing is pruned.
- **Read like the Call log.** The backend reads, from the same file, the months that hold data, the counters with their labels, and one row of values per Project and ProjectEnvironment. Only the service page shows it, on a Usage tab with the same Default or Development switch and the same read permission as its calls; the Organization's Admin → Usage page and its permission go.
- **Built-in services, too.** A Built-in External Service has no pod, so its own in-process code writes the same counts into one backend table kept for built-in services only, and the backend answers the same shape for it.
- **Carried on a switch.** A Default-environment switch copies `data/service-records.db` with `ctx.state`, under the same hold.

## Considered options

- **Envelope rows kept by the platform, in Postgres or in the service Project's request log.** Rejected: they cannot tell a refusal from a success, so a table of them suggests a verdict it cannot give, and a second record beside the service's own is one more place for the two to disagree.
- **The service tells the platform its outcome in an answer header, which the Gate strips and stores.** Rejected: the Gate would change the answer it forwards untouched.
- **A line in the service's process log instead of a table.** Rejected: plain text cannot be paged and filtered by Project and outcome for a screen.
- **The SDK pushes each increment to the backend, which stores it.** Rejected: the platform would write records about a service; what it gains — counts that outlive a deleted service and one query for an Organization-wide page — matters little when nothing is charged and the counts are shown only on the service's own page.
- **Counters declared in the Service manifest.** Rejected: with the counts and their labels in the service's own file, the backend has no use for the names ahead of time, and the manifest no longer holds anything the service does at run time.
- **The backend asks the running service (`GET /.well-known/opsiforce/calls` and `/usage`).** Rejected: the screens would fail exactly when a crash-looping service's records matter most, a sleeping Development copy would be woken to show a table, and the SDK would carry two endpoints with paging, filters and token scoping only to move rows it already wrote. It stays the fallback if a reader outside the pod's sandbox cannot read the file consistently.
- **A person on platform calls (who pressed a button, whose save fired a hook).** Rejected: the Caller identity says whom a request is for, never which human, and a service has no use for user identities.

## Consequences

- Nothing that never reaches the service leaves a record: a missing Gateway Key (401), an unknown slug (404), or a copy that is down or too slow (502, 504). Each is seen by the caller when it happens.
- The Call log is written by the service's code, so it is as trustworthy as the service. The platform holds no independent account of what an Agent did through a service.
- A calling Agent has no endpoint for its own calls; the answer its client received, and what the service said to do about it, is its record.
- The builder reads Development's calls from the file directly with `sqlite3 -readonly`.
- Deleting a service deletes its Usage history with its files.
- The file's schema is a contract between the SDK and the backend, changed only with a new SDK major.
- The backend relies on reading a file written inside the pod's sandbox; that a reader outside it gets consistent reads is still to be confirmed.
