# The Builder tests a child agent by conversing with it in one throwaway Project

The Skill & Agent Builder authors Custom Agents but cannot run one. [ADR-0056](0056-builder-chats-are-hidden-projects-with-writes-resolved-to-the-launching-user.md) settled for skill-creator's documented degraded path — serial in-session roleplay inside the Builder's own chat, stated honestly in the prompt — and skill-creator names that as its own weakness: the context that wrote the prompt is the context that runs it, so the run is contaminated by everything the author just said. Four decisions since have removed every obstacle to doing it properly. [ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md) made a Custom Agent's Development profile something a Project can be created from. [ADR-0060](0060-agent-files-are-laid-once-and-shared-with-the-backend-by-ownership-list.md) writes an agent's files into the workspace once at create and never re-derives them. [ADR-0061](0061-the-platform-harness-is-a-built-in-skill-and-an-agents-prompt-is-the-authors-body-alone.md) left the child's system prompt as the author's body plus its skills, so there is no rendered composite to reproduce. [ADR-0062](0062-a-pod-calls-the-platform-api-as-the-human-who-created-its-project-bounded-to-what-it-created.md) gave the pod a caller identity whose allow-list is exactly seven routes — create, read, connect, delete a Project, plus `me` and `agents` — bounded to Projects it created itself. What remained undecided is the loop.

**The Builder tests a child agent by creating one throwaway Project from the child's Development profile and conversing with it there, verifying the child's claims inside its pod rather than believing its transcript.** Concretely:

- **One Project, one session, a conversation — not an eval suite.** The field's minimum discipline is a fresh context per eval prompt, but the Project boundary already supplies it: the child carries no Builder history at all. Prompts therefore share one session and one workspace, because that is the realistic condition — a real user builds an app across a conversation, and the failures worth catching (breaking what it already made, re-running its own migrations, not re-reading its own files) appear only on a warm workspace. Minting extra sessions inside the pod was rejected: the in-pod status watcher reports agent busy/idle from opencode's `/api/session/active` and the platform holds Project↔session at 1:1, so a session created behind its back runs where nothing can see it.
- **Created from Development, and frozen by delivery.** ADR-0058 permits a Project on the Development profile directly, and no frozen test copy is minted, because ADR-0060 already gives one: the agent's files are written at create and never re-derived, so the test Project *is* the snapshot and an edit made mid-test cannot reach it. Bedrock's `TSTALIASID` — the one pattern in the 19-system survey where a pointer legitimately targets a mutable draft — is unnecessary here for exactly that reason. The corollary is that a test Project is **single-use**: testing an edit requires a new one.
- **Visible only from the Builder chat.** A test Project is excluded from the ordinary project list and surfaced in the chat that created it, openable as a real Project — transcript and app pane — for as long as it lives, because the most useful thing an author can do with a failed run is look at it. Note the hiding is not free: `workspace_id` NULL is the Organization-wide Public area, the *most* visible setting there is, and `project-visibility.ts` has no flag for this, so concealment rests entirely on the listing exclusion ADR-0056 must build. A query that forgets it shows every author's test Projects to the whole Organization.
- **One live per Builder chat; nothing expires on a timer.** Starting a test deletes that chat's previous test Project; deleting the chat takes its test Project with it. No TTL and no reaper: supersede-delete is deterministic and happens while the author is present, which timed expiry is not, and the per-Agent project TTL remains its own effort rather than arriving as a side door in a test loop. Deletion is the existing `ProjectService.remove` — hard, synchronous, permanent, with workspace files tombstoned and reaped at seven days.
- **The Builder initiates, and announces.** After writing or meaningfully changing a definition it tests without being asked, the way a coding agent runs the build without being asked; an agent that writes a prompt and then declines to check it is the failure this decision exists to remove, and a confirmation step degrades into noise by the fourth yes. The restraint is prompt text on `agent-authoring`, not machinery: do not test a definition the author is still mid-sentence about, do not re-test an unchanged one, say what the run will spend before spending it.
- **Expectations before the run, verification inside the pod.** The Builder writes down what each prompt should produce *before* sending it and splits machine-checkable outcomes from judgement calls — the only discipline that stops an agent from declaring victory over a transcript it authored itself. It then checks the machine-checkable ones by looking: ADR-0062 grants the creator's full authority over Projects the pod created, including shell through the runtime proxy, so the Builder curls `$APP_PORT`, reads `/workspace/app/startup.sh` and `app.meta.json` against ADR-0061's App contract, and queries the read-only observability database. Results live in the conversation — no eval-suite entity, no stored runs, no pass rates over time.
- **The observability queries move into the `platform` skill.** This retires a consequence of ADR-0061, which put the read-only `/workspace/data/database.db` in the harness skill by *name* while the schemas and the ready-to-run boot/failure/crash queries stayed in `sqlite` — a stack skill a Custom Agent does not get. A child told the database exists but not how to read it does precisely what app-builder's own prompt warns against: opens `agent-browser` on a crashed app, sees a blank page and reports a UI bug. `app_requests`, `process_logs` and `process_events` are platform facts, true of any stack, and belong to `platform`; `app.db` modelling, migrations and `DatabaseService` stay with the stack skill. The test loop's honesty depends on it, since the Builder is grading what the child reports.
- **Skills are tested single-sided.** A Skill is exercised by creating a test Project on an agent that carries it. The with/without benchmark ADR-0056 deferred stays deferred: mechanically it is only a second test Project, but the work is a comparison surface and an opinion about what "better" means, and the question an author asks first is whether the skill works at all.
- **Nothing new bounds a runaway.** The enforced ceiling is the test Project's own Bifrost team budget at the ordinary project default; the Builder's patience with a hung child is prompt text. A `steps` cap on the agent under test was rejected outright — mutating the definition in order to test it reintroduces the exact fidelity gap the real-Project loop exists to close.
- **No new route.** The seven carry the loop: `GET /projects/{id}` returns each environment's `status`, `hasApp`, `appName` and `lastActiveAt` plus `agentStatus`, `lastPromptAt` and an opencode descriptor; `connect` returns `baseUrl`, `sessionId` and the runtime `build`; prompting, reading messages and shell all ride the runtime proxy, which forwards verbatim. The app's browsable public URL is absent from the seven and is not wanted: curling the port from inside the pod is the stronger check, and the human reaches the pane by opening the Project.

## Considered options

- **A test Project per eval prompt** — rejected: it buys isolation from a contamination that is the realistic condition, and charges five cold creates for it. A Custom Agent's `pool_size` is 0, so every create takes `createDirect` at 30 to 60 seconds ([ADR-0041](0041-pending-project-pool-replaces-the-warm-pod-pool.md)).
- **A fresh opencode session per prompt inside one test Project** — rejected: sessions minted through the proxy are invisible to the status watcher and to the platform's 1:1 Project↔session model, for a fresh-context property the Project boundary already provides.
- **In-pod testing only** — the `subagent` tool, or driving the pod's credential-free `:4096` API, or `opencode run --agent … --format json`. Rejected despite being far cheaper: it shares the Builder's own workspace, so the child writes over the files the author is working from, and it tests a *prompt* rather than a *delivered agent* — the skills folder, the App contract and delivery itself all go unexercised.
- **A frozen copy of Development pinned by the test Project** — rejected: ticket 20 removed frozen copies from the model, and write-once delivery already provides the freeze they would buy.
- **A timed TTL on test Projects** — rejected for now by the owner. It would have made test Projects the safe first customer for a reaper that does not exist anywhere in the backend, but a reaper is a feature about protecting human work, and none of its hard questions — opt-in, warning path, interaction with Archive — belong to a test loop.
- **A smaller Bifrost budget tier for test Projects** — rejected by the owner; a test Project gets the ordinary project default like any other.
- **A stored eval suite** — expectations as first-class rows, runs recorded, pass rates tracked. Rejected for v1: it is a product of its own, and nothing else on this map consumes it.
- **Human-triggered testing, or propose-and-confirm** — rejected: both put the author back in the position of remembering to check, which is the position this decision removes.

## Consequences

- Ten authoring iterations mean ten test Projects created and nine deleted, each paying a cold create; the authoring loop's felt cost is a minute per iteration, and the Builder's prompt should not test more often than the author changes something.
- **Accepted gap:** a runaway test can consume a full project's LLM budget before anything stops it. The backend has no rate limiting of any kind, the Bifrost cap sits at the ordinary project default, and the only other stop is the Builder noticing. Recorded rather than hidden; it belongs with the map's standing quota fog.
- ADR-0056's "v1 testing is skill-creator's documented degraded path — serial in-session runs" is retired, and with it the caveat its prompt was to carry. Its deferred **parallel with/without-skill benchmarking** remains deferred, now for a product reason rather than a mechanical one.
- Provenance needs no new column: `projects.created_by` (ADR-0056) and `projects.created_by_project_id` (ADR-0062) already say who owns a test Project and which Builder chat made it, and the second is what the listing exclusion and the supersede-delete both key on.
- The `platform` skill grows an observability section and `sqlite` loses one, which is an image bump reaching existing Projects through the Agent-Updates `content` Job by ADR-0060 — no pod restart, Custom Agent Projects included.
- **Fidelity gaps, stated so the Builder's prompt can state them too:** a test Project is always cold, never pool-warm; its spend lands on the creator's Organization like any Project and appears in Admin storage; external services the child calls are the real ones; and because delivery freezes content at create, a test Project reports on the definition as it stood the moment it was made, not as it stands now.
- Glossary: **test Project** — a throwaway Project the Builder creates on a child agent to exercise it, one live per Builder chat, hidden from the project list and reachable from the chat that made it.
