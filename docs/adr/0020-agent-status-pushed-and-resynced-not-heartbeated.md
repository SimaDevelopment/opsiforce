# Agent Status is pushed by the observer and re-read while Working — no heartbeat, no persistence

The sidebar needs a per-project signal that the Agent is Working (see Agent Status in `GLOSSARY.md`) — for **all** of a user's projects at once, including projects whose chat no browser has open. The only source of truth is opencode inside each pod. On opencode 2.x a run is bracketed by `session.execution.started` and exactly one terminal event (`succeeded`, `failed` or `interrupted`), except on a crash, which publishes none. A background sub-agent outlives its parent's run, and its completion wakes the parent into a new run. `GET /api/session/active` answers with every running opencode session in the process, children included. opencode itself may die and come back inside a live pod, and a plain `opencode serve` never resumes an in-flight run after it does.

**The `opsiforce.observer` plugin ([ADR-0093](0093-opsiforce-extends-opencode-through-plugins-baked-into-the-agent-image-one-per-risk-class.md)) posts `run.started` and `run.ended` for each opencode session over the Service Gateway channel, the second producer on the pod→backend push path established by ADR-0015. The backend keeps the set of running session ids per ProjectEnvironment in memory (a sibling of `AppReadinessService`), and the environment is Working while that set is non-empty. While an environment is Working, the backend re-reads `/api/session/active` every 60 seconds and replaces the set; an unreachable pod is Idle.** Transitions go out on the existing Redis project-events bus and fan out on a user-scoped multiplexed SSE stream that filters to the connecting user's visible projects; `GET /projects` carries the current level (`agentStatus`, `'working' | 'idle'`) so the sidebar is correct at first paint.

- **What counts as Working.** Any running opencode session in the environment, root or child. A background sub-agent keeps the environment Working after its parent's run has ended. A stalled provider stream retries inside the same run, so it stays Working until opencode's chunk timeout (15 minutes per retry). A run waiting on a question, a permission or a shell call with no timeout stays Working until someone answers or interrupts it: opencode has no inactivity cut.
- **The observer keeps no state.** It posts `run.ended` on every terminal, whatever the reason (including `shutdown`). Duplicate posts, from retries or a second opencode location, are no-ops on the set.
- **No heartbeat; truth is re-read.** ADR-0015 keeps app liveness on edges, not a heartbeat; here the stronger reason is that opencode's running sessions are *queryable at rest*, so staleness is repaired by re-reading rather than by continuously proving liveness. The 60-second re-read heals an opencode crash inside the pod, a lost `run.ended`, an observer that failed to load mid-run, a late duplicate `run.started`, and a pod that disappeared while Working.
- **Idle is not re-read.** A lost `run.started` leaves the spinner off for that one run. Re-reading Idle environments would be the polling this ADR refuses.
- **Lifecycle clears and the boot reconcile.** The backend clears the level at every environment-lifecycle boundary it drives (suspend, restart, disable, fail, delete) — a pod that stops existing cannot be Working. On backend boot, a one-shot reconcile reads `/api/session/active` of active environments' pods through `agent-session`, retrying with backoff only the environments it could not read — bounded, not polling.
- **A Working Agent holds its pod.** The backend touches the environment's agent Keep-alive key on `run.started`, on every re-read while Working, and on the change to Idle, so the agent idle timeout counts from when the Agent goes Idle. A held `/api/event` stream stays one touch at connect: a program waiting on a run is covered by Working, and an idle watcher must not hold a pod. There is no cap on Working, ours or opencode's: false Working is cleared by the re-read and a looping run by the Project's Bifrost budget, and a waiting run holds its pod until it is answered or interrupted.
- **The preview reloads from the backend stream.** The agent-status stream carries the environment id and that environment's level; the project page reloads the App preview when the environment it shows goes from Working to Idle. A store reseed never fires a reload.

## Considered options

- **Heartbeat + TTL** — the pod re-affirms Working every ~30s and the backend expires silence. Rejected: expiry would have to outlast a 15-minute stall, and it is continuous chatter from every busy pod to defend state opencode already holds queryably; 0015 refuses the same pattern.
- **Infer from proxy traffic** — rejected: the proxy sees opencode's event stream only while a browser is attached, and the no-browser case is the feature's whole point.
- **Polling** — backend probing every pod, or a frontend `refetchInterval` on `GET /projects`. Rejected: N pollers or always-on refetch for a signal that is silent most of the time; contradicts 0015. The re-read is bounded to Working environments.
- **Persist in Postgres** — rejected: ephemeral runtime state; a no-TTL boolean reports a dead pod's agent as Working, the same failure 0015 refuses for `serving`.
- **An observer "hello" on setup** — fixes only an opencode restart, and only once a location next boots.
- **A warm-up request after an opencode restart** — a crash leaves no terminal event for the new observer to see.
- **Skip the suspend in the timeout listener while Working** — a Keep-alive key that already expired never fires again, so it would need a second retry clock.
- **A ceiling after some hours of continuous Working** — cuts legitimate long runs and adds another clock.

## Consequences

- A pod whose observer failed to load reports nothing and shows Idle; its turns still work.
- The set and the re-read live in backend memory and assume the single backend replica (`replicaCount: 1`, like `AppReadinessService`); scaling out moves them to Redis, as 0015 already prescribes for `serving`.
- Prompting a published environment's agent spins its project in the sidebar too — the level is per-ProjectEnvironment and the sidebar consumes the OR.
- The SSE stream computes the visible-project set (tenant + workspace membership) once per connection; reconnects recompute it, and project creation already refetches the list.
- Agent Updates' wait-for-idle keeps reading `/api/session/active` live, not the stored level.
- Changing the observer ships only via a new agent image and pod recreation — bump `agent-config/agent-image-version.json`; rollout mechanics as in 0015.
