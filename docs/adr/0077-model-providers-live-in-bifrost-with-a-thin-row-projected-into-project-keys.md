# Model providers live in Bifrost with a thin row, and their weights are projected into Project keys

An Organization chooses its own Model providers, so something has to hold each one's key, URL and Base format, and something has to carry its switches and weights to every virtual key the Organization's Projects own.

**A Model provider is a Bifrost provider, or a named key of one, plus one `model_providers` row (`tenant_id`, `bifrost_provider`, `bifrost_key`, `base_format`, `chat_enabled`, `chat_weight`, `backend_enabled`, `backend_weight`), and the backend projects the rows into the `provider_configs` of every `chat` key of the Organization by `chat_enabled` and `chat_weight`, and of every `backend` key by `backend_enabled` and `backend_weight`; reachability, computed from the same rows, gates the model pickers.** Concretely:

- **The row is thin.** It stores no key, URL, kind or model list, and no key name or Base format except for an Azure connection: those live only in Bifrost, as their single encrypted copy, and are read from it. A NULL `tenant_id` makes the row a platform provider, whose switches and weights are every Organization's values for it; an Organization's row of the same provider, key and `base_format` replaces them, and exists only while its values differ. `tenant_id`, `bifrost_provider`, `bifrost_key` and `base_format` are unique with NULLS NOT DISTINCT, and each weight is an integer from 0 to 100.
- **The Base format registry is a code constant.** Each entry (`openai`, `anthropic`) holds Bifrost's `base_provider_type`, the opencode provider id and `models.json` key, the official API URL, the connection test, the allowed kinds and the `allowed_requests` profile per kind, so a new format is one entry plus image changes.
- **`writeTenantKeys` writes the whole projection, per Organization, under an advisory lock.** It writes both keys of every Project, each from its own switch and weight, and a row is written only when it is reachable: switched on for that key, present in Bifrost and, for a Linked account, connected. Its weight is written as is, so 0 is a backup that Bifrost's own fallback list still reaches, and switching a row off removes it from the key. Weights split traffic only within a Base format because Bifrost first filters a key's providers by the requested model, so every entry names the models it may take, following the models on the provider's key: `["*"]` for a standard provider whose key serves every model, which Bifrost checks against its own catalog, or the models chosen for it; for a custom provider whose `list_models` is off, the models on its key that are in its Base format's catalog, all of them when the key lists `["*"]`, since `["*"]` on the entry lets Bifrost pick it for any model and fail over, skewing the split; and for an Azure connection, its format's models on its key, with `key_ids` naming that key alone. Every provider's key lists `["*"]` unless an admin chose only some models, so a model added to the catalog reaches it without rewriting the key; a boot step turns a key that lists the whole catalog into `["*"]`. The choice is one rule for every provider, made on its key without the secret, because Bifrost puts the stored secret back when the masked value it returned is sent again.
- **Bifrost's URL check is the only address rule, and admin-typed URLs are `https://` only.** A typed base URL is written to the Bifrost provider before the connection test, with `allow_private_network: false` and no `proxy_config`, so Bifrost refuses private addresses at save and again at every connection after resolving the name itself, and its refusal reaches the admin as is. The backend adds only the `https://` rule: Bifrost always allows loopback, and its own port is plain http, so a plain-http URL on `127.0.0.1` would loop requests into Bifrost for every Organization. The test never follows a redirect, which would get around Bifrost's check.
- **It runs on every change, never on a timer.** Every save, global create and delete, Linked-account change, every Project create and every pool claim runs it; a failed write fails the calling operation. A new image whose model catalog serves different models changes every entry that lists them, so at boot, when the catalog's served models differ from the ones `applied_model_catalog` holds, the backend rewrites every Organization's keys and records the new ones only once every Organization took them, so a failure is retried at the next boot. A pool slot's `chat` and `backend` keys are created with no providers, and the claim writes the claiming Organization's before it finalizes, retrying like the budget and team patches and falling back to the slow path when it keeps failing.
- **An Azure connection is a named key of Bifrost's one native `azure` provider, with one row per Base format its models come from.** A gateway has a single `azure` provider, which can serve GPT and Claude at once, so each connection, whether a platform admin's or an Organization's own, is a key of it holding the resource's endpoint, the catalog models chosen for it and, for a deployment named other than its model, an alias. Each of its rows names its `bifrost_key` and `base_format`, sits on that card with its own switches and weights, and writes its own entry on the virtual key; Bifrost 2.3 gives a virtual key one candidate per entry, so entries of one provider carry their own weights, models and `key_ids`. Settings creates, edits and deletes a connection's key through the Admin API after `GET <endpoint>/openai/v1/models` with its `api-key` passes, and keeps one row per format its models span. The Helm values declare no Azure key: a deployment's Foundry resource is added from Settings like any other connection, so every connection's rows come from Settings.
- **The `backend` key follows the App switch and weight of the same rows.** The App's own AI features are routed on the format cards like the Agent, with an Agents/Apps choice above them, so no deploy value decides them. The fixed `openai` and `anthropic` start on for Apps at weight 1; a Custom model provider with a key starts on for Apps like it starts on for Agents, and every other provider, a Linked account or an `opsiforce-*` included, starts off for Apps, so a ChatGPT plan never serves apps unless an admin chooses it. The App weight follows the Agent weight rule on its own, and an unreachable App format warns on the card but blocks nothing, since no Agent depends on it. Transcription rides the `chat` key and is unaffected.
- **Reachability gates the pickers and warns before it breaks an Agent.** The reachable models are the catalog models some reachable row serves: every model of its Base format, or only the ones on its key for an Azure connection or a Custom model provider an admin chose models for, computed on every read from the rows and Bifrost with no cache. They filter the Agent Profile picker, the profile save and the chat's model picker, and a member-open read serves them with nothing else about the providers. A card save that would leave its format unreachable answers with the Custom Agents whose Profiles name a model of that format and the Built-in Agents whose Agent Model is in it, and goes ahead only when the request acknowledges them; nothing is blocked or rewritten. When Bifrost is not configured or cannot be read, every catalog model counts as reachable, so a gateway outage never empties the pickers.
- **An existing deployment is cut over by a migration alone; a fresh install is seeded from env.** The migration creates rows only on a database that already has Organizations: the platform rows `openai` 0, `anthropic` 1, `custom-openai-1` 1, which every Organization inherits. It rewrites no `chat` key: the keys created before it hold `openai` 0, `anthropic` 1, `custom-openai-1` 0.3, which route exactly like the rows because `anthropic` and `custom-openai-1` never serve the same model, so each Organization's keys take the rows' weights at its first sync. On a database with no Organizations the migration creates nothing, so the first boot finds no platform row and gives `openai` and `anthropic` platform rows at weight 1 each: one Bifrost already has, as Helm declares it, is adopted without touching its key, and one it lacks is created from `OPENAI_API_KEY` / `ANTHROPIC_API_KEY`, only when set, through the platform create code. Weight 1 because a card whose only switched-on row weighs 0 can't be saved. The seed never runs again and never creates a Linked account.
- **A platform provider reaches every Organization, or only chosen ones, by inheritance, and only the Organization turns an added one on.** Every Organization reads every platform row it isn't withheld from, switched and weighted like it unless it saved its own values: `openai`, `anthropic` and `custom-openai-1` on, an `opsiforce-*` provider off. A `model_provider_availability` row gives a provider, by its key name or provider name, the mode `every` or `chosen`, and its `model_provider_availability_tenants` rows list Organizations: withheld ones in `every`, the only ones that have it in `chosen`; a provider without a row is `every` with none listed, so an Organization added later gets every `every` provider and no `chosen` one. A withheld provider is out of that Organization's reads, keys, pickers and save, so its admin neither sees nor switches it; the Organization's own row of it is kept, so making it available again restores its values. Changing the mode rewrites the list so every Organization keeps what it has, and decides only what a later one gets. Withholding asks only for a confirm and checks no Agent, since only a platform admin withholds and does it on purpose. Creating an `opsiforce-*` provider writes its platform row and its availability and touches no `chat` key, since a switched-off provider changes no projection, and deleting it removes the platform row, every Organization's own row of it and its availability, and resyncs every Organization. A save holds the platform lock shared, so a platform delete can't leave an Organization's row of a provider that no longer exists.
- **`custom-openai-1` is on in every Organization, like the fixed built-ins.** On a fresh install its platform row appears, switched on at weight 1, when a platform admin first signs it in, and the same transaction resyncs every Organization's `chat` keys to take it.
- **Helm declares the platform's `openai` and `anthropic`, and production's `custom-openai-1`, under `split`.** Their keys come from `env.*` references to a Secret, and production's `custom-openai-1` stays a key-less provider at the hosted Codex OAuth Dock, so a deploy changes no traffic and needs no key-storing step before it; a platform admin's sign-in moves `custom-openai-1` to the Linked-account Proxy. Bifrost's `split` source of truth never prunes what its database holds, and keeps a Helm-declared provider's database version while its entry in the values is unchanged, so a key replaced, a connection edited or a sign-in written through the Admin API survives restarts; changing a provider's Helm entry makes the file win for it at the next restart. Every other provider is created and changed only through the Admin API.

## Considered options

- **A Bifrost routing rule per Organization.** Rejected: a rule picks a target by weight without checking the model, so it needs one rule per Base format with a CEL list of that format's model ids, it cannot grant access a key does not already list, and its single fallback list retries the provider that just failed.
- **Storing the key and URL in our database and reconciling Bifrost from it.** Rejected: it keeps two copies of every secret and adds a reconciler, while Bifrost in `split` mode already keeps API-created providers across restarts.
- **Keeping switched-off rows on the key with a `*` blacklist.** Rejected: absent is the only state every Bifrost check agrees on, and it needs no second meaning for a present entry.
- **A backend address check of its own, or a per-deployment allowlist for private networks.** Rejected: it would duplicate Bifrost's check without its connect-time re-resolution, and LAN-hosted models and Private-Endpoint Azure are out of scope; a Foundry resource behind a Private Endpoint resolves to a private address, which Bifrost refuses for a Compatible endpoint.
- **The migration creating the platform rows on every database, fresh ones included.** Rejected: a migration can't read Bifrost, so on a fresh install whose Bifrost lacks a built-in it would create a row with nothing behind it, and the boot seed, which runs only while no platform row exists, would never create the missing provider from env.
- **Helm declaring no Bifrost provider.** Rejected: a provider dropped from the values keeps its `env.*` key references in Bifrost's database, which stop resolving once the Secret wiring goes with it, so every environment's deploy would depend on storing its keys as values by hand just before its push, and a fresh install's built-ins would depend on the backend's env rather than the deploy's Secret.
- **Copying every platform row into every Organization when it is created, and into every existing Organization when a platform row is added.** Rejected: a platform row's switch and weight are never edited after it is created, so the copies hold nothing an Organization chose; they multiplied the rows by the Organizations, needed a grant on every Organization create and platform create, and hid which values an Organization had actually set.
- **Rewriting every Organization's `chat` keys once after the migration, from a queue the migration fills.** Rejected: the rewrite changes no routing, so it would add a table, a boot step and its retries only to make the Bifrost dashboard show 1 instead of 0.3 sooner.
- **One row for a provider that serves both formats, with its formats read from its key models.** Rejected: a virtual key entry has one switch and one weight, so the provider could not be switched off for one format or weighed differently in each.
- **Bifrost provider-key weights for the split between formats.** Rejected: a key's weight only divides the provider's own traffic among its keys that serve the requested model, so it never moves traffic between the provider and another one.
- **Listing Bifrost providers without a row so a platform admin can make them Built-in from Settings.** Rejected: one deployment needs it, so a row added by hand at deploy time does the same with no routes or page.
- **A withheld list alone, with every provider reaching every Organization added later.** Rejected: a provider set up for one customer's Azure resource would reach every Organization created after it, and the platform admin would have to withhold it from each.
- **A custom Bifrost provider per Azure resource, with an OpenAI or Anthropic base type.** Rejected: a resource serving GPT and Claude would be two providers holding two copies of its key, and a native `azure` key already carries the endpoint and the deployment aliases Foundry needs.
- **The resource's own model listing as the models a connection serves.** Rejected: it lists what the resource offers rather than the catalog models Opsiforce routes, so the admin chooses from the catalog and the listing only tests the connection.
- **Withholding by switching the Organization's row off, or by deleting it.** Rejected: an Organization row exists only while it differs from the platform's, and its admin can switch it straight back on.
- **A periodic drift sync.** Rejected: every write that changes the projection already runs the sync, and a timer would hide a failed write instead of failing its operation.
