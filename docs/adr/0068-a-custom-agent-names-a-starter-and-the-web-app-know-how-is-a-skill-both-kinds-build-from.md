# A Custom Agent lays its template from the image on its first build, and the web-app know-how is a skill both kinds build from

[ADR-0058](0058-a-custom-agent-holds-one-definition-per-environment-and-a-project-keeps-the-files-it-was-created-with.md), [ADR-0060](0060-agent-files-are-laid-once-and-shared-with-the-backend-by-ownership-list.md) and [ADR-0061](0061-the-platform-harness-is-a-built-in-skill-and-an-agents-prompt-is-the-authors-body-alone.md) each said that a Custom Agent has no template: its Projects open on an empty `/workspace/app` and the agent builds what its prompt describes. The first real Custom Agents show the cost. Two Agents that both "build small web apps for a shop" produce two unrelated stacks, the same Agent produces a different architecture per Project, and the Skill & Agent Builder has nothing to hand a child but prose — while App Builder's template and two hundred lines of stack know-how sit in the same image, one directory over. Meanwhile the one thing every App must get right here — that the pod is disposable and only `/workspace` survives — lived as a clause in the `platform` skill and nowhere a template could enforce it.

**Every Custom Agent that builds lays a template before it builds — never on an empty `app/` — and the only template ever copied is the platform's own, laid by the agent itself from its image — not by the platform, and never from a stored definition; any other stack is created by the child from a Skill's description. App Builder's stack know-how leaves its prompt for a built-in `web-app` skill whose first step lays the platform's web-app template, so a Custom Agent on the default stack builds exactly what App Builder builds.** Concretely:

- **The `web-app` skill lays the default template.** Every pod boots the same image, so `/opt/agents/app-builder/template/app` is inside every Custom Agent's container already. `agent-config/skills/web-app/SKILL.md` opens with one checkable step — when `/workspace/app` holds nothing but the platform's `data/` and the App's configuration file, copy the template in; with anything else there, never copy, because a copy over someone's work replaces their files and their database — and then carries everything that was true of App Builder's prompt because of the template: the running dev servers, adding packages, the build order, the structure, the rules, verification. It is a shared skill, so it is minted as a Built-in Skill and a Custom Agent pins it.
- **App Builder's prompt keeps only App Builder.** Persona, the direct-task-versus-app decision, the communication rules, the install-freely posture, web search, the speech and email rules, and one line — *"Load the `web-app` skill before touching the app"*. One source, two readers, updatable through the image like every skill; a prompt line would be frozen at create.
- **A different stack is a scaffold Skill the Builder constructs, and it describes the skeleton rather than shipping it.** Every Skill the Builder authors for an Agent — a scaffold, or an addition to the starter — is a *stack Skill* that frames the work: structure, libraries by name (never version pins — the child takes the latest stable release and the Project's lockfile fixes it; the Skill only says which major its specifics were written against), contracts (formats, schemas, routes, constants), a style guide, the runtime `startup.sh` must provide, anti-patterns, and a definition of done paced like `web-app`'s: quick gates after every change, a full walk before go-live, restarts and exhaustive audits only in the Builder's test run. It never carries an implementation to copy; its `scripts/` are tools the agent runs, never code the App ships. A scaffold's first step has the child create the skeleton it describes, only into an empty `app/`.
- **The Agent's body states its architecture.** A building Agent's prompt carries a short Architecture section: which template it lays, what it changes about that template and what gives way, the services its App runs, and where its domain goes. The body is the one text every Project is sure to read and it is frozen at Project creation, which is what an architecture should be; the template is a reference structure the Architecture adjusts, and `web-app` says which parts of it are plumbing, which are the normal work, and which change only on a decision. Know-how longer than a few lines is a Skill the body names.
- **The durable-workspace rule enters the `platform` skill, stated for any stack.** What a pod recreate wipes, that `startup.sh` is the one repeatable recipe — dependencies ensured idempotently, state under `app/data/`, every long-running process under `guard` in the foreground — and that Publish is a git checkout carrying no `data/`. It names no particular service. It is a platform fact, so ADR-0061 puts it in the one skill every agent carries, and the Builder's restart check through `POST /projects/{id}/restart` is what proves a child honoured it.
- **Nothing is stored.** No profile column names a template, no environment variable carries one, the first-boot script is untouched. The template an Agent builds from is readable from its Skills and its prompt, which is where the rest of its definition already is.

## Considered options

- **A `starter` column on the Agent Profile, laid by the first-boot init container** — built first and withdrawn by the owner the same day: it stored as platform state something that is fully expressed by the Agent's Skills and prompt, and it grew a migration, an API field, a pod variable and a Store control for one line of copy the agent can run itself.
- **Keep "no template" and put the architecture in the prompt body alone** — rejected: a body cannot carry a file tree, and a prose architecture with nothing laid is re-derived differently by every Project. The body states the decisions; the template carries the files.
- **A Skill per changed layer (an "extension" Skill loaded after `web-app`)** — rejected as the default: a one-line decision (a different database, an extra worker) belongs in the Architecture section; a Skill is added only when the know-how behind it is more than a few lines.
- **A per-Project decisions file in the workspace (`app/AGENTS.md`)** — rejected: the architecture is decided once per Agent, not per Project, and the body already reaches every Project unchanged.
- **The template as a Skill whose assets hold it** — rejected, for the platform's template and for constructed stacks alike. The first cut kept it as the scaffold path; the owner reversed that: code stored as Skill assets is a template in the database under another name, lives outside git with no review or tests, and goes stale the day the starter or a library moves — while a Project needs the same decisions, not the same bytes. A shared implementation worth maintaining belongs in git, as image-shipped code, never in a Store row.
- **Leave App Builder's prompt whole and copy its stack text into `web-app`** — rejected: two copies drift, and ADR-0061 already chose the skill channel for exactly this reason.
- **A Makara package override of `web-app` that defers to its own prompt** — tried and removed: the Built-in Skill reconciler mints every composed tree of one name onto one Store row, so the override became the *latest Version* of `web-app` for every Custom Agent. The Makara package instead composes **without** `web-app` — a per-package exclusion in `compose-skills.mjs`, the same lever that gives `custom` only `platform` — and keeps its whole prompt; splitting it is a follow-up, together with the pre-existing `ui` collision the same mechanism causes.

## Consequences

- ADR-0058, ADR-0060 and ADR-0061 stand: the `custom` package ships no template and the platform lays none. What changes is that a Custom Agent's Skills now say which template the agent lays, and the Builder never authors a building Agent without one.
- The lay tests for an empty `app/`, not for a missing `startup.sh`: a missing or non-executable `startup.sh` in an App that has other files is repaired alone, never by re-laying.
- A child that skips the copy builds on an empty `app/`; the `web-app` skill states the step with a checkable condition, and the Builder's test run shows the miss.
- App Builder's prompt shrinks by two thirds and its `version` bumps, so existing App Builder Projects receive the slimmer prompt and the new skill through Agent Updates. If App Builder starts forgetting to load `web-app`, the remedy is the one-line load, never a second copy of the text.
- The App restart no longer depends on the starter's process names. [ADR-0009](0009-in-pod-control-process.md) made `startup.sh`'s `guard app-backend` / `guard app-frontend` a load-bearing interface; with templates that are not the starter that stops holding, so `POST /restart-app` restarts the process under every `guard` nested beneath the pod's `webapp` guard, whatever its name, and leaves `startup.sh` running. A restart that finds nothing to kill answers `killed: 0`, and the backend treats that as a failure and recreates the pod rather than reporting an App restart that did not happen. The `platform` skill's rule that every long-running process runs under `guard` is what makes an App restartable in place.
- Glossary: **Custom Agent**, **Platform Skill** and **App contract** are amended; no new term. "Architecture section" is prompt structure, not a domain term.
