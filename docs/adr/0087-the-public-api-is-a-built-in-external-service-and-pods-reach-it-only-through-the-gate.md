# The Public API is a Built-in External Service, and pods reach it only through the Gate

A pod acts on the platform as its Project's creator ([ADR-0062](0062-a-pod-calls-the-platform-api-as-the-human-who-created-its-project-bounded-to-what-it-created.md)). A key that let a pod call `/api/v1` directly would be all or nothing per Agent, invisible in the call log, and a second door beside the Gate: every Gate feature (Operation switches, input checks, the call log, a later "ask" level that parks a call until a human approves) would have to be rebuilt inside `PublicApiGuard`, and a pod holding the key could `curl` past any switch.

**The Public API is the Built-in External Service `public-api` ("Opsiforce Public API"), SDK-shaped like any other: a pod calls `POST $EXTERNAL_SERVICES_URL/public-api/<operation>` with its ordinary service key, the Gate applies the Project configuration, and the in-process handler calls `/api/v1` on loopback with a call token the Gate holds in memory for that one call. `/api/v1` accepts no Gateway Key.** Concretely:

- **Operations from Nest.** One decorator per route, `@ExternalServiceOperation('<snake_case name>', { kind? })`, opens the route to a pod and names its Operation, `operationId` and kind override; kind defaults from the HTTP method (GET read, POST/PUT/PATCH write, DELETE destructive), overridden for `validate_skill` (read), `remove_agent_skill` (write) and `reset_test_project` (destructive). `external-service-cli generate --from-openapi` writes `service.json` (one flat input per operation from path, query and body; a name clash fails) and a generic handler table, both committed, CI fails on drift. The same command is how a builder chat wraps a tenant's own OpenAPI.
- **Call token.** `gc-…`, in backend memory only while its Gate call runs, attached only when dispatching to a Built-in External Service; `PublicApiGuard` resolves it to the calling Project and its creator. Custom External Services never get one: an AI-written service would otherwise act on the platform with a human's authority.
- **Who the call acts as** stays ADR-0062's: the creator's last-seen permissions, without `can_use_public_api`. **Containment covers Skills and Agents:** a pod may write only its builder chat's subject and Skills, Agents and Projects its own Project created (`created_by_project_id` on `projects`, `skills` and `agents`); reads stay creator-wide. An Operation switch says what kind of call, never which Skill, so it cannot stop a `pdf-tools` chat from publishing a version of `invoices`. The depth-two chain cap refuses only `create_project`.
- **One pod key.** A pod holds only its `service` key and no platform API URL or key of its own; the runtime proxy accepts that key at `OPSIFORCE_RUNTIME_PROXY_URL`, contained like every pod call, and checks the `connect_project` switch on every request. No Agent setting grants the platform API: a ProjectEnvironment's `public-api` Project configuration does.
- **A builder chat is configured when created.** A new Project configuration starts at the kind defaults (reads on, writes off, [ADR-0082](0082-an-external-services-skill-is-a-skill-marked-by-its-service-given-per-agent-or-per-project-and-reads-its-operations-live.md)); the Builder writes a new `skill-agent-builder` chat's `public-api` configuration before its first delivery, with every read and the authoring, Test Project and `connect_project` writes on (`create_agent` and `delete_project` off), a list kept beside that code rather than in `agents.json`, which also gives the chat `service-public-api` from its first message. Any other Project switches writes on in its own configuration.
- **No exception for later operations.** A new Public API Operation is off in existing Project configurations, as for every service ([ADR-0079](0079-a-changed-service-manifest-reads-old-configurations-tolerantly-and-never-turns-on-new-operations.md)); the Service form is empty, so the service is always Available.
- **Humans call `/api/v1` directly.** IdP bearers call it with `can_use_public_api`; `/api/v1/openapi.json` and `/api/v1/docs` stay public. The live `$EXTERNAL_SERVICES_URL/public-api/openapi.json` describes the Gate calls. `skill-agent-builder`'s skills call Operations (`scripts/api.sh call <operation>`), and the `service-public-api` skill teaches them.

## Considered options

- **The same checks run inside `PublicApiGuard`, no hop.** Rejected: two enforcement points for every present and future Gate feature, and an "ask" level would have to park and replay a raw HTTP request.
- **A call token for every service (`ctx.caller.apiToken`).** Rejected: hands a tenant's code the creator's platform authority.
- **Public API reads off by default (`"default": "off"` per Operation).** Rejected by the owner: reads on, as for every service; a Project switches on what it needs.
- **"Also allow read operations added later" for the Public API only.** Rejected: one rule for every service.

## Consequences

- The upgrade's migration writes the same configuration into every existing `skill-agent-builder` ProjectEnvironment that has none, and leaves one that has a configuration as it is; the boot pass delivers the Service skill those environments are missing.
- Nothing carries the Public API to a Custom Agent: it reaches one only when an editor adds `service-public-api` on the Agent page and its Projects enable `public-api`.
- Skills and Agents a builder chat created before the upgrade have no `created_by_project_id`; only their own builder chat (as subject) can write them.
- Every Public API call by a pod appears in the call log; human calls to `/api/v1` do not.
