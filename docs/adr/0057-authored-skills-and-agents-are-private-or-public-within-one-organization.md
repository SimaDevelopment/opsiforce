# Authored Skills and Custom Agents are private or public within one Organization, and become Organization property when made public

[ADR-0055](0055-skill-store-authoring-rides-four-flat-scope-partitioned-permissions.md) partitioned authoring across a tenant scope and a global scope behind four flat permissions. The 2026-09-17 owner redirection removed the global scope outright: every authored Skill and Custom Agent belongs to exactly one Organization, and the only remaining axis is whether it is visible to its creator alone or to every member. Built-in content stays the platform's channel — the image and the reconciler — so "platform-authored dynamic content" ceases to exist as a concept, and with it the `can_manage_platform_skills`/`can_manage_platform_agents` pair, operator-direct global authoring, and the tenant→global promotion flow.

**Authoring rides two flat permissions; visibility is a state of the artifact, not a second permission tier; and a public artifact stops being its author's.** Concretely:

- **Two strings, no scope partition.** `can_manage_skills` and `can_manage_agents` govern every authored row in the caller's current Organization and join the `opsiforce_admin` bundle. "Manage" spans the whole authoring surface: create and edit drafts, publish, make public, add and remove agent skills, duplicate, import, archive, delete. Consuming needs nothing — any member browses the Store, inspects published content, and uses whatever the Agents in their Projects carry.
- **Private is unlisted, never confidential.** A private artifact is invisible in the Store, unpickable, and uneditable by anyone but its creator — including other permission holders and Organization admins, with no break-glass. It is *not* secret: Dynamic Delivery writes a Custom Agent's prompt and its skills into the Project workspace as files, so anyone who can see a Project can read what backs it by asking the Agent. Any stronger guarantee would need delivery-layer work this decision does not take on.
- **Ownership evaporates on publication.** While private, `created_by` is a hard boundary. Once public, the artifact is Organization property: any holder of the matching permission may edit it, publish over it, duplicate it, archive it, or delete it. This is the `workspaces.owner_id` shape already in the schema — an owner exists only for `type = 'private'`, and a shared Workspace has none — and it is the deliberate avoidance of LibreChat issue #10197, where creators retain sole control of globally published agents and administrators cannot remove them (`.scratch/agent-skill-platform/research/competitor-sweep.md`).
- **Widening is irreversible.** Public never returns to private, following `WorkspaceService`'s existing refusal (`"Public and workspace projects can't be made private"`, `backend/src/workspace/workspace.service.ts`). The escape is **Duplicate**: any artifact a caller can see — public, their own private one, or a Built-in one — forks into a new private draft they own, carrying a `forked_from` reference. `.skill` export/import remains the route across Organizations.
- **Encoding lives on the mutable parent.** `visibility` (`private | public`) and `created_by` (`text NOT NULL`, FK to `users` with `ON DELETE RESTRICT`) sit on the `skills` and `agents` rows, never on a Skill Version or an agent release — the surveyed field is unanimous that sharing state stays outside version history. `origin` (`built_in | custom`) replaces `tenant_id IS NULL` as the platform-content marker, so provenance and audience stay independent and a future global Custom Agent remains expressible. Reads go through shared predicate modules mirroring `project-visibility.ts`.
- **One agent-skills mechanism, named plainly.** An Agent has Skills: a row per `(agent, skill, pinned version)`, added and removed while editing the Agent, gated by `can_manage_agents` because the Agent is the object being changed. The **Attachment** vocabulary is retired. Propagation differs by Agent kind and is a property of the kind, not a second mechanism: a **Built-in Agent**'s set is read live at delivery and reaches existing Projects; a **Custom Agent**'s set is captured into each release and reaches only Projects created afterwards.
- **Visibility must be coherent downward.** A public or Built-in Agent's Store skills must all be public — the API refuses to add a private one, and refuses to publish an Agent that still carries one. Agent-embedded skills are exempt and carry no `visibility` of their own: they have no independent audience and inherit the Agent's.
- **Drafts follow the artifact.** A private artifact's Draft Revisions are creator-only; a public artifact's are visible to permission holders, because a public artifact is theirs to edit. Members without the permission see published content only, and an in-flight draft is invisible to them.
- **Retirement is non-destructive, and Delete is in-use-checked.** Archive hides a Skill from the Store or a Custom Agent from the picker and closes it to new use while everything already using it keeps working, reversibly. Delete is available for never-published drafts and for archived artifacts, refused while any Agent's skill set still references the Skill, with the refusal naming those Agents. **Deprecated (Skill)** is retired: a Built-in Skill that leaves the image simply stops being offered, exactly as the registry already handles Built-in Agents, and its stored content survives so Custom Agents that pinned it do not break. **Revoke (Skill Version)** is retired — see Consequences.
- **Standalone collapses to instance-admin.** Both strings enter the Helm static-auth default bundle and map through `SSO_GROUP_MAP`; a single-operator install is the whole Organization.

## Considered options

- **Flat authority over private artifacts too** (any permission holder sees and edits everyone's drafts; `created_by` is only provenance) — rejected: it makes "private" a list filter with no meaning, and the Personal Workspace precedent in this product already promises that private means private. The cost accepted with it is real and recorded below.
- **Owner-bound throughout** (only the creator ever edits, public or not) — rejected: this is LibreChat's behaviour and its documented governance failure. A public Skill that several Projects depend on must not become unmaintainable because its author moved teams.
- **An ACL or grant table** (openwork's three-level grant cascade, LibreChat's principal/role bitmask, Zapier's per-user share list) — rejected for now: two states do not need a grant table, the house has no roles ([ADR-0027](0027-platform-scope-routes-opt-out-of-tenant-resolution.md)), and adding principals later is additive.
- **Nullable `created_by` as the public marker** (mirroring `projects.workspace_id IS NULL` = Public) — rejected: publication would erase provenance, and NULL-as-public has already misfired here, since `projects.workspaceId` is `ON DELETE SET NULL` and deleting a Workspace silently moves its Projects into Public.
- **`ON DELETE CASCADE` on `created_by`** (mirroring `workspaces.ownerId`) — rejected: the rule wanted is *delete the departed member's private artifacts, keep their public ones*, which a foreign key cannot express; cascade would destroy Organization content. `RESTRICT` refuses instead, forcing any future user-deletion path to confront the question. Nothing in the backend deletes a user row today, so this costs nothing now.
- **Two named concepts for agent skills** (a live "Attachment" on Built-in Agents, a captured skill set on Custom Agents) — rejected: the row, API, and UI are identical; only the read moment differs, and two words would imply two mechanisms to build.
- **Keeping Revoke (Skill Version)** — rejected for v1, see Consequences.
- **Retaining a scope-escalation approval gate** (Copilot Studio's submit→admin-approve, AWS Agent Registry's publisher/curator/consumer, Dify's PR review) — moot: with no scope above the Organization, making something public is an ordinary act by an existing permission holder.

## Consequences

- **Retires [ADR-0055](0055-skill-store-authoring-rides-four-flat-scope-partitioned-permissions.md) entirely** — its four-permission matrix, strict scope partition, operator-direct global authoring, membership-not-elevation playbook, and scope-bound Revoke. Retires the global-scope clause of [ADR-0054](0054-built-in-and-custom-agents-coexist-by-scope.md): slug uniqueness is scoped by `origin` rather than by `tenant_id IS NULL`, and picker liveness is decided per ticket 20. [ADR-0051](0051-skill-catalog-append-only-store-tables.md)'s Archive/Deprecated/attachment consequences are superseded on the Deprecated and attachment clauses only.
- **No revocation channel ships in v1.** A published Skill Version frozen into an existing Custom Agent Project cannot be stopped; the remedy is recreating the Project. For Built-in Agents the equivalent reach survives under another name — removing the Skill from the Agent propagates live through Dynamic Delivery. This is a deliberate risk acceptance against the surveyed consensus that a post-hoc kill switch is mandatory regardless of publish-gate strength (the VS Code kill-bit precedent, `research/skill-validation-security.md`), and it raises rather than lowers the value of the publish-time validation gate, which becomes the only defence.
- **Private artifacts of a departed member are unreachable.** No holder can see them, and the platform has no membership-departure hook: `users` carries no active or deleted column, `UserService` has no delete, and Organization membership is provisioned identity-provider rows. The `RESTRICT` foreign key is the backstop; policy waits for a mechanism to hang it on.
- **Two strings across five sync points** — Pulumi permission list, Pulumi group, backend `Perms`, the frontend constant, the Helm static-auth list. Three pre-existing drifts were measured while deciding this and are *not* fixed here: `can_view_queue_dashboard` is missing from the backend and frontend lists, `can_manage_external_integration` from the frontend, and `can_manage_users` from the Helm static list — so static-mode installs have no user management today.
- **The visibility predicate must land twice.** The Project rule exists declaratively in `project-visibility.ts` for list paths and imperatively in `ProjectService.assertProjectVisibleToUser` for single reads; Skills and Custom Agents need both forms or reads and lists will disagree. Public-API surfaces use the `caller.permissions.has(...)` idiom after a visibility check, not `@RequirePermission`.
- Every new store and agent controller takes a **class-level** `@RequirePermission` with per-route relaxation, never the reverse — the global guard returns `true` for undecorated routes.
- **Glossary**: **Attachment**, **Revoke (Skill Version)** and **Deprecated (Skill)** are deleted; **Built-in Skill**, **Custom Skill**, **Duplicate (Skill)** and **Duplicate (Custom Agent)** are added; **Skill**, **Skill Store**, **Custom Agent**, **Archive (Skill)**, **Archive (Agent)** and **Dynamic Delivery** are rewritten.
- This ADR has no home page under `docs/` yet; the feature is unbuilt, and the page is owned by the map's PRD ticket.
