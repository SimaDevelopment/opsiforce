# Test Project

> How does the Skill & Agent Builder test a Custom Agent it authored, and how is its one Test Project refreshed?

## How it works

### The Project

- A [Test Project](../../CONTEXT.md) is the one Project the Builder creates on the [Custom Agent](../../CONTEXT.md) it authored, from that Agent's Development [Agent Profile](../../CONTEXT.md) and Development [Template](../../CONTEXT.md) — whatever its Default environment (Agent) is, and even before the Agent has any Production Profile — so the child runs the definition the chat just saved and starts from the files it just saved, laid into the workspace root and committed as "Initial template" ([ADR-0063](../adr/0063-the-builder-tests-a-child-agent-by-conversing-with-it-in-one-throwaway-project.md)).
- `kind: "test"` on create is accepted **only** from a Builder chat's own pod; anywhere else it is refused. An Agent chat's Test Project runs only on the chat's own subject Agent; a Skill chat may name any Agent it can see and gets that Agent's Development. Each chat has exactly one: it is created once, a second create answers 409 `test-project-exists` with the existing `testProjectId` and deletes nothing, and `GET /me` names it as `builderTestProject`, so the side pane and the preview URL survive the whole loop.
- A Test Project is created with its app idle timeout set to the agent idle timeout, so opening its App in the preview does not keep the pod up for the App's longer window.
- Neither a Test Project nor its chat counts toward the Organization's [Limit](../../CONTEXT.md) on Projects ([Limit](../organization/limit.md)).

### Checking a round

- Before every save the Builder checks the Template by what changed: nothing when there is no `template/`; that every path the body names exists and opens when only files that don't run changed; and otherwise `scripts/check-template.sh [setup]` from its package template, which syncs `template/` into `/workspace/.cache/template-check/` (keeping what earlier setups installed, never writing into `template/`), runs the first-time setup the body or Skills name, starts `startup.sh` in development under a pass-through `guard` with `APP_PORT` set to a spare port, waits for any HTTP answer and kills the whole process group, exiting non-zero with the log tail on a failure and reporting "nothing to boot" when there is no `startup.sh`. When `startup.sh` or what its production branch builds changed, it runs again with `--production` on a fresh copy of only what git would track, with no setup, under `OPSIFORCE_ENV=production`. The child would quietly repair a broken Template, so the test alone would look green ([ADR-0063](../adr/0063-the-builder-tests-a-child-agent-by-conversing-with-it-in-one-throwaway-project.md)).
- The Builder drives the Test Project through `scripts/tp.sh`, which keeps the Project, environment, Connection, Session and last prompt id in `scratch/test-project.json`, so each shell call and a resumed chat carry on from the last: `up` finds the Project (the recorded id, else `GET /me`, else a create's 409) or creates it, waits for Development with a three-minute ceiling, retries a `failed` environment once through a restart, reports a disabled Project as `disabled:` and connects, retrying a 503. `prompt`, `answer`, `turn`, `interrupt`, `evidence`, `sh`, `app-url`, `touched`, `restart`, `update` and `reset` cover the rest, and `node --test` covers each against a mock platform and runtime.
- The Builder converses with the child through the public API's Connection, with prompts that read like a user's, and splits the checking with it: the child checks itself as `platform`, `web-app` and its body say, saving screenshots under `/workspace/.cache/checks/`, and what the runtime recorded it running is evidence while its prose is a claim. `scripts/evidence.sh <baseUrl> <sessionId> <messageId>` (`tp.sh evidence`) lists the child's shell calls after a prompt (command, exit code, output) from the Session's messages and copies its screenshots into `scratch/shots/` through the runtime's file-read route. The Builder then uses the result once the way the brief's user would, checks every expectation no recorded command decides, and re-runs at least one covered line — re-running all of them when it disagrees with the record — using the Test Project's shell (`tp.sh sh`, which pages through all of a command's output and exits with its code) and its **own** `agent-browser` pointed at the child's App, which its pod reaches directly. Expectations go into `scratch/expectations.md` before each run — the prompts, sent word for word every round, the machine-checkable and judgement lines, and the `## Fixes` log — and are only added to, so a change that breaks what passed before fails; `scripts/check-expectations.mjs` checks the file's shape. Taste is left to the author, who has the Test Project's preview beside the chat. A secret the job needs is set by the author in the Test Project's Environment settings, and the lines that need it stay *not checked* until it is; a prompt that writes outside the Project targets something the author owns and named in the brief, or is left out.
- The Builder waits for each child turn with `scripts/turn.sh <baseUrl> <sessionId>`, never the runtime's own `wait`, which has no deadline and never returns while a Form holds the turn: it polls `GET /api/session/active` and, once idle, reads the last assistant message's finish reason, exiting 0 on a finished turn and 5 on one that broke off (printing the error); 3 when an open Form (`GET /api/session/{id}/form`) holds the turn, and 4 at its `TURN_TIMEOUT` deadline. The Builder answers a Form as the author's user would, from the brief and the expectations, through `POST /api/session/{id}/form/{formID}/reply` with `{"answer":{"<key>":…}}` (`tp.sh answer`), notes it in the round's report, and `evidence.sh` lists each question with its options and answer, or as still open.
- When the Project has a `startup.sh`, the Builder restarts the Test Project's pod once per round after it is live, through `POST /projects/{id}/restart` — open to the Agent Caller like the other Project routes — and re-runs the line its verdict leans on, because a recreated container keeps only `/workspace` and an App that does not come back has a `startup.sh` that ensures too little ([ADR-0061](../adr/0061-the-platform-harness-is-a-built-in-skill-and-an-agents-prompt-is-the-authors-body-alone.md)).
- The Builder works in rounds: one pass through the whole prompt sequence, re-prompting a slip on the spot and noting every Template, body or Skill fault until the round ends or a blocker ends it early. At round end it logs the round's fixes in the expectations file's `## Fixes`, one line per fix in a fixed grammar (round, failed expectation, whose failure, record, change, the round's refresh), applies them, and runs one check, one save and one refresh — a Reset when the child touched or built on what the change alters or the change is in the body or a Skill, otherwise an Update, the same rule it uses for a change the author asks for. `tp.sh touched`, run after the check and before the save, decides *touched* for Template files: the files the child changed since the last lay, from the Test Project's git, that the save also changes, from `template-snapshot.sh diff` against the last save; it also names each file the save drops, which an Update leaves for the Builder to remove. After a Reset the next round starts from the first prompt; after an Update it re-grades every line on the workspace and sends only the prompts whose lines failed, plus any new one. It stops to ask the author after two fixing rounds in a row that turn no failing line into a pass. A `failed` Test Project is treated as a pod fault: retried once through a restart, then reported as a likely capacity problem. A disabled one is reported as saved, not tested, with a pointer to its pane's menu.
- The verdict is a fixed report shape: every graded expectation is a pass or a fail with exactly one source, *mine* or *the child's record*, and a line nothing decided is *not checked* with its reason. It says which lines passed only after a Template update, links every deciding screenshot labelled by who took it, lists every Form the child raised with its answer, and includes `## Fixes` with one entry per fixing round; before it sends, the Builder runs `check-expectations.mjs` and checks those criteria.

### Refreshing it

- [Dynamic Delivery](dynamic-delivery.md) freezes the definition at creation, so the Test Project is refreshed in place by two public-API routes open only to the gateway key of the chat whose Project created it (`created_by_project_id`); everyone else is refused, and there is no human UI ([ADR-0063](../adr/0063-the-builder-tests-a-child-agent-by-conversing-with-it-in-one-throwaway-project.md)).
- **[Update (Test Project)](../../CONTEXT.md)**, `POST /projects/{id}/test/update`, overlays the saved Development Template onto the workspace, overwriting and adding but never deleting, and commits the files it wrote as "Template update"; a root `.gitignore` it overlays gets every missing platform line appended first, as at create ([Template](template.md)). The pod keeps running, the conversation carries on and the Bifrost spend keeps its running total; the Builder removes a dropped file through the shell and restarts the pod itself when something that runs changed.
- **[Reset (Test Project)](../../CONTEXT.md)**, `POST /projects/{id}/test/reset`, stops the pod, wipes the workspace, lays the Template, prompt and Skills from Development as a create does, clears the pinned session id so the next Connect binds a new one, resets the Project's Bifrost spend and starts the pod, so first boot runs again. The Project row, the side pane and the preview URL stay the same.

## Edge cases

- When the Builder's pod resumes, the hidden-kind exclusion means it cannot find its Test Project by listing; `tp.sh up` reads the id it recorded, else `GET /me`'s `builderTestProject`, else the id a create's 409 carries.
- A chat older than the fixed scratch names keeps `scratch/<agent>.expectations.md`; `tp.sh up` renames a lone one to `scratch/expectations.md`.

## Code

- `backend/src/builder/` — the chat's one Test Project and the `kind: "test"` create check.
- `backend/src/project/project.service.ts` — Update (Test Project) and Reset (Test Project).
- `backend/src/public-api/projects/` — the `test/update` and `test/reset` routes and who may call them.
- `agent-config/agents/skill-agent-builder/skills/agent-authoring/references/test-loop.md` — the Builder's whole testing contract: the rounds, the expectations file, the update-or-reset rule and the report shape with its completion checks.
- `agent-config/agents/skill-agent-builder/template/scripts/` — `tp.sh`, `check-template.sh`, `check-expectations.mjs`, `evidence.sh`, `turn.sh` and the API helpers the Builder runs.
