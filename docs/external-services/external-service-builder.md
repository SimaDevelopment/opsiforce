# External Service Builder

> How does an Organization write, test, publish and retire its own External Service, and which of its environments do callers reach?

## How it works

### The builder chat

- With `can_manage_tenant_external_services`, Store, External Services, **New External Service** takes a name and a slug (2 to 31 lowercase letters, digits and hyphens starting with a letter; never a built-in's name, another of the Organization's services or a reserved name) through `POST /api/external-services/services`. It registers the [Custom External Service](../../GLOSSARY.md) and its builder Project (kind `external_service_builder_chat`) and opens the chat at `/store/external-services/<id>/builder`; the slug can change (`PATCH …/services/<id>`) until the first Publish, and stored secrets stay readable because they are sealed under the service's id.
- Only holders of that permission open or chat in a builder Project and its Test Project, in every environment, because the pod shares a container with the service's secrets ([ADR-0078](../adr/0078-an-external-service-fetches-its-configurations-from-the-backend-by-the-caller-identity-and-holds-them-only-in-memory.md), [Permissions](../organization/permissions.md)).
- The chat runs the [External Service Builder](../../GLOSSARY.md), the Built-in Agent `external-service-builder`: shared skills `platform` and `sqlite`, its own `external-service-authoring` skill, no Public API and no route to Publish. Its template is an empty, valid SDK 2 service in `app/` with no routes, so every request starts *not supported*: `service.json` (`sdk: 2`), `service.ts` (`defineService({ manifest, routes: [] })`), `src/upstreams.ts`, empty `src/groups/` and `test/groups/`, `test/service.test.ts` (a request outside every group refused through `testService(service, …).fetch`), a skeleton `SKILL.md` and `README.md`, and `startup.sh` running `external-service-cli dev` in Development and `yarn install --immutable` + `serve` in Production, each under `guard service` so its output reaches the process logs, which serve the folder ([Agent](../agent-system/agent.md)).
- The builder's prompt holds four rules: follow the upstream (pass its own API through, and answer a request itself only when there is no HTTP API, for a client shim, or when the person insists after one pushback); nothing passes without a setting; refuse so the user knows what to do (what and why, what would allow it or whom to ask, which setting, the link); a human publishes, and the builder reports what is true. It also keeps the chat lean: each skill loaded once, references re-read by section, the upstream researched into files under `/workspace/.cache/upstream/` (downloaded API descriptions queried with `jq`, long docs read by a sub-task that writes notes) rather than pasted into the chat. Its `external-service-authoring` skill holds the order of work, with four points where the builder waits for the person (the brief's questions, Stop 1, the consumer prompt, the hand-over): a brief naming where the upstream runs and the tools that will call (curl, the upstream's CLI or SDK, App code), a read-only exploration of the upstream kept in `/workspace/.cache/upstream/notes.md` (including what a CLI asks a self-hosted host at startup, which becomes a client shim when the upstream lacks it), then **Stop 1**, where the person approves the narrowest upstream credential and its permissions, the upstream's own protections, both forms with their defaults (an address left blank means the upstream's public service; targets picked from a list the service reads live with its credential), the pass-through groups (one read group per kind of target, one group per kind of change, each off by default, everything else *not supported*) with their checks in plain words (a hidden target answers like a missing one wherever a caller could guess it, by name or a guessable key, and is refused as *not allowed* naming the setting only when named by an id the caller was handed), the Event types and how a Project chooses what it hears, the Usage counters, what is not in this version and the Service skill's outline. Code and unit tests per group follow, then the Service skill, live tests as the Test Project, `app/PUBLISH.md` and the hand-over; any later change to groups, checks, forms, Event types or counters goes back to the person (a change the person's own reply decides is made and shown, not asked again), while a bug fix inside an approved check does not. A problem in the Service form is refused naming the Organization admin and the service's page, never a Project setting. The skill's references cover the manifest, routes and upstreams, form handlers and hooks, inbound, testing, the Service skill, Stop 1 and the hand-over, and `references/patterns.md` holds generic snippets in place of a reference service.
- The service carries its own SDK: `app/package.json` names `file:./vendor/external-service-sdk-<version>.tgz`, installed under Yarn Plug'n'Play with the SDK unplugged, so it runs the version it was published with until someone asks the builder to upgrade it ([ADR-0081](../adr/0081-a-custom-external-service-carries-its-own-copy-of-the-sdk-and-upgrades-it-only-when-asked.md)). The image keeps the newest SDK unpacked at `/opt/opsiforce/external-service-sdk/latest/` and the built-ins read-only at `/opt/agents/external-service-builder/reference/<name>/`. The version the page calls newest is the SDK `package.json` the backend was built from, the same file the agent image packs; CI keeps the two in step by refusing an SDK source change without a new SDK version and a new agent image version.

### The test lane

- The chat's [Test Project](../../GLOSSARY.md) runs a consumer Agent whose calls the [Gate](gate.md) sends to the service's Development (the builder Project's own ProjectEnvironment, published or not), with Development's manifest and its own Service configuration (sealed with `+development`, empty until an Organization admin saves it or copies the callers' one through `…/services/<id>/development[/configuration]` and `…/development/configuration/copy-from-production`; a save, Rotate or copy runs Development's `onServiceConfigurationSaved`, with Retry at `…/development/configuration/hook/retry`). Its webhook URL is `…/webhooks/<id>/development`, whose Events reach only that Test Project, and its `ctx.state` is the file in Development's own data folder ([ADR-0086](../adr/0086-the-external-service-builder-tests-a-service-through-a-consumer-agent-against-developments-own-service-configuration.md)).
- The builder's pod drives the lane with its own Gateway Key (`Authorization: Bearer $SERVICE_GATEWAY_API_KEY`) at `$SERVICE_GATEWAY_URL/_builder` (`/api/gateway/_builder`), answered only for the default ProjectEnvironment of a builder chat (`401` without a key, `403 not-a-builder-chat` for any other): `GET` (slug, name, `service.serviceHost` = `https://<slug>.<externalServicesHost>` or null when unset, Development's `webhookUrl`, servability, its saved Service configuration (values, secrets masked) and the missing required Service-form fields, and the Test Project with its `gatewayKey`, so the builder calls Development as that Project with curl or the upstream's own clients), `POST test-project` (once), `GET/PUT test-project/configuration` (`saved`, masked `values` and `missing`; a save answers `revealed` once, like any save), `GET test-project/events`, `POST test-project/update` (delivers the Service skill again from Development) and `POST test-project/reset` (the Test Project Reset, which wipes the Test Project's workspace and so its Events, runs `onProjectConfigurationSaved` with `current: null` for Development, deregisters Development's own registrations through `onServiceConfigurationSaved` with `current: null`, deletes Development's `ctx.state` and registers them again with `previous: null`; Development's `data/service-records.db` stays as the test report's evidence). Two probes: `POST probe/{options|info|buttons}/<name>` runs a Project-form handler as `platform` for the Test Project's ProjectEnvironment, on the draft sent, and `POST probe/service/{options|info|buttons}/<name>` runs a Service-form handler as `platform` naming no ProjectEnvironment, on Development's saved Service configuration with any `values` sent laid over it.
- Conversation prompts go through the person, in the Test Project's pane beside the chat. `external-service-cli report` writes `/workspace/.cache/service-test-report.json` (commit, manifest hash and one line per expectation with its result, source and Call ids) for the Publish dialog. The Call ids are request ids in Development's `data/service-records.db` (`calls.request_id`, read like the Calls tab): a line citing a `proxied` request means the upstream was called, and an id the file lacks is listed in `unknownCallIds`.

### Publish

- A human publishes from the service page, never the builder; the Project Publish route answers `409 publish-from-service-page` for a builder Project. The Publish dialog has the Custom Agent's layout: one row per environment (badge, name, "Published · <commit>" or "Not published yet"), a "What <Environment> will receive" card holding the review, a **Callers reach** select of the published environments, and **Publish to <Environment>**. `GET …/services/<id>/publish?environmentId=` is the dialog's review: the `check` report of Development's `app/`, with each Event type marked added, changed (title or description) or unchanged against the version published in the chosen environment and the ones Development drops listed as removed, the impact on every Project configuration read tolerantly against the new manifest (shown when the target is or becomes the Default environment), the test report with what changed since its commit (it warns and never blocks), and the Service form fields the callers' configuration lacks (all of them on the first Publish), each with "Copy from Development".
- The review opens with the test warnings (`testWarnings`: "No test report", "Changed since the test", "Never called the real upstream"; never blocking) and the builder's Publish note, `app/PUBLISH.md` rendered as is (`publishNote`, null = a warning). Then come `formChanges` for both forms (each field added, removed, renamed via `was`, or with its type, default, required, options or limits changed; a list field also names its changed item fields), the Events diff, the impact including `newDefaults` ("new setting X = default in N configurations"), the Service configuration's own new fields and defaults, the test report, `skillDiff` (`app/SKILL.md`) and the collapsed `codeDiff` of `app/` between the Default environment's deployed commit and Development's working tree, untracked files included (the empty tree before the first Publish, 512 KB at most). It asks for no per-item confirmation. A service built on SDK 1 is reviewed with `builtOnSdk1` set, and the dialog says it must be rebuilt on SDK 2 and offers no Publish.
- `POST …/publish {environmentId, values, copyFromDevelopment}` refuses a service built on SDK 1 (`409 built-on-sdk-1`) or a failing `check` (`409 check-failed`), then probes Development, waking it like a caller: a request with no Caller identity must answer `401` with `Opsiforce-Outcome: unidentified`, and a `call` identity for a ProjectEnvironment of the builder chat with no Project configuration must answer `403` with `Opsiforce-Outcome: not connected`; anything else, or no answer in 10 s, is `409 probe-failed` naming what Development answered and what it must answer. It then refuses an unmet required field (`400 invalid-configuration`), saves the listed fields beside the stored values the live version still reads under a renamed field's old key, defers `onServiceConfigurationSaved` to the new version and queues the Project Publish without Environment Variables or Schedules; `GET …/publish/job` follows it, and `GET …/environments` lists the published version in each environment.
- The first Publish sets the [Default environment (External Service)](../../GLOSSARY.md), never Development; `GET/PUT …/default-environment` switches it to another environment holding a finished Publish (`409 not-published`), after the same review, which the dialog shows in place when **Callers reach** is changed. Whenever a version becomes the Default environment's, the platform writes each field default into every stored callers' Service configuration and Project configuration that has neither the field nor its `was` key (a value that no longer fits stays and counts as missing, removed fields stay stored; a Built-in does the same at boot), fills newly generated fields, runs the deferred hook and delivers the Service skill again ([Publish](../projects/publish.md)).

### The Default environment

- Every caller but the Test Project reaches the Default environment: Service routes, form calls, hooks and webhooks. Its code keeps `ctx.state` in the Default environment's own file. Its manifest, Service skill text, icon and SDK version are read from its `app/` on the shared volume, cached by modification time, so a Publish is picked up without waking the pod ([ADR-0083](../adr/0083-a-custom-external-services-default-environment-never-sleeps-its-state-lives-in-that-environments-workspace-and-is-copied-on-a-switch-and-its-webhook-url-belongs-to-the-service.md)). A file there (or under a linked directory) that resolves outside `app/`, or isn't a regular file, counts as missing: a `service.json` or icon like that makes the service unservable, and a `SKILL.md` or `package.json` like that is ignored; the Publish review and the test report read the same way.
- The Default environment never idle-sleeps; a down pod is woken and the call held up to 60 s. The webhook URL belongs to the service. A switch holds the platform's own new calls with `503 service-reloading` (a form call or hook routed to the old Default just before the switch is refused rather than run there), lets the calls in flight finish on the old pod (up to 30 s, else `409 service-busy`), copies the old Default's `ctx.state` file over the new one's and only then moves callers and inbound, so callers, state and inbound move at once. A caller's or webhook's resolve answer waits inside the Gate's 60 s hold while the switch holds the lane (`504` past it), the switch also copies `data/service-records.db` (opened read-only, retried while a commit is in flight; one that stays busy is left behind with a warning rather than failing the switch), and the Gate's cache for the slug is evicted (`POST /evict` on every replica behind `EXTERNAL_SERVICE_PROXY_CONTROL`) before the hold ends.

### The service page

- The page shows "<Environment> · default" once the first Publish sets it; until then its Environments list shows Development as where the builder edits and every other environment as not published yet, as an Agent's page does. It also shows an SDK badge ("SDK 2.0.0", "· 2.1.0 available" when this release ships a newer SDK of the same major, "needs upgrade" once the platform no longer accepts it), **Edit in Builder**, **Publish** and an actions menu with Copy webhook URL, Download service.json, Duplicate, Export, Disable or Enable and Delete ([Settings](../organization/settings.md)); the list offers **Import service** beside New External Service ([Service copies](service-copies.md)).
- The Overview tab of a custom service has the Custom Agent page's **Environments** list beside it: Development ("Where you edit") and every other environment, each "Same as Development", "Development differs" (Development's `app/` changed since the commit published there) or "Not published yet", with **Default** on the one callers reach. The selected row lives in the URL (`?env=`) and starts on the Default environment (Development before the first Publish); Events show that environment's manifest, read from its `app/` by `GET …/services/<id>/manifests`. Away from the Default environment each Event type is marked added or changed against the Default's manifest, and one it drops is listed struck through as removed. The Configuration tab, and a built-in service's page, show only what callers reach.
- A service built on SDK 1 (its manifest says `"sdk": 1` or it vendors an SDK of major 1) is served nowhere: its page loads, its Overview says "Built on SDK 1, rebuild or delete" and nothing else, it shows no other tab and no Publish, and Edit in Builder, Disable and Delete still work. The platform converts nothing.
- Disable (`POST …/services/<id>/disable`) disables the builder Project: its pods stop, cutting open streams, the backend evicts the Gate's cached callers of the service, its next call or webhook is refused `404` "<service> is turned off in this Organization", Project forms, the chat bar and Agents stop seeing it (its Service skill is delivered again to every environment that had it), and everything is kept until Enable, which delivers it again the same way. The Project routes' Disable and Enable of the builder Project do exactly the same; their Delete of the builder Project or of one of its environments answers `409 manage-from-service-page`, and the Project menu offers neither. The Overview tab lists the consuming ProjectEnvironments as Connected Projects, each with Disconnect ([Configuration](configuration.md)). Delete lists them too (`GET …/consumers`), needs the slug typed (`DELETE …/services/<id>?confirmSlug=<slug>`, else `400 slug-mismatch`), runs `onProjectConfigurationSaved` with `current: null` for each consumer on the version it reaches (Development for the Test Project, unpublished services included, whose sleeping pod is woken first within the 60 s start hold; none while the service is disabled; 10 s each once the pod serves, failures logged) and deletes the builder Project with every configuration, state and not-wired mark, and its Service skill with every Agent's pin of it; callers then get `404` and the slug is free.

## Edge cases

- When the builder chat has no Development Service configuration, its live test lines are reported not checked.
- When the vendored SDK is of an older major than the platform accepts, the service is built on SDK 1: its calls and webhooks answer `404`, the page says "needs upgrade" and "Built on SDK 1, rebuild or delete", and Publish answers `409 built-on-sdk-1`.
- When a Built-in External Service later takes a custom service's slug, the built-in stays hidden in that Organization and the service page says so.
- When a Delete's consumer hook fails, the Delete goes on and the failure is logged.

## Code

- `backend/src/external-services/custom/` — creating a service and its builder chat, the `_builder` lane, Disable, Enable and Delete.
- `backend/src/external-services/publishing/` — the Publish review, the `check`, impact and test reports, the manifest of each environment and the diff between two manifests, the SDK status, and the Default environment with the first-Publish hook.
- `backend/src/external-services/registry/` — reading a published service from its files.
- `backend/src/external-services/test-lane/` — the Test Project's starting Project configuration, its Update and its Reset.
- `backend/src/external-services/external-services-project-lifecycle.ts` — what External Services does when a Project is created, disabled, enabled, reset or removed.
- `agent-config/agents/external-service-builder/` — the agent, its authoring skill and the service template.
- `frontend/src/pages/store/external-service-page.tsx` — the service page, its header, tabs and dialogs.
