# Incoming Email

> How does a ProjectEnvironment get a receiving email address, and what happens when mail arrives at it?

## How it works

- Incoming email is a [Built-in External Service](../../GLOSSARY.md) written on SDK 2: the folder `external-services/incoming-email/` holds its `service.json`, `service.ts` (one Service route, `GET /address`, and the `webhook` handler from `src/webhook.ts`), its Service skill `SKILL.md` and `test/inbound.test.ts` ([Service manifest](service-manifest.md)). It runs in the backend behind the [built-ins adapter](call-log.md#built-ins). The address is generated by the Project form, so it has no save hook. Sending mail is a different feature.
- Its [Service configuration](../../GLOSSARY.md), set by the platform operator on its page under Store, External Services, is the Mailgun receiving domain (`receivingDomain`), the account's webhook signing key (`signingKey`, sealed) and the largest attachment kept (`maxAttachmentMb`, default and cap 25). With the domain and key filled it is Available; without them it shows "Needs setup", Organizations do not see it, and its webhook answers 503 so Mailgun retries.
- Upgrading a deployment needs no operator step: at boot, when `MAILGUN_RECEIVE_DOMAIN` (falling back to `MAILGUN_DOMAIN`) and `MAILGUN_WEBHOOK_SIGNING_KEY` are both set and no Service configuration is stored yet, the backend writes one from them; a stored one is never overwritten. The variables and this importer go a release later.
- A [ProjectEnvironment](../../GLOSSARY.md)'s address is its [Project configuration](../../GLOSSARY.md): `localPart`, 16 random characters from `a-z0-9`, unique across the deployment, and the rendered `address` = `<localPart>@<receivingDomain>`, shown with Copy in the chat bar's dialog. An Agent or App reads it at `GET https://incoming-email.$EXTERNAL_SERVICES_HOST/address` (`{"address"}`; *not connected* before the first save). A blank `localPart` renders the address blank.
- The address exists from the first save and changes only by a confirmed Rotate in that dialog; Disconnect deletes it and stops delivery. [Development](../../GLOSSARY.md) and each published environment have their own address: a [Publish](../projects/publish.md) never copies one, and the target keeps its own or gets a fresh one.
- Mailgun holds the receiving domain's MX records and one catch-all Route forwarding every recipient to `<OPSIFORCE_PUBLIC_URL>/api/external-services/webhooks/incoming-email` as a parsed multipart POST, attachments as file parts; the platform never parses MIME. The Gate's webhook lane forwards it to the adapter's `/.well-known/opsiforce/webhook`.
- The handler checks Mailgun's HMAC-SHA256 over `timestamp + token` against the signing key in constant time and refuses a signature older or newer than 300 s (401). It turns the forward into one `email.received` Event per recipient: `address` (the local part), `recipient`, the envelope sender as `from`, `fromHeader`, `subject`, `text` (Mailgun's stripped text, else the plain body), both bodies, `messageId`, `headers` and `attachments`, with each attachment as an Event file and the ones over `maxAttachmentMb` listed in `omittedAttachments` instead. The Event key is the `Message-Id`, falling back to the signature token, so a redelivered email is stored once.
- The handler picks the receivers itself: from `projectConfigurations()` it delivers each recipient's Event to the configurations whose `localPart` equals the recipient's local part (`deliver()`, [Event](events.md)). The recipient's domain is not checked, so an address issued on an earlier domain keeps receiving while Mailgun still forwards that domain. Each stored Event counts `events` on the service page's Usage.
- The Agent learns the service from its Service skill `service-incoming-email`, which a ProjectEnvironment receives once the service is enabled in its chat bar, or when its Agent carries it. The App reads the Event from `events` and `event_files` and is rung with `eventIds` ([Event](events.md)).
- External Services v2 retired the v1 Built-in Skill `incoming-email`. Once, at boot, every Agent Profile pinning it, on every Environment, pins `service-incoming-email` at its current Version instead, with no [Service settings (Agent)](../../GLOSSARY.md), or just drops the old pin where the profile already carries `service-incoming-email`; a ProjectEnvironment that switched `incoming-email` off has `service-incoming-email` switched off instead. Each Agent swapped gets a Service skill fan-out, so its existing Projects receive `service-incoming-email` and lose `incoming-email`. An Agent import that pins `incoming-email` gets `service-incoming-email` with a note ([Agent copies](../agent-system/agent-copies.md)).
- An environment with a v1 address has a Project configuration holding that address's local part (even one on another domain). An environment with a v1 address, even one that never received an email, or whose `external-services.db` already held `messages` rows is a legacy environment and also gets each email as a `messages` row with inline `attachments`, and `rowIds` in its ring.

## Edge cases

- When the signature fields are missing, wrong or stale, the webhook answers 401 and stores nothing.
- When no configuration has the recipient's local part, the webhook answers 200 and notes `unmatchedRecipients`; Mailgun does not bounce the sender.
- When a receiver is over the Event cap, the webhook answers 503 and Mailgun retries; the `Message-Id` key keeps the other receivers from doubling.
- When the Mailgun settings do not fit the Service form (say a malformed domain), the importer logs an error and writes nothing; the operator fills the form instead.
- When a v1 address collides with one another environment already holds, both environments keep it and both receive mail sent to it.

## Code

- `external-services/incoming-email/` — the manifest, `service.ts`, `src/webhook.ts` (Mailgun signature, attachments, receivers, Event mapping), the Service skill and its tests (`yarn workspace @opsiforce/external-services test`).
- `backend/src/external-services/upgrade/incoming-email-upgrade.ts` — the one-release importer of the Mailgun settings.
- `backend/src/external-services/upgrade/retired-skill-swap-upgrade.ts` — the one-release swap of `whatsapp` and `incoming-email` pins for their Service skills.
- `backend/db/migrations/0076_external-services-v2.sql` — the External Services v2 schema, including the move of v1 addresses.
- `backend/src/external-services/legacy/legacy-messages.ts` — the `messages` row a legacy environment gets for each email.
