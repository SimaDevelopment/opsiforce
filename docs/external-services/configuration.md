# Configuration

> Where are an External Service's two configurations stored, who edits them, and what happens when one is saved or its manifest changes?

## How it works

### Two levels

- A [Service configuration](../../GLOSSARY.md) is one `external_service_configs` row per service and owner: the platform's for a [Built-in External Service](../../GLOSSARY.md), edited by the platform operator on its Store page (`PUT /api/external-services/platform/services/<id>/configuration`, `can_manage_platform_external_services`), and the Organization's for a [Custom External Service](../../GLOSSARY.md) (`PUT …/services/<id>/configuration`, `can_manage_tenant_external_services`), which also has Development's own row that only test calls read ([External Service Builder](external-service-builder.md)).
- A [Project configuration](../../GLOSSARY.md) is one `external_service_project_configs` row per service and ProjectEnvironment, GIN-indexed on its values. It holds the [Form](../../GLOSSARY.md)'s values and the reserved key `_labels` (the label of every value picked from a callback), which service code never sees.
- Every `secret` is sealed with AES-256-GCM under `EXTERNAL_SERVICES_ENCRYPTION_KEY`, its associated data naming the service by its id, the owner (a Service configuration's `platform` or tenant id, plus `+development` for Development's row; a Project configuration's `environment:<projectEnvironmentId>`) and the field path with item ids, so a value opens only where it was sealed ([ADR-0080](../adr/0080-built-in-vendor-settings-live-in-service-configuration-and-sealed-secrets-are-bound-to-their-place.md)). The backend refuses to boot without a well-formed key, and the Helm chart refuses to render without one.
- A service is [Available](../../GLOSSARY.md) while its callers' Service configuration validates against its Service form: until then the operator's page says "Needs setup" and no Organization sees it in the Store, the chat bar or an Agent's picker. Calls from Projects already connected are not refused for it: the SDK hands the missing keys to route code as `ctx.missingServiceFields`, and only a Project configuration missing a required field is refused as incomplete.

### Reading against a changed manifest

- Stored values are kept as saved and read against the current manifest tolerantly: a field's `was` moves an old value to its new key, a value that no longer fits counts as missing (a required one makes the configuration "Needs attention", naming each such field by its labels, such as "Numbers › Number", and the service's SDK refuse that ProjectEnvironment's calls as incomplete), and removed keys stay stored but are never delivered ([ADR-0079](../adr/0079-a-changed-service-manifest-reads-old-configurations-tolerantly-and-a-publish-writes-each-new-fields-default-into-them.md)).
- A new Project configuration starts from the Project form's defaults. Every new Project, of any Agent, starts with one for each Available service whose manifest sets `"connectedByDefault": true` (Incoming email), written and announced like the Service settings (Agent) below, which overlay it; a Disconnect stays ([ADR-0095](../adr/0095-a-service-manifest-can-connect-every-new-project-to-the-service.md)). A new Skill & Agent Builder chat starts with a `public-api` one whose authoring, Create Projects and Manage created Projects settings are on ([Public API built-in](public-api.md)).
- A Project of a Custom Agent starts with a stored Project configuration for every Available service whose [Service settings (Agent)](../../GLOSSARY.md) its Agent Profile holds: on create (UI, Public API, Workspace) and for the Agent's [Test Project](../agent-system/test-project.md) it is written before the Agent's files are delivered and announced after, for a Project Duplicate or Import once the files are in place, its Service skills delivered before the hook runs. It holds the Project form's defaults overlaid with the settings' field values, ignoring any key the service no longer offers as a setting. No target is picked. A complete configuration runs `onProjectConfigurationSaved` as the platform, naming no person; a failure is the usual "Saved, but …" and the Project is still created. One a required target leaves "Needs attention" runs no hook until someone saves it with the targets picked ([ADR-0089](../adr/0089-a-custom-agents-service-settings-seed-a-real-project-configuration-in-every-new-project.md)).

### Read by the service

- A service fetches its configurations itself with its pod's Gateway Key ([ADR-0078](../adr/0078-an-external-service-fetches-its-configurations-from-the-backend-by-the-caller-identity-and-holds-them-only-in-memory.md)): `GET $SERVICE_GATEWAY_URL/configuration`, with the request's Caller identity when it asks for a caller, answers the whole Service configuration and the named ProjectEnvironment's Project configuration (or `null`, not connected) with secrets opened, the required fields missing from each, and the settings link `<OPSIFORCE_PUBLIC_URL>/projects/<projectId>?configure=<slug>`, with `&environment=<projectEnvironmentId>` when the caller is not the Project's Development environment. The asking pod's key picks the Service configuration: Development's own for Development's pod.
- `GET $SERVICE_GATEWAY_URL/configuration/projects` lists every Project configuration of the copy's lane opened, the Test Project's for Development and every other one for the Default copy. The SDK keeps each answer in memory for at most 5 s, drops the kept copy when a save hook reaches it (before the service's own hook runs, declared or not), and refuses a caller as not connected or incomplete before any of the service's code runs.
- Form calls and save hooks reach a service's pod directly at `POST /.well-known/opsiforce/{options|info|buttons|hooks}/<name>` with a `platform` Caller identity, naming the ProjectEnvironment for a Project-form call and `onProjectConfigurationSaved` and none for a Service-form call and `onServiceConfigurationSaved`. The body is `{form, values, query?, item?}` (the whole draft with stored secrets merged and opened; `item` names a list item's id) or `{previous, current}`, with no `context` and no cut to referenced items. A Project-form handler sees the saved configurations beside the draft; a Service-form handler sees the draft as its Service configuration, while `service.configuration()` stays the saved copy. The SDK answers an undeclared hook `204`, so a missing hook never counts as "none", and refuses an answer holding a secret of the Service configuration as `failed`.

### Where Project configurations are edited

- `/api/external-services/projects/<projectId>/environments/<projectEnvironmentId>/services` serves the chat bar under a Project's composer: every service Available to the Organization, each `enabled` (a configuration is stored here), `needs-configuration` (the Agent carries its [Service skill](service-skill.md), nothing is stored here) or `available` (neither), with its configuration state (`saved` and the `missing` fields), which the chat bar shows as **Connected** or **Needs attention**; one service's Project configuration (secrets masked, Service configuration items by label only, the `missing` fields); and `PUT …/<serviceId>/configuration`, whose first save enables the service here and delivers its Service skill to this ProjectEnvironment (the dialog's button reads Connect until then, Save after). Anyone who can open the Project reads; saving needs `can_configure_project_external_services`, and without it the dialog opens read-only, saying an Organization admin or anyone with that permission can change it.
- The dialog shows the service's Project form and its Calls. `/projects/<projectId>?configure=<slug>&field=<key>` (optionally `&environment=<projectEnvironmentId>`, default the Project's Development environment) opens it on that field, scrolled into view and highlighted, opening a collapsed section that holds it; an unknown slug says no such service is available to the Project. A refusal's settings link is this address.
- Disconnect (`DELETE …/<serviceId>/configuration` under the chat bar's prefix, for `can_configure_project_external_services` or `can_manage_tenant_external_services`; the service page's Connected Projects list offers the same as `DELETE /api/external-services/services/<id>/consumers/<projectEnvironmentId>` for `can_manage_tenant_external_services`) deletes one ProjectEnvironment's Project configuration, queues a skill delivery so its Service skill leaves that environment unless its Agent carries it, then sends `onProjectConfigurationSaved` with `current: null` (best effort, failures logged, none while the service is disabled). The service drops its kept copy on that hook and fetches "none", so the next call is refused as not connected; a request already running keeps the configuration it read. Reconnecting is filling the form again.
- Form calls let a form ask its service while someone edits it: `POST …/<serviceId>/{options|info|buttons}/<name>` under the chat bar's prefix, the operator's `platform/services/<id>/…` or the Organization's `services/<id>/…`, each with `{values, query?, item?}`. `values` are the unsaved values with stored secrets merged into blank secret boxes on the server; a callback inside a `list` item names the item; a Project form call carries a Caller identity for the environment being edited. Form calls time out after 10 s, never write configuration and pass the platform's answer checks ([Gate](gate.md)); an unknown name is `404 unknown-callback`.
- The renderer (`external-service-form/`) is the same for every service and level: chips, searchable and dependent pickers, "no longer found" for a stored pick a callback stopped returning, "stored · encrypted" with Replace, the one-time reveal, Rotate, `info` Copy and badges, and button results.

### Saving

- Every save of either level goes through one form save. A `list` item gets a platform id (`li_…`) on its first save and keeps it, so references and sealing places follow the item; a blank secret keeps the stored one; callback-sourced values are only shape-checked.
- A `generate` field empty on save is filled by the platform, so the form never asks for it even when it is `required`. `unique: true` (on `text` only) is checked on save against every other configuration of the service, in the save's transaction under a lock per service and field: a generated collision is generated again, a typed one answers `400 invalid-configuration` "is taken", and a value the configuration already stores is never taken from it, even when another configuration holds it too. The save response's `revealed` carries each secret it generated, once; afterwards it reads `{stored: true}` and a lost value means Rotate.
- Rotate (`POST …/configuration/rotate {field, item?}`) generates a new value for one generated field, reveals a secret once and counts as a save. A built-in's new manifest that declares `generate` on a field stored configurations left empty is filled at boot, without a hook.
- After-save hooks run after the commit: `onServiceConfigurationSaved` and `onProjectConfigurationSaved`, both with `{previous, current}` opened, 10 s plus 5 s of grace. A failure never rolls the save back: the response carries `hookFailure` ("Saved, but … [Discard] [Retry]"), `previous` stays the last version the service acknowledged (`null` for a Project configuration stored while it still "Needs attention", whose hook never ran; a goodbye with `current: null` at a Project or environment removal skips any configuration that is missing a required field, while a Disconnect sends it to every configuration that was saved), kept on the configuration itself with any secret moved by a `was` rename sealed again at its new key, and `POST …/configuration/hook/retry` (Development's: `…/development/configuration/hook/retry`) runs it again, while `POST …/configuration/hook/discard` (Development's: `…/development/configuration/hook/discard`) forgets the pending hook without calling the service, under the same permission as a retry. Form saves, Rotate, a Copy from Production into Development, a Publish carry, the cascade below and a service's Delete (`current: null`) all fire hooks.
- Saving the callers' Service configuration without a `list` item strips every Project configuration's reference to it in the same transaction, logs it, fires that Project configuration's hook and leaves a notice its dialog shows once.

## Edge cases

- When a hook fails or times out, the values stay saved and the page offers Retry until a hook answers, or Discard to stop waiting for the service to apply that save.
- When a Publish (App) carries a Project configuration, it overwrites the target's values and never copies a unique generated value ([Publish](../projects/publish.md)).
- When a Project or a ProjectEnvironment is deleted, each of its Project configurations first runs `onProjectConfigurationSaved` with `current: null` on the version that environment reaches (best effort, 10 s plus 5 s of grace, skipped while the service is disabled), then goes.
- When a typed value of a `unique` field is already held by another configuration, the save answers `400 invalid-configuration` and stores nothing.
- When a deployment upgrades past SDK 1, migration `0081_sdk-1-removed` drops the `operations` and `receive` keys from every stored Project configuration, turns an Agent's `public-api` Service settings into the five Public API settings ([Public API built-in](public-api.md)), and clears every other Service settings (Agent) still holding them, so those Agents' new Projects start from the form's defaults until an editor sets them again.

## Code

- `backend/src/external-services/configuration/` — both stores, the form save, generated values, Rotate, hooks, the cascade, tolerant reads and Available.
- `backend/src/external-services/http/` — the operator, Organization and chat bar routes.
- `backend/src/external-services/test-lane/configurations-at-create.ts` — the configurations a new Project starts with: the service under test, a Custom Agent's Service settings (Agent) and every service that connects new Projects.
- `backend/src/sealing/secret-sealer.ts` — the place-bound sealing.
- `frontend/src/components/external-service-form/` — the one renderer every Form goes through.
- `frontend/src/components/project/external-services/` — the chat bar button and the Project configuration dialog.
