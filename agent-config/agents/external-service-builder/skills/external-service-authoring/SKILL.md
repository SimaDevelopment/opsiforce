# Authoring a Custom External Service

A Custom External Service is the one program that speaks to one outside system for this
Organization. Agents and Apps never reach it directly: every call passes the platform's **Gate**,
which checks the caller's switches, the input and the bounds before your handler runs, and records a
Call log row. Your job is a service the Gate can guard well: Operations that say what they do, inputs
that say what they touch, and handlers that refuse what the Gate cannot see.

The service is the folder `/workspace/app`:

| File | What it is |
| --- | --- |
| `service.json` | The Service manifest: header, Service form, Project form, Operations, bounds, Events, `$defs` |
| `service.types.ts` | Generated from `service.json`; never edit it, always commit it |
| `handlers.ts` | Wiring only: `export default defineHandlers<Manifest>({ manifestHash, … })`, one entry per name the manifest uses, each a function from `src/` |
| `src/` | The code, one file per part of the service (§Layout) |
| `test/` | `node:test` tests on the SDK test kit, mirroring `src/` |
| `SKILL.md` | The Service skill every consuming Agent reads (`references/service-skill.md`) |
| `README.md` | Optional, for maintainers: upstream docs, decisions, how to test |
| `icon.svg` | Optional, at most 32 KB, no scripts, no event attributes, no outside links |
| `vendor/external-service-sdk-<version>.tgz` | The SDK this service runs, installed unplugged |

## Layout

Every service has this shape from its first Operation, however small, and every built-in in
`reference/` has it too:

```
service.json             the API
service.types.ts         generated
openapi-routes.json      generated by `generate --from-openapi`, only when the service wraps an OpenAPI document
handlers.ts              wiring only: defineHandlers({ … }) naming functions from src/
src/
├─ client.ts             the outside system: base URL, auth, error → refusal mapping, pagination, rate limits
├─ bounds.ts             indirect-id checks
├─ operations/<area>.ts  one file per capability area
├─ forms.ts              options, info and buttons
├─ hooks.ts              save hooks (webhook registration)
└─ inbound.ts            signature check, payload → Event mapping
test/                    operations/<area>.test.ts, inbound.test.ts, …
└─ fixtures/             recorded upstream payloads, redacted
SKILL.md
README.md, icon.svg      optional
```

- A `src/` file exists only when the service has that part.
- `client.ts` is the only file that knows the outside system's URLs and error format.
- A new capability area is one new `src/operations/<area>.ts`, its test and its manifest entries.
- Tests mirror the `src/` files that hold logic. Shared test setup and fixtures may be `.ts` modules.
- An area file past ~300 lines or ~6 Operations becomes `operations/<area>/<operation>.ts` with an `index.ts`.
- A `client.ts` past ~250 lines becomes `client/` (`http.ts`, `errors.ts`, `pagination.ts`).

## Where the truth is

- **The SDK this service runs**: its README, CHANGELOG and `.d.ts` files are plain files under
  `.yarn/unplugged/` (find them with `find .yarn/unplugged -path '*external-service-sdk*' -name README.md`).
  When a reference here and those files disagree, the files win.
- **The newest SDK this image ships**, read-only: `/opt/opsiforce/external-service-sdk/latest/`
  (`README.md`, `CHANGELOG.md`, `service.schema.json`, `dist/*.d.ts`).
- **Worked examples**, read-only: the Built-in External Services in
  `/opt/agents/external-service-builder/reference/<name>/`, each a folder in the same shape as yours
  with its own tests and `SKILL.md`. Read them for patterns; never copy their files or their vendor
  details. The folder may be empty on an image that ships no built-in yet.

## The order of work

1. **Brief.** Learn what the outside system is, who will call the service (Agents, Apps or both), what
   they need to do with it, how it authenticates, whether it sends webhooks, and which targets you may
   write to while testing (a test board, a sandbox account). Ask only what you cannot find out.
2. **Design**, then **review Stop 1**: show the API and wait for approval before any handler exists.
   `references/review-stops.md` has the exact shape.
3. **Manifest.** Write `service.json` from the approved design (`references/manifest.md`), then
   `yarn check` until it reports no error and every warning is one you can justify.
4. **Types.** `yarn types` rewrites `service.types.ts`; `yarn dev` already does this on every change.
5. **Handlers and unit tests** together, one Operation at a time (`references/handlers.md`).
6. **Inbound**, if the system sends webhooks (`references/inbound.md`).
7. **Service skill**: write `SKILL.md` (`references/service-skill.md`).
8. **Live tests** in the chat's Test Project, then the **test report**
   (`references/review-stops.md` §Testing).
9. **Hand over**: say what exists, what was tested and how, what was not and why, and that the service
   is ready for a human to publish.

`references/patterns.md` has the generic answers to recurring design questions: several accounts,
indirect ids, output filtering, pagination, rate limits, webhook registration, wrapping an OpenAPI
document, and SDK upgrades.

## The loop

```sh
yarn check        # external-service-cli check: the manifest and the icon
yarn types        # external-service-cli types: regenerate service.types.ts
yarn typecheck    # tsc: handlers against the generated types
yarn test         # node:test on the test kit
```

Commit every change that passes, `service.types.ts` and `yarn.lock` included. Production installs and
serves exactly what is committed (`yarn install --immutable`, then `serve`).

The CLI is `yarn external-service-cli <command>`:

| Command | What it does |
| --- | --- |
| `external-service-cli check [--built-in]` | Prints every `error`/`warning` with its path; exits 1 on an error |
| `external-service-cli types` | Writes `service.types.ts`; says `is up to date` when nothing changed |
| `external-service-cli dev` | Serves the folder on `$APP_PORT`, rewrites the types and restarts on every change (Development runs it) |
| `external-service-cli serve` | Serves without reloading (Production runs it) |
| `external-service-cli report --from <lines.json>` | Writes the test report the Publish dialog reads |
| `external-service-cli generate --from-openapi` | Writes `service.json` and a handler table from an OpenAPI document |

`generate --from-openapi` is newer than `1.0.0`: run `yarn external-service-cli --help` to see whether
the vendored SDK has it and which arguments it takes. `references/patterns.md` §Wrapping an existing
OpenAPI document says when to use it.

`dev` and `serve` refuse to start on a stale `service.types.ts`, a handler the manifest names but
`handlers.ts` lacks, or one `handlers.ts` has but the manifest does not name; the reason is on stderr
and in the platform's process logs. A running service answers `GET /_service/health` only with its
own key in `x-opsiforce-gate`:

```sh
curl -s -H "x-opsiforce-gate: $SERVICE_GATEWAY_API_KEY" "localhost:$APP_PORT/_service/health"
# {"sdk":1,"sdkVersion":"1.0.0","manifestHash":"…","handlers":{"operations":[…],…}}
```

## Rules on top of the chat's

- **Every write and destructive Operation is bounded**, or the person agreed in Stop 1 that it may touch
  anything the stored credentials reach; `check` warns on each one that is not.
- Stop 1, the live tests and the hand-over carry their own rules in `references/review-stops.md`: a
  later design change goes back to the person, live writes reach only targets the brief names, and the
  conversation prompt runs before "ready".

## Upgrading the SDK

A service runs the SDK version in its `vendor/` file name until someone upgrades it; the Gate accepts
every `1.x`. Compare the vendored `CHANGELOG.md` with
`/opt/opsiforce/external-service-sdk/latest/CHANGELOG.md`. **Suggest** an upgrade, and do it only once
the person agrees, when the newer version fixes a bug this service hits or adds something the person
asked for (a CLI command, a field feature, a `ctx` member). Never upgrade as a side effect of other
work. `references/patterns.md` §Upgrading the vendored SDK has the steps.
